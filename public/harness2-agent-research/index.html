학습 없이 개선?
바뀌는 건 하네스다.

Google Research 저장소의 Harness²는 실재한다. 프롬프트·도구·기억을 실행 증거로 고치는 연구다. 다만 이를 JEV 1.14의 비전 성능 입증으로 읽으면 안 된다.

2026.10.20 확인 · 원문 2026.10.19 · 논문·고정 커밋·실험 문서 대조

판정: 방법은 확인. JEV 성능은 보류.

확인 — 가중치를 고정하고 실행 하네스를 재귀적으로 개선하는 공개 코드와 논문이 있다.

저자 보고 — 전문 업무 벤치마크에서 개선. 독립 재현이나 모든 모델·작업의 성능 보장은 아니다.

미검증 — 원 게시물의 JEV 1.14 비전 성능 향상. 공개 수치·데이터·재현 가능한 연결 저장소를 이번 조사에서 확인하지 못했다.

검증 범위: 원문 본문과 미디어 메타데이터, 공식 코드·논문 초록·프로젝트 페이지·문서를 읽었다. 원문의 22초 영상을 시청·계측하지 않았고 프레임워크 설치·실행·벤치마크 재현도 하지 않았다. 본문의 수치는 모두 연구 저자 보고다.

원문과 연구 구분작동 원리수치의 범위도입 판단출처

01 / 같은 글에 등장해도, 같은 증거는 아니다

JosephZhou(@openmys)의 10월 19일 글은 “Google Research의 Harness²를 JEV 1.14에 연결했고, 가중치를 건드리지 않고 비전 벤치마크가 크게 올랐다”고 주장한다. 프롬프트 수정·도구 제작·경험 축적을 설명하고 마지막에는 “JEV-Harness² repo drops soon”이라고 적었다. 게시 시각은 03:35 UTC, 한국 시각 12:35다. 읽기 전용 미러로 원문을 확인했으며, 인용된 다른 사람의 Harness² 소개와 원 게시물을 분리했다.

Google의 공개 연구와 JEV 결합 시연은 별개다. 공식 Harness²의 공개 평가 대상은 전문·법률·사무 업무다. 이 숫자를 JEV 비전 벤치마크 수치로 옮겨 적을 수 없다. 원문에는 데이터셋 이름, 전후 점수, 반복 수, 비용과 평가 조건이 적혀 있지 않다.

작성자 홈페이지가 연결한 GitHub 공개 저장소 목록과 검색에서 해당 JEV-Harness² 연결 저장소를 확인하지 못했다(10월 20일 확인). 이것은 “세상에 없다”는 판정이 아니라 공개 검증 경로를 확보하지 못했다는 뜻이다. JEV 1.14의 정체·버전·라이선스도 이 자료만으로 확정하지 않는다.

반면 google-research/harness2는 공개 저장소다. 최초 커밋 메시지 “Initial commit of Harness2 open-source release”는 10월 8일 UTC, 논문 v1 제출은 2026년 10월 9일 18:34 UTC다. 커밋 날짜가 GitHub의 실제 공개 전환 시각을 보증하지는 않는다. 확인 시 별도 GitHub Release 항목은 없으며, 이 글은 10월 14일 커밋 1cfe254e8d25에 고정했다.

02 / 자기개선의 대상은 두 겹이다

하네스는 모델 주위에서 일을 가능하게 하는 프롬프트·도구 안내·메모리·스킬·위임·실행 규칙이다. 모델의 신경망 가중치를 다시 학습하는 대신 이 주변 구성을 바꾼다. “학습 없이”는 추가 실행과 비용 없이라는 말이 아니다.

제안 Propose → 시험 실행 Probe → 증거를 비교해 결합 Compose
  1. 현재 작업 안에서: 일반적 수정과 작업 특화 수정을 제안하고, 같은 작업에 후보 하네스를 실행한다. 결과·행동의 차이를 비교해 채택할 구성을 만든다. 병렬 모드는 여러 후보를 넓게, 순차 모드는 앞선 구성을 이어받아 깊게 탐색한다.
  2. 다음 작업을 위해: 채택한 하네스와 증거로 뒷받침된 교훈을 개선용 라이브러리에 남긴다. 공식 문서상 같은 도메인 작업은 순서대로 실행하며 앞선 기록만 읽는다. 모든 후속 작업이 직전 실행 하네스를 그대로 물려받는다는 뜻은 아니다.

공개 구현의 편집 대상은 시스템 프롬프트, 가드레일, 메모리, 도구 안내, 하위 에이전트, 스킬, 스크립트, 플러그인이다. 편집 가능하다는 설명은 운영 시스템의 권한·보호 규칙을 자동으로 풀어도 된다는 승인이 아니다.

“정답 없이 개선”이면 평가도 필요 없는가?

아니다. 개선 단계가 정답·채점기 피드백 없이 실행 간 차이를 활용한다는 주장이다. 최종 점수는 별도 평가 단계에서 얻는다. 공식 사용 흐름도 refinement → judge → report를 구분한다. “채점 없이 모든 작업이 정확해졌다”거나 정답 검증이 불필요해졌다고 해석하면 틀린다.

03 / 확인한 숫자, 확인하지 못한 숫자

논문 초록과 고정된 README가 보고한 단일 개선 단계의 최대 증가폭이다. GLM-5·Gemini 3.5 Flash, 네 가지 모델–하네스 조합과 세 전문 업무 벤치마크에 한정된다. 각 최대값이 하나의 동일 설정에서 모두 나온다는 뜻은 아니다.

연구 저자 보고 · 독립 재현 아님
평가최대 증가폭읽는 법
WorkBuddy-Bench+11.5점사무·웹·코드 업무 점수
JobBench+4.5점전문 업무 점수
LAB+11.8%p법률 업무 partial pass rate
JEV 1.14 비전확인 불가원문 주장, 별도 검증 필요

예컨대 공식 프로젝트 페이지의 Gemini 3.5 Flash / OpenCode WorkBuddy 평균은 기본 72.4 → k=1에서 77.5 → 병렬 k=5에서 80.8이다. 세 번 실행한 보고 평균이며, Code·Web·Office의 매크로 평균이다. 이 예는 +11.5점 최대값의 설정과 혼동하지 않는다.

11.8%p는 상대 11.8% 향상이 아니다. LAB 지표도 전체 작업 완전 성공률이 아니라 partial pass rate다. 더 많은 재귀 예산의 개선은 추가 추론·도구 실행을 사용한 결과이므로, 같은 비용·같은 지연시간에서의 우월성을 자동으로 뜻하지 않는다.

원문 영상의 애니메이션이나 시연 화면을 실제 벤치마크 로그·독립 평가로 간주하지 않았다. 이번에는 JEV 데이터셋·전후 점수·통제된 비용·홀드아웃 성능이 미확인이다.

04 / 실무에서는 “자동 채택”보다 “증거 있는 제안”

배울 만한 설계

반복 실패를 사람이 추측으로 고치는 대신, 후보 변경을 작게 만들고 실제 산출물·도구 사용·회귀 결과로 비교한다. 효과가 확인된 교훈만 다음 작업의 개선 절차에 반영한다.

바로 운영에 붙이기는 보류

후보 실행과 평가의 비용, 권한 범위, 수정 이력·되돌리기, 별도 홀드아웃이 필요하다. 이 글의 평가는 연구 설계에 대한 것이며 우리 서비스에 적용했다는 뜻이 아니다.

  1. 총비용을 함께 보자. 여러 기준·후보·결합 실행과 반성 단계가 호출을 늘린다. 공식 문서는 모델 기반 실행의 API 비용을 명시한다. 점수뿐 아니라 작업당 총비용·지연시간·실패 복구를 동일 조건에서 비교해야 한다.
  2. 평가 유출을 막아야 한다. 공식 README는 실행기의 네트워크 접근이 제한되지 않고 Codex 샌드박스가 꺼져 있다고 경고한다. 실험 문서에는 검증 중 한 Codex 실행이 공개 JobBench rubric을 내려받았다는 사례까지 있다. 이는 모든 논문 결과가 유출됐다는 증거는 아니지만, 재현 시 네트워크 격리와 채점 정보 차단을 명시해야 하는 이유다.
  3. 보안 규칙과 수정 범위를 분리하자. 실험용 작업 공간·허용 목록·변경 검토·롤백을 두는 것이 이 글의 운영 권고다. 에이전트가 보호 규칙 자체를 임의로 약화하는 구성은 채택하지 않는다.
  4. 코드와 데이터의 권리는 별개다. Harness² 코드는 Apache-2.0. 서드파티 코드·벤치마크·데이터셋은 각 원래 라이선스를 유지한다. JEV 결합 코드의 라이선스를 이 라이선스로 추정할 수 없다. 공식 README는 “공식 지원 Google 제품이 아니다”라고 명시한다.

최종 결론: Harness²는 “모델을 다시 훈련하지 않고 에이전트의 작업 방식을 개선”하는 실재하는 연구다. 전문 업무 결과는 저자 보고로 소개할 수 있다. JEV 1.14 비전 성능이 크게 오른다는 주장은 공개 재현 자료가 확인될 때까지 보류한다. 코드 설치나 운영 하네스 변경은 하지 않았다.
