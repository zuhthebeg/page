M4 Max 64GB로 GLM 5.2 돌릴 수 있나

753B 파라미터 오픈모델 GLM 5.2를 회사에서 굴러다니는 M4 Max 64GB 맥북들로 exo 분산클러스터를 짜서 실제로 돌릴 수 있는지, 공식 모델 스펙과 하드웨어 스펙을 교차 계산해 확인했다.

01 GLM 5.2 스펙

Z.ai(구 Zhipu)가 2026-06-16 MIT 라이선스로 공개한 코딩 특화 MoE 모델. 공식 블로그 기준 스펙은 다음과 같다.

항목값
총 파라미터~744B (소스에 따라 753B로도 표기)
활성 파라미터/토큰~40B (MoE, 256개 전문가 중 8+1 활성)
레이어 수78
은닉 크기6,144
컨텍스트최대 1M 토큰 (IndexShare 스파스 어텐션)
어텐션Multi-head Latent Attention + DeepSeek Sparse Attention

MoE라 연산량은 40B급이지만, 메모리에는 전체 744B 가중치가 다 올라가 있어야 한다 — 토큰마다 어떤 전문가가 활성화될지 미리 알 수 없기 때문. 클러스터 사이징은 활성 파라미터가 아니라 총 파라미터 기준으로 해야 한다.

02 메모리 계산 — 몇 대 필요한가

실제 배포된 mlx-community/GLM-5.2-4bit (zai-org/GLM-5.2를 MLX 포맷으로 변환, mlx-lm 0.31.3)의 실측 모델 크기는 418GB다. M4 Max 64GB의 실사용 가능 GPU 메모리는 기본값 기준 ~48GB(macOS wired memory 한도, 튜닝 시 최대 ~58GB까지 확장 가능하나 시스템 안정성과 트레이드오프).

양자화모델 총 용량노드당 48GB 기준 필요 대수
4-bit (mlx-community 실측)418GB9대 (여유 없이 딱 맞음)
8-bit (추정)~753GB16대
bf16 풀정밀 (추정)~1.49TB31대

4-bit 기준 최소 9대. 이건 가중치 저장 공간만 계산한 숫자다. KV 캐시·exo/MLX 통신 버퍼·OS 오버헤드를 얹으면 9대는 여유가 전혀 없다. 안전 마진 포함 10대를 목표로 잡는 걸 권장한다. GLM 5.2는 MLA(Multi-head Latent Attention) 구조라 KV 캐시 자체는 표준 어텐션보다 가벼운 편이지만, 1M 토큰급 롱컨텍스트를 실제로 쓰면 이 여유가 금방 사라진다.

참고: mlx-community 모델카드에 "현재 퀀트에는 MTP(speculative decoding) 블록이 빠져 있다"는 명시가 있음 — GLM 5.2가 홍보하는 "MTP로 토큰 가속 최대 20%" 효과가 이 4bit 버전엔 아직 적용 안 됐을 수 있다.

하드웨어 스펙 자체는 문제없다. M4 Max 64GB는 Thunderbolt 5를 기본 탑재하고, JACCL(RDMA over Thunderbolt)이 요구하는 macOS 26.2 이상만 맞추면 exo의 텐서 병렬 경로를 쓸 수 있다.

04 리스크 — 계산은 통과해도 실증은 아직

  • exo의 GLM-5 계열 지원이 확정 안 됨. exo 저장소에 "Request to add support for GLM-5" (#1468)가 오픈 이슈로 존재한다. mlx-community 쪽엔 이미 MLX 변환 가중치가 있어서 모델 자체는 로드 가능할 확률이 높지만(exo가 "커스텀 모델은 HuggingFace에서 로드 가능"이라 명시), MoE 256개 전문가를 exo의 자동 샤딩이 효율적으로 나눠줄지는 실제로 붙여봐야 안다. 시도 전에 이슈 상태부터 확인할 것.
  • exo 자체 공개 벤치마크는 전부 4대 이하. exo가 공식 제시하는 텐서 병렬 스피드업 수치(2대 1.8배, 4대 3.2배)와 M3 Ultra Mac Studio 4대 클러스터 사례들은 전부 4대 규모에서 나온 것이다. 이번 계산이 요구하는 9~10대 규모 RDMA 텐서 병렬은 공개적으로 검증된 사례를 찾지 못했다. 노드가 늘어날수록 통신 토폴로지(데이지체인이냐 허브 메시냐)가 성능에 미치는 영향이 커지는데, 이 규모에서는 미지수다.
  • 사무실 배선 문제. Thunderbolt는 직결이 기본이라, 노트북 9~10대를 어떻게 물리적으로 연결할지(TB5 허브 다수 구매 또는 데이지체인 설계)가 별도 과제다. 안 되면 RING(TCP, 일반 네트워크) 백엔드로 폴백되는데 훨씬 느려진다.
  • 9~10대 확보 자체가 리소스 허들. M4 Max 64GB는 흔한 스펙이 아니다. 사내에서 동시에 그만큼을 빌려 쓸 수 있는지가 기술보다 먼저 걸리는 문제일 수 있다.

05 권장 실행 순서

  1. 바로 9~10대로 GLM 5.2 도전 금지. 확보 난이도도 높고, exo 다중노드 RDMA 자체를 처음 만져보는 상태에서 최대 난이도로 시작하면 실패 원인 진단이 어렵다.
  2. 2~4대로 먼저 exo+JACCL 파이프라인부터 검증. 훨씬 작은 오픈모델(예: 100GB대 모델, mlx-community에 있는 것)로 디바이스 자동 디스커버리·RDMA 활성화·텐서 병렬이 실제로 동작하는지 확인한다. exo 공식 벤치마크와 같은 규모라 비교 기준도 있다.
  3. GLM-5 이슈(#1468) 상태 재확인. 클로즈됐으면 네이티브 지원, 아니면 mlx-community/GLM-5.2-4bit를 커스텀 모델 경로로 직접 지정해서 로드 시도.
  4. 대수를 늘려가며 스케일 검증. 4대에서 되는 걸 확인한 뒤 6대, 8대로 늘리며 스피드업 곡선이 꺾이는 지점을 직접 관측한다. 이 곡선 자체가 사내 회사놀이 데모/보고서 소재로도 값어치 있다.
  5. 최종적으로 9~10대 GLM 5.2 클러스터. 위 단계를 통과한 뒤에 시도. 메모리 여유가 없으므로 KV 캐시를 짧게(수천~수만 토큰) 잡고 시작해서 점진적으로 늘린다.

06 결론

이론적으로는 가능하다. 4-bit 양자화 기준 418GB, M4 Max 64GB 노드당 실사용 ~48GB로 나누면 최소 9대, 안전 마진 포함 10대면 메모리는 맞는다. 하드웨어 요건(TB5, RDMA)도 M4 Max가 충족한다.

다만 exo가 이 정도 규모·이 모델을 실제로 잘 처리한다는 공개 증거는 없다 — GLM-5 계열 지원은 오픈 이슈 상태고, 텐서 병렬 벤치마크는 전부 4대 이하에서만 나왔다. "계산상 된다"와 "회사에서 켜보면 된다" 사이에 검증되지 않은 구간이 있다는 뜻이다. 처음부터 9~10대로 밀어붙이지 말고, 2~4대 소규모로 exo 자체의 동작을 먼저 확인한 뒤 단계적으로 규모를 키우는 게 실패 확률을 크게 낮춘다.
