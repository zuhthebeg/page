단일 엔드포인트 뒤의 선택:
사내 LLM 게이트웨이를 어디에 세울 것인가

시맨틱 라우터(vLLM SR)와 멀티프로바이더 게이트웨이(OmniRoute)를 게이트웨이 운영자 관점에서 해부한다. 무엇을 도입하고, 무엇을 공부하고, 우리 게이트웨이를 어디로 진화시킬 것인가.

작성 cocy — LLM Gateway / Platform 일자 2026-07-23 범위 사내 도입 의사결정

LLM 게이트웨이를 운영하는 입장에서 "라우터 하나 붙이자"는 말은 위험하다. 게이트웨이는 컨트롤 플레인이다 — 어느 요청이 어느 모델·어느 컴퓨트·어느 데이터 경계로 흐르는지를 결정하고, 그 결정을 관측·감사·통제할 수 있어야 한다. 최근 화제가 된 두 프로젝트, vLLM Semantic Router와 OmniRoute는 이름은 비슷해도 서로 다른 층에 산다. 개인 생산성 도구를 사내 표준 컨트롤 플레인으로 착각하면, 3개월 뒤 키 유출·거버넌스 부재로 되돌린다.

이 문서는 세 대상을 같은 기준으로 세운다: (1) vLLM SR, (2) OmniRoute, (3) 현재 우리가 운영 중인 자체 게이트웨이(서버리스 Worker + AI Gateway). 결론부터: 쓸 것과 배울 것이 다르다.

01운영자의 평가축 — 도구 기능이 아니라 통제 가능성

기능 목록은 마케팅이 정한다. 도입 여부는 운영 가능성이 정한다. 게이트웨이를 굴려본 사람이 실제로 보는 8개 축:

  1. 배포 모델 — 서버리스 / 사이드카(Envoy) / 데스크톱-앱. 우리 SRE 운영 표준에 얹히나.
  2. 라우팅 방식 — 명시(모델명 지정) / 의미기반(요청 신호로 판단) / 프로바이더 폴백(쿼터 소진 시 전환). 정책을 코드로 표현·버전관리할 수 있나.
  3. 비용 거버넌스 — 캐싱, 무료티어 활용, 예산 상한, 요청별 원가 귀속.
  4. 관측성·감사 — 라우팅 결정 로그, 리플레이, 요청 추적. 사고 났을 때 "왜 이 모델로 갔나"를 복기할 수 있나.
  5. 키·시크릿 보안 — BYOK 키가 어디에 어떻게 저장되고, 누가 접근하나. 키 집중은 단일 유출점이다.
  6. 데이터 경계·컴플라이언스 — on-prem/edge로 민감 요청을 가둘 수 있나. 데이터 residency.
  7. 벤더 성숙도·리스크 — 라이선스, 소유 조직, 나이, 커뮤니티 실체, 릴리스 안정성.
  8. 정책·확장성 — 규칙→ML/RL 라우팅, 안전 필터, 플러그인. 조직이 커질 때 확장되나.

02대상 프로파일 — 하드팩트로 본 실체

vLLM Semantic Router Apache-2.0 Go

★ 5.0kfork 770생성 2025-08소유 vllm-project(공식)버전 v0.3 Themis

요청을 16개 신호군(의도·안전·도메인·난이도…)으로 분류해 이기종 모델풀로 의미기반 라우팅하는 시맨틱 라우터. 앱은 /auto 엔드포인트 하나만 호출하고, 라우터가 뒤에서 싼/센/로컬 모델을 조합한다. Envoy ExtProc 사이드카 또는 독립 데몬으로 배포. 12개 라우팅 알고리즘(규칙→지연 휴리스틱→RL), 시맨틱 캐싱, 환각 탐지, 안전 플러그인, 결정 리플레이. AMD 협업, arXiv 논문(WRP 아키텍처·signal-driven routing) 다수. 연구 성숙도는 높고 제품 성숙도는 0.x.

OmniRoute MIT TypeScript

★ 26.0kfork 3.4k생성 2026-02(5개월)contributor ≈278버전 v3.8.49

단일 OpenAI 호환 엔드포인트로 278+ 프로바이더 / 500+ 모델을 통합하는 실용형 게이트웨이. 핵심은 무료티어 스태킹(43개 풀의 무료 한도를 합산해 잔량을 대시보드로), 쿼터 소진 자동 폴백(재로그인 없이 다음 프로바이더로), 토큰 압축(RTK+Caveman, 15–95% 주장). Claude Code·Codex·Cursor·Cline·Copilot에 바로 물리고 Desktop/PWA 제공. 개발자 비용 절감 도구로는 강력하나, 5개월 된 프로젝트에 ★26k는 실사용과 화제성이 섞여 있다 — README의 "500+ contributors"는 실측 ≈278로 과장.

자체 게이트웨이 (llm.cocy.io) 현행 CF Worker

배포 서버리스라우팅 명시(모델명)폴백 Claude→GPT인증 Bearer/BYOK

Cloudflare Worker + AI Gateway 위에서 모델명으로 명시 라우팅. OpenAI 직접 경로 / 구독 CLI 경로 / Claude CLI 경로를 모델 alias로 분기하고, 실패 시 상위 폴백. 서버리스라 운영 부담이 낮고 리전 우회에 강하지만, 의미기반 라우팅·결정 감사·정책 관리가 없는 "얇은" 컨트롤 플레인이다. 우리의 실전 레퍼런스이자, 이 검토의 개선 대상.

04도입 시나리오별 답 — 하나의 정답은 없다

A. 개인·팀 개발 생산성 (코딩 에이전트 비용 절감)

→ OmniRoute, 단 자체호스팅 + 키 격리 전제. Claude Code/Codex에 물려 무료티어를 쌓고 쿼터 소진 시 자동 폴백하는 건 즉시 체감 이득이다. USER 원칙(유료 API 회피·무료/로컬 우선)과도 맞는다. 다만 남의 호스팅 인스턴스(omniroute.online)에 키를 주지 말 것 — MIT라 직접 띄우고, 전용 키·감사 로그·아웃바운드 도메인 제한을 건다. 토큰 압축 15–95%는 best-case이며, 우리 실측(반복 JSON에서만 큼)으로 보수적으로 기대할 것.

B. 팀 공용 게이트웨이 (우리 llm.cocy.io의 다음 단계)

→ 자체 게이트웨이를 "정책+폴백+관측성" 있는 미니 컨트롤 플레인으로 진화. OmniRoute를 통째로 표준화하기엔 거버넌스가 부족하고, vLLM SR을 얹기엔 서버리스 스택과 결이 다르다. 대신 두 프로젝트에서 패턴을 훔친다: OmniRoute의 쿼터-aware 폴백 로직, vLLM SR의 신호기반 난이도 라우팅(간단한 요청은 싼 모델로)·결정 로깅. 현재의 명시 라우팅 위에 이 두 층을 얹는 게 가장 현실적인 ROI다.

C. 엔터프라이즈 에이전트 플랫폼 (사내 표준 후보)

→ vLLM SR을 PoC 대상으로. 조직 규모의 게이트웨이가 요구하는 것 — 의미기반 라우팅, 정책 as code, 결정 감사·리플레이, 데이터 경계, 안전 필터 — 을 아키텍처 수준에서 갖춘 유일한 후보다. WRP(Workload-Router-Pool) 논문은 사내 PoC 설계의 골격으로 쓸 만하다. 리스크는 0.x API churn과 Envoy 운영부담 — 그래서 표준 채택이 아니라 통제된 PoC로 시작한다.

05도입 전 거버넌스 체크리스트

어느 도구든 사내에 들이기 전 통과해야 하는 관문. 하나라도 막히면 도입이 아니라 실험으로 격하한다.

  • 키 격리 — BYOK 키는 게이트웨이 전용 vault/시크릿에. 개인 키 재사용·평문 저장 금지. 유출 시 폭발 반경 산정.
  • 아웃바운드 통제 — 게이트웨이가 어느 외부 도메인으로 나가는지 화이트리스트. 민감 요청의 프로바이더 경유 금지 규칙.
  • 결정 감사 — 요청→선택모델→근거를 로그로. 사고 복기 가능해야 도입 가치가 있다.
  • 폴백 SLO — 폴백이 품질 저하로 이어질 때의 허용선 정의. "싸게 됐지만 답이 틀렸다"를 측정.
  • 라이선스·데이터 약관 — 무료티어 프로바이더의 데이터 학습 정책 확인(무료 = 데이터로 지불일 수 있음).
  • 벤더 이탈 대비 — 0.x/개인 주도 프로젝트는 스냅샷 고정 + 우리 어댑터 뒤에 격리. 업스트림 급변에 서비스가 흔들리지 않게.

06결론

Bottom line

OmniRoute는 쓰고, vLLM SR은 배우고, 우리 게이트웨이는 진화시킨다. OmniRoute는 개발 생산성 파일럿(자체호스팅·키 격리 전제)으로 당장 이득이 나는 도구다. vLLM SR은 엔터프라이즈 컨트롤 플레인의 참조 아키텍처이며 사내 PoC의 교본이다. 그리고 그 사이에서 우리 llm.cocy.io를 얇은 프록시에서 정책·폴백·관측성을 갖춘 컨트롤 플레인으로 끌어올리는 것이, 게이트웨이 운영자 포지션에서 가장 큰 레버다.

도구를 고르는 일이 아니라, 우리가 어떤 컨트롤 플레인을 소유할지를 정하는 일이다. 단일 엔드포인트 뒤에 무엇을 세우느냐가 곧 플랫폼의 성격을 정한다.
