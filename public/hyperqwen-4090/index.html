EVIDENCE BEFORE UPTIME

381 tok/s.
그래서 4090을
다시 켤 때인가?

HyperQwen은 흥미로운 추론 스택이다. 하지만 문서에 있는 말을 빠르게 되돌려 주는 능력과, 새 답을 잘 만드는 능력은 같은 지표가 아니다.

2026.10.14 확인 · 한국어 출처 검증 · GPU 실측 없음

판정: 켜 볼 가치는 있다. 맡겨 둘 근거는 아직 없다.

조건부 GO — 이미 있는 RTX 4090 24GB에서, 격리된 1인용 파일럿.

지금은 NO — 24/7 상시 운영, 프로덕션 에이전트 전면 교체, 이 숫자만 보고 GPU 구매.

381 tok/s는 일반 채팅 약속이 아니다. 속도·정확성·전력의 교환을 실제 업무에서 확인한 뒤 결정한다.

검증 범위: 원문·저장소·모델 카드·라이선스를 읽었다. 아래 속도는 개발자 또는 외부 사용자의 보고이며, 우리가 측정한 성능은 없다. 대상 4090 PC의 실제 GPU·RAM·저장장치·가동 상태도 확인하지 않았다. 설치나 설정 변경은 하지 않았다.

숫자의 조건왜 빨라지나4090의 의미품질·운영 위험파일럿 기준출처

01 / 원문은 이미 단서를 달았다

원 X 게시물 [1]은 82 → 114 → 138 → 381 tok/s의 개선 과정을 설명한다. 동시에 일반 대화는 약 133 tok/s이고, 최고 수치는 약 25k 토큰 문서를 재현하는 작업이라고 분명히 적었다. 원문 자체를 “모든 채팅이 4.6배”라고 읽는 건 잘못이다.

127tok/s · 1인용

현재 README의 RTX 3090 단일 스트림 보고.

381tok/s · 문서 재현

입력의 문장을 그대로 출력하는 특수 작업.

1,035tok/s · 64개 합계

동시 요청 64개의 총 decode 처리량. 한 사람의 속도가 아니다.

모두 개발자 보고. 현재 README의 127과 예전 게시물의 약 133은 버전·조건이 다른 숫자다. 새 수치가 옛 측정을 무효화하거나, 옛 수치가 현행 버전을 보장하는 것은 아니다. [2]

최적화 문서 [3]의 비교는 더 구체적이다. 같은 25k 컨텍스트에서 첫 60줄을 그대로 재현하면 lookup 없음 159 → 기존 lookup 260 → 긴 검증 블록 381 tok/s였다. 그러나 자유 요약·Q&A는 같은 표에서 약 67–72 tok/s다. “25k 문서 RAG라면 전부 381”도 아니다.

두 번째 질문의 TTFT 22.4초 → 0.56초는 게시물이 전한 공유 접두사 캐시 재사용 사례다. 첫 요청을 약 40배 빠르게 만든 게 아니고, 새 문서나 캐시 미스에서 같은 효과가 보장되지 않는다. decode 속도와 첫 토큰 대기시간도 분리해야 한다. [1]

02 / 새 모델이 아니라, 검증을 덜 반복하는 스택

기존 qwen38-27b-rtx3090 저장소는 지금 HyperQwen으로 이름이 바뀌었다. Qwen3.8-27B 양자화 모델, 준비 파이프라인과 고정 vLLM 패치 묶음을 결합한다. 모델의 정체를 바꿔 더 똑똑하게 만든다는 주장과는 다르다. [2]

초안 제안 → 본 모델이 묶음 검증 → 통과한 토큰만 출력
  • MTP: 모델의 다중 토큰 예측 헤드가 초안을 제안한다. 잘 맞을수록 한 번의 본 모델 검증에서 여러 토큰을 얻는다.
  • DFlash2: 작은 블록 드래프터가 여러 위치를 병렬로 예측하고, 후보 선택기와 짧은 convolution으로 초안의 일관성을 높인다.
  • Context lookup: 출력이 입력과 겹칠 때 컨텍스트에서 다음 구간을 찾아 초안으로 쓴다. 복사 중일 때만 긴 검증 블록을 채우기 쉽다.
  • Prefix cache: 이전에 처리한 입력의 공유 부분을 재사용한다. 출력 초안과는 별개로 입력 처리 시간을 줄인다.

재현 작업의 약 14.97 토큰/step은 그 작업에서의 결과이지, 모든 초안의 보편적 수락률이 아니다. 긴 블록 설정은 8 → 4 요청 슬롯, 64k → 56k 컨텍스트의 비용도 낸다. [3]

논문과 “품질 손실 없음”을 정확히 읽기

DFlash 논문은 원래 DFlash를 다룬다. DFlash2는 2026-08-18 Inco 기술 발표와 모델 카드로 확인했다. 이 논문을 DFlash2의 별도 논문처럼 인용하지 않는다. 발표의 다른 하드웨어 속도 향상도 4090의 성능 증명이 아니다.

위치별 수락은 앞선 위치가 맞았다는 조건에 달린다. 초안이 틀리면 본 모델이 거절하거나 보정한다. 올바른 검증·rejection sampling 구현은 동일한 대상 모델의 출력 분포를 보존하도록 설계된다. 그렇다고 양자화 모델이 원본 BF16과 같아지거나, 코드·도구 실행이 안전해지는 것은 아니다. HyperQwen 문서도 긴 greedy 비교 9개 중 7개만 토큰 동일했고, 나머지는 근접 점수 차이라고 기록한다. [3][8]

03 / 4090이면 3090보다 훨씬 빠른가?

외부 사용자 재현 보고 · 직접 실측 아님

외부 사용자 이슈 #32는 native Linux의 RTX 4090에서 135.5 tok/s, 당시 3090 기준은 133 tok/s라고 보고했다. 4090은 450W 한도, 3090은 250W 한도였다. 이는 전력 한도이지 지속 소비전력 실측값이 아니다. 저장소 버전은 bbc6c0f다. [4]

해당 보고자의 해석은 batch-1 decode가 메모리 대역폭에 묶인다는 것이다. 4090의 추가 연산량만큼 단일 사용자 속도가 뛰지 않았다. 조건이 다른 외부 비교이며 최신 README 127과의 맞춘 A/B 테스트도 아니다. 그래도 “4090이니 자동으로 4배”라는 기대를 버릴 근거는 된다.

따라서 이미 가진 24GB 카드를 로컬 작업의 후보로 평가할 이유는 있다. 반대로 이 워크로드 하나 때문에 새 4090을 사라는 근거는 약하다. 12GB 단일 카드에 같은 구성을 그대로 적용하는 결론도 이 자료에서 나오지 않는다. [2]

04 / 빠르게 부팅하는 것과, 안정적으로 맡기는 것

품질: 숫자를 읽되 범위를 지켜야 한다

개발자의 품질 문서 [5]는 IFBench 299개 프롬프트에서 W4A16 strict prompt-level 78.3을 보고한다. 원본 모델 카드의 79.5와 비교하지만, 같은 환경에서 원본을 재실행한 통제 비교는 아니다. fast 구성의 GSM8K는 200문항에서 96.5%, PPL은 base 8.045에서 8.095다. 이것만으로 한국어 코드 수정이나 도구 JSON의 정확성, 긴 에이전트 작업을 보장할 수 없다.

한국어: MTP의 작은 어휘 목록은 별도 함정

gotcha 61은 기본 MTP 드래프트 어휘가 영어·덴마크어·코드 중심이라고 설명한다. Hangul 행은 6,807개 중 4개만 포함한다는 보고다. 이는 토큰 행 개수이지 한국어 실사용 수락률 측정은 아니다. 중국어의 MTP 속도 저하가 보고됐지만 그 수치를 한국어 예측값으로 옮기면 안 된다. DFlash2는 이 목록을 쓰지 않는다. 긴 컨텍스트 때문에 MTP 모드로 전환한다면 한국어 수락·품질을 따로 평가해야 한다.

WSL2: 캐시와 공유 메모리가 숨은 변수

WSL2 4090 외부 재현 [6]은 구동 가능성을 뒷받침한다. 그러나 초기 부팅의 compile/JIT 캐시 상태, 재시작 시 물려받은 캐시, 컨텍스트 깊이에 따라 측정이 바뀐다. 문서에는 원인을 잘못 지목했다가 취소한 결과도 남아 있다. 한 번의 cold run을 버전 성능으로 단정하지 말고, TTFT와 decode를 따로 기록해야 한다.

vLLM 0.31 검증 문서 [7]에서는 기본 single-user의 4090 WSL2 부팅·응답과 no-spill이 보고됐다. 반면 실험 프로필은 로딩 중 Shared Usage가 1.3GB까지 올랐다가 약 100MB로 내려갔다. 부팅 성공만 확인할 게 아니라 VRAM과 호스트 공유 RAM을 함께 봐야 한다. 이 값 역시 외부 테스트의 결과이며 목표 PC의 예측값이 아니다.

0.31 CPU KV offload: 기본 채팅 전체의 장애는 아니다

같은 문서에서 8GB CPU KV tier가 꽉 차서 eviction이 일어나는 경우, 두 긴 대화의 다음 턴 캐시 재사용이 0으로 떨어지는 회귀가 보고됐다. 이전 0.30은 해당 비교에서 96.3%를 재사용했다. 현행 패치 시리즈는 upstream PR #61050을 포함하지만, native 3090의 8GB 결과는 85.2% / 82.1%로 부분 회복이며 한 부팅의 결과다. 이 행이 patched 4090의 완전한 회복을 증명하지는 않는다. 초기 파일럿은 CPU tier와 실험적 긴 컨텍스트 확장을 피하는 쪽이 낫다. [7]

모델 존재와 라이선스 — 확인한 범위

HyperQwen 코드와 원본 Qwen3.8-27B는 실제 존재하고 Apache-2.0 LICENSE를 확인했다. 기본 준비 스크립트가 선택하는 W4A16 양자화 대상 모델, fast 추가 텐서와 양자화 DFlash2 드래프터의 모델 카드도 Apache-2.0을 명시한다. 별도 LICENSE 파일을 읽었다는 뜻은 아니다. 드래프터는 독립 채팅 모델이 아니다. 배포 시 각 산출물의 저작권·라이선스·변경 고지 의무를 확인해야 한다. [9][10][11]

HF 원본 pin: 1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0. 저장소 pin: 95ee3b64b0df7014ee2626529524d6b99c3dcdd1. 이 글은 해당 시점 문서의 검증이며 미래 버전 보증이 아니다.

05 / 30–60분만 켜서 무엇을 볼까

다음은 제안하는 합격 기준이지 실측 결과나 예상 성능이 아니다. 실제 하드웨어·여유 RAM·디스크·전력 여건을 먼저 확인하고, 설치를 별도로 승인한 뒤에만 진행한다. README상 첫 준비는 약 9.5GB 이미지와 약 20GB 모델 작업이 필요하다. 다운로드·준비 시간은 아래 30–60분에 포함하지 않는다. 이번 검증에서는 둘 다 받지 않았다. [2]

  1. 0–10분 / 격리·고정. 1인용 기본 모드, 고정 소스/이미지/모델 버전을 기록한다. 외부 공개 없이, 실제 계정·비밀정보·쓰기 가능한 업무 도구를 연결하지 않는다. 기존 에이전트와는 분리한다.
  2. 10–35분 / 같은 입력으로 세 종류. 한국어 일반 대화, 작은 코드 수정, 약 25k 토큰 문서의 인용·자유 요약을 각각 10회씩 비교한다. 프롬프트·출력 길이·샘플링을 고정하고 cold와 반복-prefix warm을 구분한다. TTFT p50/p95, decode tok/s와 전체 요청시간을 따로 기록한다. 표본이 작으므로 p95는 탐색 지표다.
  3. 35–50분 / 실제로 맞는지. 코드 diff를 확인하고 테스트한다. 인용이 원문에 존재하는지 확인한다. mock 도구로 JSON 스키마·도구 이름·인자·도구 선택의 의미를 채점한다. 파싱 성공만으로 정답 처리하지 않는다.
  4. 50–60분 / 비용과 판정. VRAM peak, 공유 RAM 증가, OOM·재시작·오류, 실제 GPU/가능하면 콘센트 전력·소음과 지연을 기록한다. 전력 한도를 바꿔 최적화하는 단계는 아니다.
파일럿 합격안
  • 세 워크로드 모두 10회 완료, OOM·프로세스 재시작 0회. 공유 RAM의 지속 증가나 spill에 따른 지연 급증이 없을 것.
  • 고정 코드 테스트 전부 통과, 인용 근거 전부 확인, mock 도구의 스키마와 기대 의미 전부 일치. 예상 밖 도구 실행은 즉시 중단.
  • 업무별 허용 TTFT·전체 지연·전력 기준을 측정 전에 적고 만족할 것. 381이라는 숫자를 합격선으로 쓰지 않을 것.
  • 통과해도 다음 단계는 제한된 실제 업무 평가다. 30–60분 테스트를 24/7 안정성이나 프런티어 모델 대체 증명으로 취급하지 않을 것.

결론: 지금 켤 이유는 “381을 내기 위해서”가 아니다. 로컬에서 반복 문서·작은 코드 변환을 처리할 실용적인 보조 경로인지 확인하기 위해서다. 그 정도의 격리 파일럿에는 조건부 GO. 상시 서비스와 에이전트 전면 교체에는 아직 NO.
