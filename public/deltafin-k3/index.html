64GB 맥 한 대에서 2.8조 파라미터 — Deltafin이 Kimi K3를 굴린 방법

가중치만 1.56TB인 MoE 모델 Kimi K3(2.8T 파라미터)를, RAM 64GB짜리 M1 Max 한 대에서 실행한 오픈소스 프로젝트 Deltafin이 공개됐다. VRAM도 클러스터도 없이 "모델은 SSD에 두고, 토큰마다 필요한 조각만 읽는다"는 접근이다. 레포 문서와 공개 벤치마크를 직접 읽고 숫자를 검증했다.

01 무엇이 공개됐나

Kimi K3는 Moonshot AI의 2.8조 파라미터 Mixture-of-Experts 모델이다. MXFP4 양자화 기준 가중치가 safetensors 96개 샤드, 약 1.56TB — 어지간한 워크스테이션 RAM에도, 당연히 어떤 단일 GPU에도 안 들어간다. Deltafin은 이걸 Apple Silicon 맥(및 Linux)에서 돌리는 추론 엔진으로, Moonshot의 모델링 코드를 수정 없이 그대로 쓰고 CUDA 전용 커널만 순수 PyTorch 심으로 대체했다.

항목값
총 파라미터~2.8T (MoE)
가중치 총량~1.56TB (MXFP4, 96 shards)
라우팅 전문가82,432개 (~1.45TB) — 레이어당 896개 중 16개 선택 × 92 레이어
상주 스파인 (어텐션·공유전문가·임베딩)~114GB bf16 → int8 변환 시 ~60GB
토큰 1개당 읽는 전문가 데이터16 × 92 = 25.8GB
측정 하드웨어M1 Max · 10코어 CPU · 32코어 GPU · 64GB · 내장 NVMe

핵심 관찰은 단순하다: MoE는 토큰 하나를 만들 때 자기 몸의 극히 일부만 쓴다. 그러면 전체를 메모리에 올릴 필요 없이, 그 일부만 그때그때 디스크에서 읽으면 된다 — 문제는 그 "일부"가 토큰마다 25.8GB라는 것.

02 두 가지 모드 — 디스크가 모델 저장소가 된다

메모리 계층이 VRAM→RAM에서 한 칸 더 내려가 RAM→SSD→HTTP까지 확장된다. 전문가 전체를 로컬 SSD에 두는 full 모드와, 215GB만 받고 나머지는 Hugging Face CDN에 HTTP 범위 요청(range request)으로 전문가 하나씩 가져와 캐시하는 stream 모드가 있다.

--full (권장)--stream
필요 디스크~1.7TB~215GB
다운로드5~10시간 (이어받기 가능)~30분
이후 속도14.6초/토큰 (중앙값)캐시 미스 시 ~3분+/토큰
추론 중 네트워크불필요상시 필요

차이의 원인은 하나다. 토큰당 25.8GB의 전문가 읽기가 로컬 NVMe에서는 약 4초, 네트워크 너머에서는 분 단위가 된다. "일단 215GB로 시작해서 나중에 나머지를 채우는" 점진 경로도 지원한다.

03 숫자 — 20분/토큰에서 14.6초/토큰까지

레포가 밝힌 최초 동작 버전과 현재 버전의 격차가 이 프로젝트의 본체다. 같은 M1 Max에서 측정된 유지보수자 기준값(6회 풀모델 실행 중앙값, 탐욕 디코딩·fp32 정밀도·전문가 전체 로컬)이다.

지표최초 동작 버전현재개선
프리필 / 첫 토큰 (5토큰 프롬프트)2,429초28.0초~87×
정상 디코드 (전문가 로컬)~20분/토큰14.6초/토큰~82×
디코드 (전문가 스트리밍)~20분/토큰~3분/토큰네트워크 바운드

82배를 만든 개별 최적화도 수치와 함께 공개돼 있다:

  • 병렬 pread + F_NOCACHE — 전문가 읽기를 토큰당 40초 → 4.3초로. OS 페이지캐시를 일부러 우회해서(25.8GB짜리 일회성 읽기가 캐시를 오염시키니까) 커널 복사 비용을 제거했다.
  • int8 스파인 + 커스텀 Metal 역양자화 커널 — 레이어 로딩 118ms → 21ms. 상주 가중치를 bf16 대신 int8로 저장하고 GPU에서 풀어 쓴다.
  • 패킹된 int8 출력 헤드 — 디코드 +17.3%, 헤드 저장 공간 4.7GB → 1.17GB.
  • 무손실 n-gram 추측 디코딩 — 초안이 수락되면 한 번의 forward로 토큰 2개. 거부돼도 상태를 비트 단위로 복원해 출력이 참조 시퀀스와 정확히 일치한다.
  • 완전 재현 가능한 실행 — 탐욕 디코딩 + 정확한 fp32 수치로, 같은 프롬프트는 매번 같은 토큰을 낸다. 벤치마크마다 토큰 오라클로 정답을 대조했다.

현재 병목도 정직하게 적혀 있다: 디코드 시간 14.6초 중 약 7.5초가 53GB int8 스파인을 매 토큰 다시 읽는 디스크 대역폭이다. 64GB 호스트에서는 스파인이 전문가 읽기용 페이지캐시와 공존할 수 없어서 매번 재독이 불가피하다 — RAM이 더 크면 이 비용이 통째로 사라진다.

04 가장 값진 데이터 — 양자화는 I/O 레짐을 바꾼다

커뮤니티 기여자가 NVIDIA DGX Spark(128GB 통합 메모리)에서 보고한 4개 구성 비교(PR #2, 동일 출력 확인)가 이 보고서에서 제일 가져갈 만한 대목이다.

구성총 시간연산프리로드 대기
bf16 스파인 + CPU865초299초504초
bf16 스파인 + CUDA858초160초676초
int8 스파인 + CPU649초327초2초
int8 스파인 + CUDA221초184초18초

스파인을 bf16(107GB)에서 int8(53GB)로 바꾸면 바이트가 절반이니 2배 빨라져야 할 것 같지만, 실제로는 end-to-end 4배가 나왔다. 이유: 107GB 스파인이 메모리를 다 먹으면 전문가 읽기용 페이지캐시가 사라져서 프리로드 대기가 수백 초로 폭발한다. 53GB로 줄이는 순간 캐시 헤드룸이 생기고 대기가 붕괴한다(504초 → 2초).

양자화의 이득이 산술 비용 절감이 아니라 메모리 레짐 전환에서 나온 것이다. "모델이 메모리에 들어가냐"를 이분법으로 볼 게 아니라, 가중치·캐시·버퍼가 한 메모리 풀을 두고 경쟁하는 시스템으로 봐야 한다는 얘기 — 12GB GPU에서 GGUF 양자화·CPU 오프로드 조합의 성패가 갈리는 이유도 정확히 이 메커니즘이다.

05 현실 확인 — 무엇에 쓸 수 있고 무엇에 못 쓰나

  • 챗봇 ✗. 중앙값 14.6초/토큰 = 분당 4.1토큰. K3는 추론(thinking) 모델이라 답 전에 생각부터 하는데, 그 생각도 분당 4토큰으로 흘러나온다. 짧은 답 하나에 몇십 분이다.
  • 에이전트 백엔드 ✗. OpenAI 호환 API 서버(/v1/chat/completions, 스트리밍 포함)가 있긴 하지만, 레포 스스로 "에이전트는 호기심 대상이지 워크플로우가 아니다"라고 못 박는다. 긴 시스템 프롬프트의 프리필 비용이 치명적이고, 동시 요청 1개 제한에 greedy 고정이다.
  • 연구·검증 도구 ✓. 완전 결정론적 실행이라 같은 프롬프트가 항상 같은 토큰을 낸다. 프런티어급 MoE의 라우터 선택을 로컬에서 트레이스로 뜰 수 있고(K3_TRACE), API 뒤에 숨은 모델을 비트 단위로 재현하며 뜯어볼 수 있다는 건 연구자에겐 실제 가치다.
  • 방향 제시 ✓. MoE 스파스성을 스토리지 계층까지 확장한 실증. "활성 파라미터만큼의 메모리 + 총 파라미터만큼의 SSD"라는 사이징 공식이 성립함을 보였다. SSD가 지금보다 2~3배 빨라지면(PCIe 6 시대) 이 접근의 속도 등급이 한 단계 올라간다.

06 결론

"돌아간다"와 "쓸 수 있다"는 다르다. Deltafin은 전자를 82배 최적화로 증명했고, 후자가 아니라는 것도 스스로 정직하게 문서화했다. 분당 4.1토큰은 어떤 실용 시나리오에도 못 들어간다.

그런데도 일독을 권하는 이유는, 이 레포가 로컬 LLM I/O 엔지니어링의 드문 교본이기 때문이다. 페이지캐시 우회(F_NOCACHE), 이중 버퍼 레이어 로딩, 무손실 추측 디코딩, 그리고 무엇보다 "양자화가 연산이 아니라 I/O 레짐을 바꾼다"는 DGX Spark 4배 데이터 — 전부 재현 가능한 수치와 함께 공개돼 있다. 초대형 MoE를 개인 하드웨어에서 만지는 시대의 물리 법칙이 어떻게 생겼는지, 이만큼 구체적으로 보여주는 자료는 흔치 않다.
