벡터DB 없는 RAG가
RAG 업계를 끝낸다?

X(@oliviscusAI, 2026-09-28)에서 이런 글이 돌고 있다. "RAG 업계 전체가 끝장날 판이다. 연구자들이 벡터DB, 임베딩, 청킹, 유사도 검색 없이 돌아가는 새 RAG를 만들었다. 이름은 PageIndex. FinanceBench 98.7%로 리더보드의 모든 벡터 RAG를 이겼다. 100% 무료 오픈소스." GitHub API, 벤치마크 원자료, 공개된 답안 파일을 직접 대조했다.

PageIndex는 진짜 있고, 긴 전문 문서를 다룰 때 벡터 검색의 약점을 정면으로 겨냥한 좋은 설계다. 하지만 게시물이 내세운 숫자와 표현은 대부분 맥락이 빠졌다. 98.7%는 이 오픈소스가 아니라 같은 회사의 상용 금융 제품 점수다. 채점도 "정답을 포함하면 정답"으로 처리하는 관대한 LLM 채점에 사람이 보정한 결과다. "업계 종말"은 적용 범위를 무시한 과장이다.

"연구자들이 새 접근법을 개발했다"는 문장은 두 가지가 틀렸다. 만든 주체는 Vectify AI라는 회사고, 공개된 지 1년 반이 됐다. 최근 화제가 된 계기는 2026년 8월 SDK에 추가된 로컬 모드(pip install pageindex로 내 PC에서 색인·검색)로 보인다. 이건 평가지, 확인된 사실이 아니다.

2. 어떻게 동작하나 — 이 부분은 주장대로다

일반 RAG는 문서를 잘게 쪼개(청킹) 벡터로 바꾸고(임베딩), 질문과 비슷한 조각을 찾는다(유사도 검색). PageIndex는 다른 방식을 쓴다.

  • 색인: 문서의 목차 구조를 뽑아 장·절·항 형태의 트리를 만든다. README에 따르면 트리 구조 자체는 LLM 없이 레이아웃에서 추출하고, 싼 모델이 각 노드를 요약한다.
  • 검색: 질문을 받으면 LLM이 트리를 위에서부터 읽어 내려가며 "이 질문의 답은 어느 절에 있을까"를 추론해 해당 노드만 연다. 사람이 두꺼운 보고서에서 목차를 보고 찾아가는 방식과 같다.
  • 장점: "비슷한 문장"이 아니라 "관련 있는 위치"를 찾는다. 재무제표처럼 비슷한 표현이 수십 번 반복되는 문서에서 벡터 검색이 엉뚱한 연도·항목을 집어오는 문제를 피한다. 어느 절을 읽었는지 경로가 남아서 근거 추적도 쉽다.

벡터DB, 임베딩, 청킹, 유사도 검색이 없다는 네 줄은 전부 사실이다.

3. 98.7%의 정체

게시물의 핵심 숫자다. 출처를 따라가면 PageIndex README가 링크한 VectifyAI/Mafin2.5-FinanceBench 레포가 나온다.

확인 항목원자료 내용판정

직접 검산해봤다

Vectify가 답안 원문(result_gpt4o.json)을 공개해둔 덕에 일부는 확인할 수 있다. 150문항 중 정답이 짧은 숫자인 54문항을 골라, 정답 숫자가 Mafin 답변 안에 실제로 들어 있는지 기계적으로 대조했다.

결과: 54문항 중 51개는 숫자가 그대로 일치했다. 나머지 3개 중 1개는 표기 차이($400,000,000 vs "$0.4 billion"), 1개는 반올림 차이(7.9% vs 7.8%)라 사실상 정답이다. 명확히 다른 건 1개(Pfizer 분할 비용, 정답 77.78 vs 답변 70)였다. 숫자형 문항에서는 98% 안팎이 실제로 맞는다.

즉 98.7%라는 숫자 자체는 조작이 아니다. 문제는 그 숫자가 가리키는 대상이다. 튜닝된 상용 제품이 150문항에서 받은 점수를, 무료 오픈소스를 설치하면 얻는 성능처럼 옮겨 적었다.

4. "모든 벡터 RAG를 이겼다"의 기준선

PageIndex README 그래프는 "PageIndex 98.7% vs 벡터 RAG 50%"로 그려져 있다. 그런데 공식 FinanceBench 리더보드라는 건 없다. 벡터 RAG 쪽 수치는 2023년 11월 FinanceBench 논문의 실험에서 나왔다. 논문 초록에는 "GPT-4-Turbo에 검색 시스템을 붙였더니 81%를 틀리거나 답을 거부했다"고 적혀 있다.

  • 비교가 불공정하다. 2023년 GPT-4-Turbo + 기본 벡터 검색과 2025년 GPT-4o + 튜닝된 상용 파이프라인을 붙여놨다. 모델 세대 차이와 파이프라인 튜닝 효과가 "벡터 vs 트리" 차이와 섞여 있다.
  • Mafin 레포의 경쟁 비교표도 상대가 Quantly·Fintool·Perplexity 같은 상용 서비스다. 같은 모델, 같은 조건에서 벡터 RAG와 1:1로 붙인 대조 실험은 없다.

공정하게 말하면 이렇다. PageIndex 쪽에는 오픈소스 버전으로 측정한 별도 벤치마크(PageIndex-OSS-Benchmark)도 있다. 34개 PDF, 62문항에서 gpt-5.6-luna는 85.5~96.8%, gpt-5.6-sol은 96.8~100%가 나왔다. 오픈소스 자체도 성능이 좋다는 근거다. 다만 역시 벤더 측정이고, 벡터 RAG 비교군은 없다.

5. "100% 무료"와 "업계 종말"

주장실제판정
"100% 무료"코드는 MIT 무료. 하지만 색인과 검색에 LLM API가 필요하다. README 실측으로 색인 약 $0.001/페이지, 질문당 $0.003(luna)~$0.08(sol). OCR·MCP 서버·대규모 파일시스템 기능은 PageIndex Cloud(별도 API 키) 전용코드만 무료
"RAG 업계 끝"긴 전문 문서 몇 개를 정밀하게 묻는 작업에 강하다. 대신 질문마다 LLM이 트리를 추론해서 벡터 검색보다 느리고 비싸다. 수백만 문서에서 빠르게 찾는 용도는 Vectify도 별도 클라우드 레이어로 풀고 있다과장(평가)

README도 스스로 적용 대상을 "재무 보고서, 법률 문서, 규제 공시, 기술 매뉴얼, 의학 문헌, 교과서 같은 길고 복잡한 전문 문서"로 한정한다. 벡터 RAG를 대체한다기보다 긴 문서 정밀 QA라는 한 영역에서 더 나은 선택지가 생긴 것이다.

결론 — 쓸까?

쓸 만하다. 계약서, 공시, 매뉴얼처럼 목차가 있는 긴 문서를 다루는데 벡터 검색이 자꾸 엉뚱한 조각을 가져온다면 PageIndex는 시험해볼 가치가 충분하다. 로컬 모드라 문서가 밖으로 안 나가는 것도 장점이다(LLM API로 보내는 부분은 제외). 반대로 짧은 문서가 대량으로 쌓인 사내 위키나 고객 문의 검색이라면, 벡터 검색의 속도와 비용 이점이 여전히 크다.

게시물에서 가져갈 건 "PageIndex라는 좋은 도구가 있다"까지다. "98.7%", "업계 종말", "완전 무료"는 각각 "상용 제품이 150문항에서", "특정 문서 유형에서", "코드는"을 붙여야 참이 된다.
