Model practice note · Fine-tuning vs RAG

작은 LLM 파인튜닝,
진짜 실용적인가?

X에서 “1.5B 모델을 200~500개 좋은 예제로 파인튜닝하면 일반적인 프롬프트를 쓴 프런티어 모델보다 특정 업무에서 더 낫다”는 가이드를 봤다. 핵심 방향은 타당하지만, 모든 문제에 파인튜닝을 권하는 글로 읽으면 위험하다.

판정: 기술 방향은 타당, 성능 우위 주장은 조건부
✓ QLoRA·LoRA로 작은 모델을 특정 업무에 맞추는 건 검증된 방식✓ 200~500개는 실험 시작점으로 현실적△ “프런티어 모델보다 낫다”는 task·데이터·평가셋에 종속✗ 최신 사실·검색·정확한 수치 기억은 파인튜닝으로 해결하지 않음

1. 원문의 핵심 주장

가이드의 실전 순서는 작게 시작해 데이터를 정리하고, QLoRA로 어댑터를 학습한 뒤, 프롬프트만 쓴 기준선과 고립된 테스트셋을 비교하라는 것이다. 예시 모델은 Qwen2.5-1.5B-Instruct이고, Google Colab의 T4에서 첫 실험을 하도록 안내한다.

중요한 메시지는 “파인튜닝이 모델을 전반적으로 더 똑똑하게 만든다”가 아니라, 하나의 좁은 업무를 더 일관되게 만든다는 쪽이다.

2. 기술적으로 맞는 부분

QLoRA기본 모델을 4비트로 로드하고 원본 가중치는 고정한 채 LoRA 어댑터만 학습해 메모리를 줄인다.
데이터 품질 500개의 형식적인 예제보다 실패 패턴을 반영한 200개의 검토된 예제가 낫다.
분리 평가 같은 회사·문서가 train과 validation에 섞이면 암기한 것을 일반화로 착각한다.
운영 분리 학습 GPU와 API gateway·인증·rate limit·관측 계층을 같은 머신에 몰지 않는다.

3. 파인튜닝과 RAG를 구분해야 한다

문제우선 검토할 방법이유
말투·출력 형식·도메인 용어를 일관되게 만들기Prompt → 예제 → LoRA/QLoRA반복 가능한 행동 패턴을 학습시키는 문제
최신 시장 규모·규정·사내 문서 반영RAG / tool calling지식은 계속 바뀌므로 검색과 출처가 필요
정확한 숫자·금융 데이터 보존구조화 DB + 검증 코드모델 가중치에 숫자를 저장하는 방식은 신뢰하기 어렵다

4. 실제 도입 순서

  1. prompt-only baseline을 고정하고 실패 유형을 분류한다.
  2. 원천 데이터의 사용권·개인정보·기밀성을 확인하고, 승인된 URL만 재현 가능하게 수집한다.
  3. 회사 단위로 train/validation/test를 분리한다. 테스트셋을 본 순간 그 셋은 더 이상 순수한 테스트가 아니다.
  4. 소형 base model + QLoRA로 짧은 실험을 한다. loss가 낮아지는 것보다 미사용 데이터의 업무 성공률이 중요하다.
  5. 출력 품질·unsupported claim·숫자 보존·latency·token cost를 기준선과 비교한다.
  6. 배포한다면 HTTPS·인증·rate limit·queue·GPU server를 분리하고, adapter version과 rollback 경로를 기록한다.

5. 이 가이드에서 빠지기 쉬운 리스크

  • 200~500개는 법칙이 아니다. 데이터 다양성·난이도·라벨 품질에 따라 필요한 양이 크게 달라진다.
  • 벤치마크 착시. 같은 기업 문서가 학습과 평가에 섞이면 수치가 부풀려진다.
  • Colab은 실험용. 무료 런타임은 idle timeout과 최대 수명이 있고, 체크포인트를 외부 저장소에 자주 저장해야 한다.
  • 개인정보 재학습 금지. 명시적 동의·마스킹·데이터셋 버전·삭제 정책 없이 사용자 요청을 자동으로 학습 데이터로 모으면 안 된다.

결론

작은 모델을 좁은 업무에 맞춰 일관되게 만드는 전략은 충분히 가능하다. 다만 “작은 모델이 프런티어를 이긴다”가 아니라, 범위를 좁히고 데이터·평가·운영을 통제하면 비용과 지연을 크게 낮출 수 있다가 정확한 결론이다. 현재 정보가 필요하면 RAG, 행동 패턴이 반복되는데 프롬프트만으로 불안정하면 QLoRA를 검토한다.
