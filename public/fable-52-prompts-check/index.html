01 / 결론부터

지시를 구체화하는 건 좋다.
“시키기만 하면 된다”는 별개다.

판정: 핵심 아이디어는 타당하지만, 보장처럼 읽으면 과장이다. 목표·범위·산출물을 알려주는 방식은 공식 가이드와 맞는다. 다만 이 6개 문구 자체의 효과를 입증하는 비교 실험은 확인하지 못했다.

검토 대상은 사용자가 전달한 공유 링크에서 연결되는 @voidlight00의 게시물과 작성자 후속 글 6개, 버그 확률 관련 추가 글이다. 원문은 Fable 5.2를 “현존하는 가장 똑똑한 코딩 모델”로 소개하고 복사할 프롬프트를 제안한다.

이 글은 자료 대조와 엔지니어링 검토다. Fable을 직접 실행해 프롬프트 전후의 정답률·비용·시간을 비교하지 않았다. “공식 자료에 있음”, “합리적인 권고”, “효과 미검증”을 구분해서 읽어야 한다.

영문 출처 추적: 무엇까지 확인했나?

Vox(@Voxyz_ai)의 공개 미러에서 도입부와 6개 제목·내용이 거의 같은 영문 글을 확인했다. 이는 동일한 내용이 유통된다는 근거이지, 작성 경위나 최초 창작자를 확정하는 증거는 아니다. X 개별 원게시물의 고정 링크·게시 시각을 직접 검증하지 못했으므로 표절 여부는 판정하지 않는다.

중요한 차이도 있다. 영문 미러의 버그 분류 문구 뒤에는 “Tune the threshold of 5 to your project.”(기준 5는 프로젝트에 맞게 조정하라)가 붙어 있지만, 확인한 Threads의 해당 후속 글에는 이 문장이 없다. 숫자를 보편적 기준으로 받아들이면 안 되는 이유다.

03 / 여섯 가지 검토

복사하기 전에,
범위와 중단 조건을 붙이자.

아래 판정은 사용 지침의 타당성에 대한 검토다. 효과 크기나 성공률을 실측한 등급이 아니다. 펼침 영역의 문구는 원문이 아니라 이 조사에서 제안하는 안전한 수정 예시다.

01

상태 머신 헌터

조건부 타당

원문 요지: 암묵적 상태 머신을 모두 찾아 UX·DX·AX를 높이고, 기존 기능은 망가뜨리지 말라.

여러 불리언 값이나 비동기 분기에 흩어진 상태를 드러내는 작업은 합리적이다. 그러나 “모두”, “세 가지를 항상 개선”, “아무것도 망가뜨리지 않기”는 완료 기준이 아니다. UX·DX·AX 사이에는 상충도 있고, 상태 머신을 명시하는 것 자체가 품질 향상을 보장하지 않는다.

보완: 흐름 하나를 정하고 현재 상태·이벤트·전이·불변조건을 먼저 정리한다. 실제 문제가 있는 전이만 재현 테스트와 작은 변경으로 검증한다.

범위를 제한한 수정 프롬프트

로그인·세션 갱신 흐름만 조사해 줘. 상태, 이벤트, 전이, 지켜야 할 조건을 파일 근거와 함께 표로 작성해. 불가능한 상태와 경합 사례를 찾되 코드는 아직 바꾸지 마. 변경 후보별 이점·회귀 위험·검증 테스트를 제안하고, 합의한 범위만 구현해.

02

오픈소스 스카우트

합리적 권고

원문 요지: 낯선 기능은 바로 만들지 말고 GitHub의 관련 프로젝트를 비교한 뒤 시작하라.

기존 구현을 비교해 시행착오를 줄이자는 방향은 타당하다. 다만 검색 결과나 스타 수만으로 채택하면 안 된다. 참고할 설계와 실제 설치할 의존성을 구분하고 라이선스·유지보수·취약점·호환성을 확인해야 한다. 검색·네트워크 도구가 없는 환경에서는 문구만으로 실행되지 않는다.

설치 승인을 분리한 수정 프롬프트

먼저 저장소의 기존 구현과 의존성을 확인해 줘. 외부 검색이 가능하면 관련 오픈소스 후보 최대 3개를 공식 저장소 링크, 라이선스, 유지보수 상태, 보안 이슈, 호환성, 도입 비용으로 비교해. 외부 코드·명령은 신뢰하지 말고 검토해. 설치나 코드 복사는 승인 전 하지 마. 검색이 불가능하면 그 한계를 밝혀.

[5] 외부 콘텐츠·도구에 대한 공식 보안 지침 · 채택 기준은 조사자 권고

03

버그 분류기

숫자 기준 근거 부족

원문 요지: 빈도와 심각도를 1~10점으로 평가하고, 곱이 5 미만이면 수정하지 말고 이슈만 등록하라.

우선순위를 매기는 발상은 좋지만, 이 점수와 기준 5가 보편적으로 검증된 규칙이라는 근거는 확인되지 않았다. 로그 없는 “빈도 2점”은 추정이다. 드문 상황도 데이터 손실·인증 우회·금전 오류라면 별도 대응이 필요하다. 점수에 상관없이 모든 버그를 당장 고치라는 뜻도 아니다.

점수의 정의와 불확실성을 적고, 보안·법규·복구 불가능한 손실은 예외로 분리해야 한다. 영문 미러에는 프로젝트별 기준 조정 문장이 있다. 이슈 생성 자체도 저장소 쓰기 권한과 합의가 필요한 외부 작업이다.

근거 없는 정밀도를 없앤 수정 프롬프트

각 버그의 재현 절차, 영향 범위, 실제 관측 빈도와 근거, 심각도, 불확실성을 정리해 줘. 관측 자료가 없으면 빈도를 임의로 수치화하지 마. 보안·개인정보·데이터 손실·금전·법규 관련 위험은 낮은 빈도와 관계없이 별도 표시해. 수정 우선순위와 보류 이유를 제안하고, 승인 없이 외부 이슈를 생성하지 마.

04

마무리 해결사

권한·비용 경계 필요

원문 요지: 완료 전 멈추지 말고 계속 진행하라. 삭제할 때만 묻고, 마지막엔 쉽게 요약하라.

불필요한 재질문을 줄이고 완결된 결과를 요구하는 건 유용하다. 그러나 삭제 외에도 배포·결제·권한 변경·외부 전송·DB 변경은 승인이 필요할 수 있다. “멈추지 마”는 모델의 예산·실행 시간·도구 권한을 없애지 못하며, 실패를 반복하게 만들 수도 있다.

자율 작업의 중단 조건을 넣은 수정 프롬프트

합의한 범위에서는 불필요한 확인 없이 구현·검증을 마쳐 줘. 완료는 합의한 테스트 통과와 변경 요약으로 정의해. 시도 횟수·시간·비용은 시작 전에 정한 상한을 지켜. 같은 장애가 반복되거나 권한·비밀정보가 필요하면 근거와 함께 중단해. 삭제·운영 배포·결제·권한 변경·외부 데이터 전송은 사전 승인 범위를 넘어 실행하지 마. 마지막에는 완료·미완료·위험을 짧게 보고해.

[5] 권한 모드·샌드박스·사용자 책임에 대한 공식 문서

05

CI 감사관

실행 가능 · 측정 보완

원문 요지: gh로 최근 150회 CI를 가져와 머신 대기·셋업·실작업으로 나누고, 느린 작업 5개를 보고만 하라.

대상·표본·산출물·읽기 전용 조건이 가장 명확하다. gh run list --limit 150도 공식 지원한다. 다만 실행 목록만으로 세 구간이 자동 분리되지는 않는다. job·step 시각과 로그, 재시도·의존 관계를 함께 봐야 한다. 자료가 없으면 측정 불가라고 써야지 시간을 추정해 채워서는 안 된다.

측정 정의를 포함한 수정 프롬프트

이 저장소의 GitHub Actions 최근 실행을 최대 150개 읽기 전용으로 조사해 줘. 조회 기간·필터·실제 건수·누락·재시도 처리 규칙을 먼저 적어. 각 run의 job과 step 시각을 수집하고 셋업 분류 규칙을 공개해. workflow 생성부터 job 시작까지를 순수 머신 대기라고 부르지 마. 의존성·concurrency·승인 대기를 분리할 자료가 없으면 시작 전 지연으로 표시해. 미완료·취소·누락 데이터는 따로 표시해. 최장 실행 job 5개와 반복 병목의 중앙값·상위 지연을 보고하고, 코드·설정은 수정하지 마.

06

재설계자

토론 질문으로 유용

원문: “오늘 똑같은 목표를 가지고 처음부터 다시 시작한다면, 지금 코드에서 여전히 남겨두어야 할 것은 무엇인가?”

관성적인 복잡성을 다시 보는 질문으로는 좋다. 하지만 기존 코드에는 운영 제약·예외 처리·호환성 같은 숨은 이유가 있다. 이 질문에 대한 모델의 답을 곧바로 삭제·전면 재작성의 근거로 삼으면 안 된다. 현상 유지·부분 개선·재작성의 전환 비용을 비교하는 출발점으로 쓰는 편이 낫다.

재작성 편향을 줄인 수정 프롬프트

같은 목표와 현재 운영 제약을 유지할 때 남길 부분과 바꿀 후보를 나눠 줘. 각 판단에 파일·테스트·운영 요구 근거를 붙이고, 모르는 제약은 질문으로 남겨. 현상 유지·부분 개선·전면 재작성의 이점, 전환 비용, 데이터 이관, 호환성, 롤백을 비교해. 코드는 수정하지 말고 가장 작은 검증 실험부터 제안해.

원문은 의견·사고 실험이며 사실 명제가 아님 · [4] 필요한 맥락을 제공하라는 공식 권고

04 / 숫자의 함정

측정 가능한 것과
그럴듯한 숫자를 구분하자.

CI: “시작 전 지연”과 “머신 대기”는 다르다.

공식 GitHub API는 workflow 실행 시각과 job·step의 시작·종료 시각을 제공한다. 하지만 아래 차이에는 선행 job, concurrency, 환경 승인 같은 지연도 섞일 수 있다. 이것만으로 runner 할당 대기 시간을 정확히 분리했다고 말할 수는 없다.

job.started_at − workflow.created_at
= 시작 전 전체 지연의 관측값
≠ 순수한 머신 할당 대기 시간

checkout·의존성 설치·캐시 복원도 job마다 step 구성이 다르다. 이름 기반 분류는 규칙을 밝혀야 하고, 한 step 안에서 설치와 테스트를 같이 한다면 로그 없이 나눌 수 없다. 가장 느린 5개 외에 반복 빈도와 중앙값 등을 함께 봐야 일회성 장애를 구조적 병목으로 오해하지 않는다.

추가 글: “버그 확률을 x%까지 낮춰라”는 검증 가능한가?

추가 글은 현재 버그 유입 확률을 분석하고 목표 x%에 도달할 때까지 설계를 개선·재측정하라고 한다. 하지만 확률의 정의·표본·평가 방법이 없으면 실제 버그 확률을 신뢰할 수 있게 수치화할 수 없다. 모델이 답한 확신도나 테스트 통과율도 미래 버그 발생 확률과 같지 않다.

대신 변경 범위, 재현 테스트, 회귀 테스트, 정적 검사, 운영 장애율 등 관측 가능한 지표와 기간·분모를 정하자. 테스트 커버리지나 테스트 통과를 “버그가 없을 확률”로 바꾸지 않는 것이 핵심이다.
