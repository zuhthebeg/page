Context Language Models

X(@thesupermannx, 2026-09-30)에서 이런 글이 돌고 있다. "메타가 Context Language Models를 오픈소스로 공개했다. LangChain, RAG, 오케스트레이션 하네스 없이 모델이 스스로 컨텍스트를 파일처럼 관리한다. 59% 적은 연산으로 모든 SOTA 컨텍스트 기법을 이겼다." 논문 원문(arXiv:2609.37725), 공식 코드 저장소, 실제 프롬프트 파일을 직접 대조했다.

이 연구가 실제로 보여준 건 이렇다. 자동 요약 압축(Codex 스타일)을 쓰는 대신, 에이전트에게 "네 대화 기록이 이 파일에 있으니 필요 없는 부분은 직접 고쳐라"라고 맡기면 같은 모델로 더 잘하고 더 싸게 끝나는 경우가 많다. 의미 있는 결과다. 다만 새 모델이 나온 게 아니고, 하네스가 사라진 것도 아니며, "모든 SOTA를 59% 적은 연산으로"는 서로 다른 벤치마크의 숫자를 섞은 문장이다.

2. "하네스 없이"가 틀린 이유 — 실제 동작

이름이 "Language Model"이라 새 모델처럼 들리지만, 논문의 주요 결과는 기존 모델(Qwen3.6-27B, Claude 4.6 Sonnet, GPT-5.6 Sol)을 그대로 쓴 것이다. 바뀐 건 하네스 안의 규칙이다.

  • 기존 방식: 하네스가 정한 규칙대로 기록을 줄인다. 예를 들어 길이가 일정 수준을 넘으면 앞부분을 요약해서 갈아끼운다(Codex 스타일 요약). 최근 연구들은 "언제 요약할지"나 "무엇을 빼둘지" 같은 정해진 도구를 모델에게 준다.
  • CLM: 대화 기록 전체를 파일 하나로 비춰두고, 모델이 그 파일을 마음대로 고치게 한다. 다음 요청은 고쳐진 파일 내용으로 나간다. 요약할지, 지울지, 메모를 남길지, 그대로 둘지는 모델이 정한다.

저장소의 실제 시스템 프롬프트(clm/clm_harness/clm_agent/prompts.yaml)를 보면 구조가 그대로 드러난다.

Your conversation is mirrored to /tmp/.live_ctx/LIVE_CTX_MAIN.txt
(refreshed before every command). Free up context by editing that file —
replace stale regions (big outputs, dead ends, superseded notes) with a
concise, specific summary.

즉 Mini-SWE-Agent 계열 하네스와 Harbor 실행 환경 위에서, "기록 파일을 bash로 고쳐라"라는 지시와 편집 규칙을 준 것이다. 하네스는 그대로 있고 하네스가 하던 압축 결정을 모델에게 넘긴 것이 핵심이다. LangChain이나 RAG와는 애초에 다루는 문제가 다르다(RAG는 외부 지식 검색, CLM은 작업 중 쌓이는 대화 기록 관리).

3. 숫자 검증 — 숫자는 맞다, 문장이 섞였다

트윗과 초록에 나온 숫자를 논문 본문 수치로 다시 계산했다.

숫자 6개는 모두 본문 수치로 재계산된다. 문제는 트윗이 이 숫자들을 섞어서 "모든 SOTA를 59% 적은 연산으로 이겼다"고 쓴 것이다. 59%는 EdgeBench에서 점수를 5% 올렸을 때의 수치다. 논문 본문에서 TerminalBench 2.1은 "최강 기준선과 같은 점수를 70% 연산으로"이고, 이겼다고 하지 않는다. 비교 대상도 업계 전체가 아니라 논문이 고른 기준선 5~6개다.

"47.6% 폭등"의 실제 의미

트윗이 가장 크게 내세운 숫자인데, 논문을 보면 해석이 다르다.

  • 학습 전 9B 모델은 CLM 방식이 오히려 요약 방식보다 6점 낮았다(28.8% vs 34.7%). 작은 모델은 기록을 언제 어떻게 고칠지 잘 판단하지 못했기 때문이다. 논문도 그렇게 설명한다.
  • 같은 RL로 학습시킨 요약 방식도 34.7% → 42.1%로 올랐다. 학습 후 차이는 0.4점이다.
  • 진짜 성과는 정확도가 아니라 비슷한 정확도를 38.8% 적은 연산으로 낸다는 점이다.

Suffix Cache Reuse — 조건부 사실

모델이 대화 중간을 고치면 일반 서빙 엔진은 고친 지점 뒤를 전부 다시 계산한다(KV 캐시 재사용은 앞부분이 똑같을 때만 된다). 그래서 저자들은 고친 지점 뒤쪽 캐시도 재사용하는 SGLang 패치를 만들었다. BrowseComp-Plus에서 표준 SGLang 대비 65% 연산으로 같은 정확도를 냈다(35% 절감). 서버를 직접 운영해야 쓸 수 있는 최적화이고, API로 모델을 쓰는 사용자에게는 해당이 없다.

5. 우리한테 의미 있나 — Claude Code·Codex·OpenClaw 사용자 관점

이 논문에서 가장 실용적인 대목은 비교 대상이다. 논문이 계속 이긴 "가장 강한 기준선"은 Codex 스타일 요약, 즉 기록이 길어지면 앞부분을 요약해서 갈아끼우는 방식이다. Claude Code, Codex, OpenClaw의 자동 압축도 큰 틀에서 이 계열이다(평가). 그러니 이 결과는 "우리가 매일 쓰는 압축 방식보다 모델에게 맡기는 게 나은 경우가 많다"는 뜻으로 읽을 수 있다.

  • 지금 써보려면: Pi 에이전트라면 pi install npm:@lolipopshock/pi-clm으로 바로 된다(MIT). Claude Code와 OpenClaw에는 모델이 자기 대화 기록 파일을 직접 고치는 경로가 기본으로 없다. 붙이려면 하네스를 고쳐야 한다(평가).
  • 모델 크기가 중요하다: 논문 부록을 보면 9B 모델은 TerminalBench 2.1에서 과제 절반에서 기록을 한 번도 고치지 않았다. 27B 모델은 과제당 평균 2.6번 고쳤다. 작은 로컬 모델에 그대로 적용하면 오히려 손해일 수 있다.
  • 회사에서 쓰려면: 코드는 비상업 라이선스다. 회사 서비스에 그대로 가져다 쓸 수 없다. 아이디어 자체(기록 파일 + 편집 지시)는 단순해서 직접 구현할 수 있지만, 이건 라이선스 판단이 아니라 기술적 평가다.
  • 보안: 논문도 직접 경고한다. 모델이 자기 컨텍스트를 고칠 수 있으면 프롬프트 인젝션이나 모델이 스스로 만든 지시가 턴을 넘어 살아남는 통로가 된다. 압축 요약에 모델이 승인되지 않은 지시를 끼워 넣은 사례도 인용했다. LLM 게이트웨이나 감사 로그를 운영한다면, 모델이 고친 기록과 원본 기록을 따로 보관해야 한다.

결론

좋은 연구다. 저자진이 탄탄하고, 코드와 프롬프트가 공개돼 있고, 본문 숫자는 서로 앞뒤가 맞는다. "자동 요약 압축보다 모델에게 기록 편집을 맡기는 게 낫다"는 주장은 여러 벤치마크에서 일관되게 나왔다.

게시물에서 가져갈 건 "대화 기록 관리를 하네스 규칙에서 모델 판단으로 넘기는 방식이 실제로 효과가 있다"까지다. "하네스 없이"는 "하네스의 압축 규칙 대신"으로, "59% 적은 연산으로 모든 SOTA"는 "고른 기준선 대비, 벤치마크에 따라 21~59% 적은 연산으로 대부분 이기거나 비김"으로, "메타가 오픈소스로"는 "워싱턴대·메타 공동 연구, 비상업 코드 공개"로 고쳐야 참이 된다.
