01 이미 갖춘 것 — 생각보다 단단한 골격

Travly의 어시스턴트는 단순 챗봇이 아니다. migrations/0018의 assistant_action_proposals 테이블과 API 구성을 보면 plan-then-execute + HITL 워크플로가 이미 돌아간다:

  • 파이프라인이 있다. chat(의도) → parse-plan/generate-draft(계획) → verify-places(검증) → preview → execute(승인 후 실행) → cancel. 학습노트의 Intent→Plan→Verify 루프 형태 그대로.
  • 확인 우선(confirm-first) 승인 게이트. 제안은 pending으로 저장되고 사용자가 확인해야 실행 — 비가역 작업에 사람을 끼우는 HITL이 코드에 박혀 있다(학습노트 04의 핵심).
  • 상태머신. pending→running→completed/failed/cancelled/expired — 노트 3단계 로드맵이 요구하는 잡 생애주기를 이미 구현.
  • 계획이 데이터다. actions_json로 구조화 산출, summary_json로 요약, classifyExecutionMode로 immediate/background 분기.
  • 제안 만료(expires_at)와 결과 기록(results_json/error_text) — 위생과 감사의 씨앗.
  • 모델 라우팅. _common.ts에 primary/fallback·모델별 타임아웃·5분 캐시·alias 정규화. 라우팅 패턴이 살아 있다.

즉 "에이전트 안 쓰고 워크플로로 풀 수 있으면 그렇게 하라"는 노트 원칙을 (의도했든 아니든) 잘 따르고 있다. 자율 루프가 아니라 고정 흐름 + 승인이라 감사·예측 가능성이 높다.

03 가장 아픈 갭 — 기억이 없다

어시스턴트는 사실상 요청마다 백지에서 시작한다. chat은 클라이언트가 넘긴 history·현재 위치·시각만 받는다. 사용자가 누구인지, 지난 여행에서 무엇을 좋아했는지, 동행이 누구인지를 저장·검색하지 않는다.

여행은 user-memory의 가치가 가장 큰 도메인이다. "대만인 배우자가 있음"(Semantic), "지난달 오사카에서 라멘집을 별 5개 줬음"(Episodic) 같은 사실이 다음 추천 품질을 좌우한다. 지금 Travly는 이걸 전부 버리고 있다 — 제품 차별화와 에이전트 성숙도가 동시에 걸린 1순위.

04 우선순위별 개선안

  1. 메모리 레이어 (최우선). D1에 user_facts(Semantic) 테이블 + 과거 일정·리뷰를 Episodic으로 인덱싱(pgvector 없으니 D1 + 임베딩 검색, 또는 우리 로컬 임베딩 활용)해 chat에 주입. 쓰기 정책은 "다음에 또 쓸 사실인가" 하나로 시작. 망각·정정 경로도 같이.
  2. 멱등성 + 보상. execute에 멱등키와 상태 전이 가드(pending→running 원자적 UPDATE), 부분 실패 시 롤백/보상. 내부 HTTP self-call을 직접 함수 호출 + D1 트랜잭션으로 교체.
  3. 예산·서킷브레이커 + 감사. 스텝/시간/토큰 예산과 초과 시 중단. results_json을 who/what/why 감사 로그로 확장 — 백엔드+SRE 출신의 차별화 포인트(노트 04).
  4. 계획에 성공 조건. actions_json 각 액션에 검증 조건 필드를 넣고, verify-places를 일반 검증자로 확장 — "실행자 말고 검증자가 채점".
  5. 시크릿 정리. _common.ts에 LLM API 키가 평문 상수로 하드코딩돼 있다. 서버사이드(Pages Function)라 브라우저 노출은 아니지만, 소스·git에 박힌 키는 즉시 env 바인딩(시크릿)으로 빼고 로테이션.
  6. 비용 경로. primary가 gpt-5.4-mini = OpenAI 과금 경로다. 단순 작업(파싱·요약)은 이미 슬롯 잡아둔 로컬 Gemma나 구독 경로로 오프로드 — 로컬 LLM 보고서의 결론과 직결.

05 제언 — Travly를 PoC로 다시 보라

학습노트 4단계(채팅→멀티스텝→승인 게이트→메모리)를 Travly에 겹쳐 보면, Travly는 이미 3.5단계까지 와 있다 — 채팅·멀티스텝·승인 게이트가 다 있고, 빠진 건 메모리 한 칸이다.

  • 즉 "휴가 신청 + 팀 공지" 같은 가상 PoC를 새로 짤 필요가 없다. 실제 사용자·실제 비가역 작업(일정 생성)·실제 승인 흐름이 도는 Travly가 더 좋은 PoC다.
  • 여기에 메모리 + 멱등 실행 + 감사를 얹는 작업이 곧 노트 2~3단계(직접 구현·Runtime 설계)의 산출물이 된다. "운영하며 겪은 실패와 수정"이라는 차별화 케이스가 공짜로 쌓인다(노트 07).
  • 주의(노트 07의 약점 보완): 빠른 실행보다 요구사항/계약(스텝 입출력 스키마·실패 정책)을 먼저 고정하는 연습을 Travly 리팩터에서 의도적으로 할 것.

06 진단의 한계

  • 점수는 학습노트 프레임에 비춘 내 주관 평가다. 절대 등급이 아니라 "어디를 다음에 손볼지"를 가리키는 나침반으로 쓸 것.
  • 실행 경로(execute) 일부는 헤더만 보고 판단했다 — 멱등성·트랜잭션은 실제 동작 테스트로 재확인 권장(과부하 더블클릭·중복 실행 시나리오).
  • 이 진단은 어시스턴트(에이전트) 축만 본 것이다. Travly의 UX·성장지표·수익화는 별도 평가가 필요하다.
