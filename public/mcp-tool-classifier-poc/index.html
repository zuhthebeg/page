LLM 게이트웨이의 MCP 도구,
서버 식별과 카테고리 분류 PoC

사용자에게 LLM API를 제공하는 게이트웨이가, Codex·Claude Code 같은 클라이언트의 요청에 실려 오는 도구 스펙을 수집해 MCP 서버·함수·파라미터 단위로 Redis에 저장하고, 두 환경에서 화이트·블랙리스트를 운영하는 구조를 가정한다. 서버를 식별하지 못한 도구 수백 개가 custom으로 몰리고, 카테고리가 자주 틀리는 문제를 GPU 없이 CPU만으로 줄이는 것이 목표다. 오른쪽 아래 버튼으로 이 문서 전체를 마크다운으로 복사해 사내 AI 에이전트에게 그대로 지시할 수 있다.

한 줄 요약
① 이름 파서를 클라이언트별 실제 규칙에 맞춘다 → ② 요청 단위 "도구 묶음" 정보를 수집에 추가한다 → ③ 별칭이 아니라 도구 세트 지문으로 서버를 정규화한다 → ④ 남은 카테고리 분류는 기존 화이트·블랙리스트 판정을 라벨로 학습한 CPU 분류기로 제안하고, 사람이 확정한다. 요청 경로에는 모델을 넣지 않는다.

0. 제약과 원칙

  • CPU 전용. GPU 없음. 모든 모델은 CPU 배치로 돌린다.
  • 데이터 반출 금지. 사내 MCP 스키마는 내부 정보다. 외부 LLM API로 보내지 않는다. 모델 가중치만 내려받아 사내에서 실행한다.
  • 요청 경로 불변. 실시간 요청 처리에는 "정규 ID 조회"만 넣는다. 분류는 주기 배치(예: 1시간)로 한다.
  • 자동 승인 금지. 모델은 제안만 한다. 쓰기·삭제·실행·외부전송 계열은 반드시 사람이 확정한다.
  • 기존 운영 무중단. 현재 Redis 키와 화이트·블랙리스트는 건드리지 않는다. PoC 결과는 별도 키 접두사(예: poc:)나 파일로만 낸다.

1. 왜 custom으로 빠지는가 — 클라이언트별 도구 이름 규칙

게이트웨이는 MCP 서버에 직접 연결되지 않는다. LLM 요청의 tools 배열에 들어 있는 모델에 보이는 이름만 본다. 이 이름은 클라이언트마다 다르게 만들어진다.

클라이언트규칙 (1차 출처 확인)파서가 틀리는 지점
Claude Codemcp__<server>__<tool> (공식 hooks 문서). <server>는 사용자가 자기 설정에 붙인 별칭같은 서버가 사용자마다 다른 별칭(jira / atlassian / my-jira)으로 들어와 서버가 여러 개로 쪼개짐
Codex (openai/codex, codex-mcp/src/tools.rs, mcp/mod.rs)구분자 __. mcp__ 접두사는 설정에 따라 붙거나 안 붙음(prefix_mcp_tool_names, 서버별 예외 목록). [a-zA-Z0-9_] 밖의 문자는 전부 _로 치환(brave-search → brave_search). 이름이 겹치거나 128바이트를 넘으면 _ + sha1 앞 12자리 해시를 붙이고 잘라냄① 접두사 없는 이름을 MCP로 인식 못 함 ② 해시 접미사(_a1b2c3d4e5f6)가 붙은 이름을 새 도구로 인식 ③ 잘린 이름 ④ -가 _로 바뀌어 다른 클라이언트와 서버명이 불일치
내장 도구Bash/Read/Edit/apply_patch/shell 등 클라이언트 자체 도구MCP가 아닌데 custom으로 섞임
스킬스킬은 보통 개별 도구가 아니라 "스킬 호출 도구"의 인자로 들어옴도구 분류 대상과 섞이지 않게 분리 필요

Codex 규칙은 2026-09-30 main 브랜치 소스 기준이다. 버전별로 다를 수 있으니 반드시 실제 Redis 샘플로 검증할 것. 스킬 표현 방식은 클라이언트·버전별로 샘플 확인 필요.

2. 단계별 작업 지시

Phase 0 — 현황 측정 (코드 변경 없음)

  1. Redis의 도구 수집 데이터를 읽기 전용으로 JSONL로 덤프한다. 한 줄 = 도구 1개: env, client, raw_name, parsed_server, parsed_tool, description, params_schema(JSON), first_seen, last_seen, count, list_status(white/black/none), category. 필드가 없으면 비워둔다.
  2. 다음을 집계해 표로 낸다: 전체 도구 수, custom 비율, 클라이언트별 이름 패턴 분포(mcp__*__* / *__* / 구분자 없음), 해시 접미사 패턴 _[0-9a-f]{12}$ 비율, 설명 언어(한국어 포함 비율).
  3. custom에 들어간 도구에서 무작위 100개를 골라 "왜 못 잡았는지"를 위 표의 원인으로 분류한다.

완료 조건: 원인별 건수 표. 이게 이후 우선순위를 정한다.

Phase 1 — 결정적 이름 파서 교체

  1. 클라이언트 식별(User-Agent 등) 후 클라이언트별 파서를 적용한다. mcp__ 유무 모두 처리, 해시 접미사 제거 후 원래 이름 보존(raw_name은 그대로 저장), -/_ 정규화한 비교용 키 생성.
  2. 내장 도구 목록을 클라이언트별로 두고 MCP 분류 대상에서 제외한다.
  3. 파서 단위 테스트: 위 표의 사례마다 최소 1개씩, Phase 0에서 뽑은 실패 사례 전부.

완료 조건: 같은 덤프로 다시 돌렸을 때 custom 비율 감소량을 수치로 보고.

Phase 2 — 수집에 "요청 단위 묶음" 추가 (최소 변경)

현재는 서버·함수·파라미터로 풀어서 개별 저장하므로 "이 도구들이 같은 요청에 같이 왔다"는 정보가 없다. 서버 식별의 핵심 신호라 이것만 추가한다. 사용자 프롬프트 등 대화 내용은 저장하지 않는다.

  1. 요청마다 파싱된 서버 네임스페이스별로 도구 이름을 정렬해 도구 세트 지문 = sha256(정렬된 도구명 목록)을 만든다.
  2. Redis에 추가: poc:fp:<지문> → 도구 이름 집합(SET), poc:alias:<env>:<별칭> → 지문별 관측 횟수(HASH). TTL은 운영 정책에 맞춤.
  3. 게이트웨이 지연시간 영향 측정(추가 p50/p99). 비동기 기록 권장.

완료 조건: 하루치 수집 후 지문 개수·별칭 개수 보고.

Phase 3 — 서버 정규화 (배치)

  1. 정규 서버 레지스트리를 만든다: canonical_server_id → {표시 이름, 대표 도구 이름 집합, 버전별 지문들}. 초기값은 현재 이름이 명확한 서버들로 채운다.
  2. 새 별칭·지문이 들어오면 레지스트리의 각 서버와 도구 이름 집합의 Jaccard 유사도를 계산한다. 유사도 ≥ 0.8이면 자동 매핑 제안, 0.5~0.8은 검토 큐, 미만은 신규 서버 후보. 임계값은 Phase 0 데이터로 조정한다.
  3. 기존 개별 저장 데이터(묶음 정보 없음)는 보조 신호로 묶는다: 정규화한 네임스페이스 문자열 유사도, 도구 이름 공통 접두사, 설명 임베딩 유사도로 custom 도구를 클러스터링해 "서버 후보"를 만든다.
  4. 사람은 후보마다 한 번만 이름을 붙인다. 이후 같은 지문은 어떤 별칭으로 와도 자동 매핑된다.
  5. 화이트·블랙리스트 키를 별칭이 아니라 canonical_server_id + 정규화 도구명으로 조회하는 매핑 테이블을 만든다. 두 환경 간 목록 이관도 이 ID로 한다.

완료 조건: custom 도구 수 → 서버 후보 수로 몇 배 줄었는지, 자동 매핑 제안의 사람 검수 정확도(샘플 100건).

Phase 4 — 카테고리 분류기 (CPU, 학습형)

  1. 분류 체계를 두 축으로 분리한다. 동작 축: read / write / delete / execute / external_send / admin. 도메인 축: 사내 기존 카테고리. 한 목록에 두 축이 섞여 있으면 사람 라벨도 흔들린다. 기존 카테고리를 두 축으로 재매핑하는 표를 먼저 만든다.
  2. 입력 텍스트 = 정규화 도구명 토큰(create_issue → create issue) + 정규 서버명 + 설명 + 파라미터 이름·타입·enum을 평탄화한 문자열.
  3. 라벨 = 기존 카테고리(custom 제외) + 화이트·블랙리스트 판정. 두 환경 라벨이 충돌하는 도구는 별도 목록으로 뽑아 사람이 정리한다.
  4. 모델 A (기준선): scikit-learn TF-IDF(단어 + 문자 3~5그램) + LogisticRegression(class_weight=balanced).
  5. 모델 B: intfloat/multilingual-e5-small 임베딩(한국어 포함, ONNX int8로 변환 가능) + LogisticRegression. 입력 앞에 "passage: " 접두사. 필요 시 BAAI/bge-m3와 비교(더 느림).
  6. 평가는 반드시 GroupKFold(그룹 = 정규 서버)로 한다. 같은 서버의 도구가 학습·평가에 동시에 들어가면 점수가 부풀려진다. 보고 지표: 축별 macro-F1, 클래스별 정밀도·재현율, 위험 하향 오분류 수(write/delete/execute/external_send를 read로 예측한 건수), 확신도 임계값별 "자동 제안 비율 vs 그 구간의 정밀도" 곡선.
  7. 속도: CPU 코어 수를 명시하고 학습 시간, 도구 1,000개당 추론 시간을 잰다.

완료 조건: 모델 A/B 비교표 + 권장 확신도 임계값(예: 그 구간 정밀도 ≥ 95%에서 커버리지 몇 %).

Phase 5 — 운영 연결 (PoC 이후)

  • 배치가 제안을 poc:proposal:*에 쓰고, 검토 화면/큐에서 사람이 확정한다. 확정 결과는 다음 학습 라벨이 된다(주 1회 재학습).
  • 스키마 해시가 바뀐 도구는 기존 판정을 유지하지 말고 재검토로 돌린다.
  • 신규 서버·도구는 기본 블랙(또는 보류) 상태로 두고, 제안이 나와도 쓰기 계열은 수동 승인.

3. 보안 체크 — 설명은 믿지 말 것

도구 설명(description)은 MCP 서버 작성자가 마음대로 쓰는 텍스트다. "읽기 전용 조회 도구"라고 써놓고 실제로는 쓰기·외부전송을 하는 tool poisoning이 알려진 공격 방식이다. 설명을 읽는 모델은 속을 수 있다.
대응: ① 파라미터 구조 신호(command, sql, path+쓰기 동사, url/webhook, to/recipient)를 규칙으로 먼저 본다 ② 설명 기반 예측과 구조 기반 규칙이 어긋나면 그 자체를 위험 신호로 검토 큐에 올린다 ③ 설명 안의 지시문(“ignore”, “always call”, 숨은 문자 등)을 탐지해 플래그한다.

4. 쓰지 말 것

  • 생성형 LLM이나 Jev류 판단 모델을 요청 경로에 넣기. CPU에서 느리고(0.8B급도 건당 수 초), 사내 분류 체계를 학습 없이 알 수 없다. 배치 보조로도 학습형 분류기보다 이득이 불분명하다.
  • 외부 LLM API로 스키마 보내 분류시키기. 데이터 반출.
  • 모델 확신도만으로 화이트리스트 자동 등록.

5. AI 에이전트에게 줄 지시문

너는 사내 LLM 게이트웨이의 MCP 도구 분류 PoC를 수행한다. 이 문서(Phase 0~4)를 순서대로 진행한다.
제약: CPU 전용, 외부 API로 데이터 전송 금지, 운영 Redis 키·화이트/블랙리스트 수정 금지(읽기 전용 + poc: 접두사 키만 쓰기),
요청 경로 코드 변경은 Phase 1 파서와 Phase 2 비동기 기록만 허용하며 반드시 테스트와 지연시간 측정을 동반한다.
각 Phase 종료 시 "완료 조건"의 수치를 표로 보고하고, 다음 Phase로 넘어가기 전에 멈춰서 승인을 받는다.
모르는 필드·규칙은 추측하지 말고 Redis 샘플에서 확인한 근거와 함께 적는다.
