작은 판단 모델이
내 대화의 모델을 고를 수 있을까?

OpenClaw에서 쉬운 요청은 가벼운 모델로, 어려운 요청은 강한 모델로 보내고 싶었다. 실제 한국어 대화 147건으로 Laya와 Jev-Style v3를 로컬에서 돌려봤다. 빠르기는 충분했다. 그러나 판단은 달랐다.

cocy 실측 · RTX 3080 Ti · 개인 원문 비공개
01 / VERDICT

지금은 자동 라우팅하지 않는다

맥락을 넣은 Jev-Style v3: 49–52%
단순한 규칙 + 이전 작업 유지: 76%

같은 147건의 재라벨된 3단계 과제에서 비교. 이것은 Jev 원본 API의 성능이 아니라 오픈웨이트 Jev-Style v3의 현장 실험 결과다.

작은 모델의 장점은 지연시간이었다. 하지만 작업 난도는 보편적인 문장 분류가 아니다. “이 일은 중요한가, 실패 비용이 큰가, 직전 대화에서 이어지는가”라는 우리 운영 기준을 알아야 한다. 모델을 일찍 연결하면 오히려 복잡한 작업을 약한 모델로 보내는 비용이 더 크다.

02 / DATA

먼저 데이터가 무엇인지

147실제 대화 건수최근 한 달 텔레그램 사용자 메시지, 중복 제거
53%맥락 의존“ㄱㄱ”, “계속해” 등 앞 대화 없이 분류 불가
1명정답 라벨러합의 라벨이나 독립 재검증 아님

처음에는 각 문장을 가벼움(6)·보통(43)·무거움(20)·후속(78)으로 분류했다. 두 번째 실험은 직전 대화 2턴을 붙이고 후속 메시지를 원래 작업의 난도로 다시 매겼다. 그 결과 3단계 정답 분포는 가벼움 10·보통 95·무거움 42였다. 4단계와 3단계의 정확도는 서로 직접 비교하면 안 된다.

원본 메시지·개별 정답·예측 로그는 공개하지 않는다. 개인정보 필터링을 거쳤지만 외부 학습·API 전송도 하지 않았다. 라벨 편향과 표본 부족 때문에 일반적인 한국어 벤치마크로 해석할 수 없다.

맥락 포함 3단계 정확도. Jev-Style 49.0–51.7%, Laya 24.5–34.0%는 선택지 순서를 바꾼 조건 범위. 76.2% 규칙은 같은 라벨러가 설계하고 평가한 휴리스틱이므로 독립적 일반화 성능이 아니다. ‘항상 보통’은 분포 불균형을 보여주는 기준선이다.

첫 4단계 실험에서는 Laya 17.7–43.5%로 20줄 규칙의 61.9%보다 낮았다. 새 v3는 4단계에서 44.2%. 그러나 v3의 성과는 순서 민감도다. 3단계에서 선택지 순서를 뒤집어도 95.9%가 같은 답이었다. 반면 LIGHT로 잘못 내린 메시지가 9~18건이었고, 그중 HEAVY도 3건 있었다.

원본 Jev 미측정

TypeSafe Jev API

로컬 클론의 점수로 원본 API를 판정할 수 없다. 공식 스킬은 에이전트가 API를 사용하게 도울 뿐, 설치만으로 라우팅 정책이나 모델 성능을 개선하지 않는다. 외부 API 테스트에는 계정·비용·대화 전송 범위 결정이 필요하다.

Jev-Style의 “Laya보다 51개 언어 모두 앞선다”와 벤치마크 성적은 제작자 자체 발표다. 우리의 147건 비교는 별도 현장 실험이지만 단일 사용자·단일 라벨러에 한정된다. 클론끼리의 비교로 Jev 원본을 폄하하지 않는다.

05 / NEXT

비용을 줄이려면 어디부터?

  1. 채팅 모델은 당분간 고정. 짧은 후속 답은 현재 작업 모델을 유지하고, 애매한 요청은 강한 모델을 유지한다.
  2. 자동화 작업별 비용부터 측정. 각 작업의 실제 토큰·비용·실패율을 본 다음 적합한 작업에만 가벼운 모델을 지정한다. 현재 “자동화가 비용 대부분”이라는 말은 아직 측정되지 않은 가설이다.
  3. 라우터를 재시도한다면 개인 기준으로 학습. 라벨 몇백 건을 추가하고 시간 분리 평가·심각한 잘못된 다운그레이드율까지 본다. 이번 147건으로 범용 정확도를 주장하지 않는다.
