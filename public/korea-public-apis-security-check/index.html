한국 공개API 300개 GitHub 목록,
써도 안전할까?

X 글(2026-11-07, 조회 약 4만)은 “한국에서 쓸 수 있는 공개API 300여 개 정리해둔 깃허브, 별 3.3k”라고 소개한다. 본문에 저장소 주소는 없다. 첨부 사진에 저장소명 public-apis-4Kr, MIT license, 3.3k stars, 375 forks가 찍혀 있어 yybmion/public-apis-4Kr로 특정했다. 우리는 이 저장소를 다운로드해 파일만 읽었고, 코드는 실행하지 않았다. 이 글은 저장소와 샘플 몇 개의 점검이지, 목록에 올라 있는 공급자 300곳의 감사가 아니다.

판정: 저장소 자체에서는 숨은 외부 전송 코드를 찾지 못했다. 하지만 “외부 전송 없음”으로 단정하지는 않는다. 위험은 목록이 아니라 그 안의 API를 실제로 쓸 때 생긴다.

2. 저장소 점검 결과 (정확한 커밋 기준)

커밋 000e39566e21e837288d4375a4a708c7d3043e92(2026-11-07 15:41 UTC), 파일 24개. MIT 라이선스(저작권자 yoobin_mion).

3. “외부 전송 없음”이라고 말할 수 없는 지점

저장소를 쓰는 방식에 따라 데이터가 나가는 곳이 달라진다. 단계를 나눠서 본다.

  • 목록 읽기: GitHub에서 열면 GitHub가 접속 기록을 갖는다. 배지는 GitHub 이미지 프록시를 거쳐 나오는 것이 일반적이지만 이번에 직접 확인하지는 않았다. 저장소를 내려받아 로컬 뷰어로 열면 shields.io 배지 요청이 뷰어에서 직접 나갈 수 있다.
  • 목록에서 링크 클릭: 해당 공급자(data.go.kr, naver, kakao 등)에 IP·브라우저 정보·리퍼러가 간다. 이건 모든 웹 링크와 같다.
  • 저장소 내려받기·클론: GitHub와만 통신한다. 클론한 것만으로 코드가 실행되지는 않는다.
  • 스크립트 실행: 우리는 하지 않았다. 직접 돌리면 README에 있는 모든 링크(약 300곳)로 요청이 나가고, 인증서 검증이 꺼져 있다.
  • 개별 API 사용: 여기가 실제 위험이다. 아래 샘플로 확인한 범위를 적는다.

4. 개별 API 샘플 (공급자 감사가 아니라 문서 열람)

공급자 문서 페이지를 GET으로 읽기만 했다. 키를 발급받거나 호출하지 않았다.

샘플확인한 사실의미
국토부 아파트 매매 실거래가 (공공데이터포털)엔드포인트가 https://apis.data.go.kr/1613000/RTMSDataSvcAptTrade. 인증키는 요청 파라미터 serviceKey(URL 인코딩)HTTPS이므로 전송 구간은 암호화. 다만 키가 URL에 실려 서버 로그·브라우저 기록·프록시 로그에 남기 쉽다. 브라우저에서 직접 호출하면 키가 페이지 소스에 노출된다
업비트 Open API문서가 JWT 토큰을 요청 헤더에 담아 보내도록 안내(문서 일부 확인)URL이 아니라 헤더라 로그 노출 위험은 낮다. 서명 비밀키는 서버 쪽에서만 다뤄야 한다. 거래·출금 권한 범위 설정은 이번에 확인하지 않았다
서울 지하철 실시간 도착, 주유소 가격(오피넷), 넥슨문서 페이지가 스크립트로 렌더링되어 엔드포인트 주소와 키 전달 방식을 확인하지 못했다미검증. HTTP 여부도 모른다

README 표의 인증 방식 분포(309행)는 apiKey 223, OAuth 33, 인증 없음(✕) 30, Login 13, Partnership 4, JWT 2, 기타 4다. 즉 대부분이 키 방식이다. 키가 공급자마다 제각각 URL·헤더·본문 어디로 가는지는 이 점검 범위 밖이다.

5. 쓸 때 지킬 것

1) 키는 서버에서만. 브라우저 JS에 공공데이터포털 serviceKey를 넣으면 누구나 볼 수 있다. 서버나 Workers 프록시를 두고, 그 프록시가 키를 붙이게 한다.
2) 프록시도 전송 지점이다. 사용자의 요청이 우리 서버를 거쳐 공급자로 나가므로, 이용자 IP·검색어(예: 주소·위치)를 로그에 남기지 않도록 한다. 개인정보가 섞인 질의는 특히 조심.
3) http:// 엔드포인트는 피한다. 목록에 평문 링크가 3개 있다. 키가 평문으로 나가는지는 공급자별로 직접 확인해야 한다.
4) 약관과 호출 한도를 먼저 읽는다. 공개API라도 상업 이용·재배포·캐시 허용 범위가 다르다. 이 점검은 약관을 보지 않았다.
5) 링크 점검 스크립트는 그대로 쓰지 않는다. 인증서 검증이 꺼져 있다. 돌려보려면 격리된 환경에서 의존성 버전을 고정하고 쓴다.

6. cocy 판단

이 저장소는 “어디에 무슨 API가 있는지” 알려주는 색인으로는 쓸 만하다. MIT이고, 문서 위주이며, 우리가 읽은 코드에서 의심스러운 동작은 없었다. 그렇다고 “안전하다”까지 말하기는 어렵다. 안전 여부는 그 안의 링크를 따라가 실제로 키를 만들고 호출하는 단계에서 결정되며, 그 부분은 공급자마다 다르고 이번에는 샘플 세 곳만 봤다. 트윗의 “API 하나 붙이면 서비스 하나”는 홍보 문구로 읽는 편이 맞다.
