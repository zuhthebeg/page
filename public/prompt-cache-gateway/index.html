Research note · LLM gateway · 2026-10-27

모델만 바꿨는데
비용이 3배 — 프롬프트 캐시 쉽게 풀기

당근 커뮤니티홈팀의 사례 글이 화제다. 단가가 20% 싼 GPT-5.6으로 바꿨는데 요청당 비용이 3.2배가 됐다. 원인은 프롬프트 캐시 히트율이 85.8%에서 2.3%로 떨어진 것이었다. 이 글을 OpenAI·Anthropic 공식 문서와 대조했다. 그리고 사내 LLM 게이트웨이를 운영하는 입장에서 무엇을 점검해야 하는지 정리했다.

쉬운 설명공식 문서 대조게이트웨이 점검표

9/10판정: 당근 글의 핵심 사실은 공식 문서와 일치. 게이트웨이 운영자에게 실전 가치 큼.

1. 먼저 오해 하나: 우리가 KV캐시를 "앞단에" 두는 게 아니다

LLM은 글을 읽을 때 토큰마다 중간 계산값을 만든다. 이걸 KV캐시라고 한다. 시험 보기 전에 규정집을 읽으며 적어 둔 메모라고 생각하면 된다. 이 메모는 모델이 도는 GPU 메모리 안에만 있다. API로 쓰는 우리 쪽, 즉 게이트웨이에는 둘 수가 없다.

프롬프트 캐시는 제공사가 그 메모를 요청이 끝난 뒤에도 잠깐 남겨 두는 기능이다. 다음 요청의 앞부분이 글자 하나까지 똑같으면 메모를 다시 쓰고 값을 깎아 준다. 그래서 게이트웨이가 할 일은 캐시를 "갖는" 게 아니다. 앞부분을 매번 똑같이 만들어서 보내는 것이다.

프롬프트 캐시 (이 글의 주제)

입력을 읽는 계산만 재사용한다. 답은 매번 새로 만든다. 품질은 그대로다. 제공사 서버에 있고, 게이트웨이는 앞부분을 안정적으로 유지하는 역할만 한다.

응답 캐시·시맨틱 캐시

같거나 비슷한 질문에 저장해 둔 답을 그대로 돌려준다. 이건 게이트웨이에 직접 둘 수 있다. 대신 틀린 답을 재사용할 위험이 있다. 전혀 다른 기능이다.

자체 GPU에 vLLM 같은 서버를 직접 띄우는 경우라면 서버 쪽 prefix caching을 우리가 켤 수 있다. API를 사서 쓰는 경우에는 위 설명이 맞다.

2. 왜 "앞부분"이 똑같아야 하나

모델 안에서 뒤쪽 토큰의 메모는 앞쪽 토큰 전부를 보고 만들어진다. 그래서 맨 앞에서 한 글자만 바뀌어도 그 뒤 메모가 전부 달라진다. 당근 글의 예가 좋다. 프롬프트 맨 앞에 넣은 시각이 09:00에서 09:01로 바뀌면, 그 뒤 지시문 수천 토큰을 다시 계산한다. 시각을 맨 뒤로 옮기면 마지막 몇 토큰만 다시 계산한다.

규칙 하나로 줄이면 — 매번 같은 것(지시문·규칙·예시·도구 정의)은 앞에, 매번 바뀌는 것(사용자 입력·시각·요청 ID)은 뒤에.

3. 효과는 얼마나 큰가

당근은 앞부분을 고친 뒤 히트율이 95% 안팎으로 올랐고, 요청당 비용이 약 5분의 1로 줄었다. 아래는 공식 단가 배율로 직접 계산한 값이다. 고정부가 입력의 95%이고 쓰기 1.25배, 읽기 0.1배라고 가정했다.

캐시 상태입력 비용 (캐시 없음 = 100)설명
캐시 없음100기준
매번 저장만 하고 못 읽음125당근이 빠졌던 상태. 할증만 낸다
고정부를 매번 읽음 (명시 구분점)약 1595×0.1 + 5×1.0. 바뀌는 부분은 저장하지 않는다

같은 요청이 캐시 상태에 따라 8배 넘게 차이 난다. 쓰기 할증이 있으니 손익분기점도 있다. 고정부를 읽는 비율이 약 22% 아래면 캐시를 켠 쪽이 더 비싸다. 계산식은 0.1×h + 1.25×(1−h) = 1이다. 출력 토큰은 캐시와 무관하게 정가다. 그래서 출력이 긴 작업에서는 전체 절감 폭이 이보다 작다.

4. 당근은 왜 당했나 — 모델이 바뀌면 캐시 규칙도 바뀐다

OpenAI 문서에 따르면 GPT-5.6부터 자동 구분점이 가장 최근 메시지의 끝에 찍힌다. 당근의 요청은 "지시문 + 글 본문"을 메시지 하나로 보냈다. 그래서 저장되는 덩어리가 "지시문 + 글 A" 통째였다. 다음 요청 "지시문 + 글 B"는 그 덩어리와 같지 않으니 못 읽는다. "지시문까지"만 담은 덩어리는 한 번도 저장되지 않았다. 모든 요청이 1.25배를 내고 저장만 한 것이다. 에러는 하나도 없었다.

해결은 지시문이 끝나는 자리에 명시 구분점을 찍는 것이었다. OpenAI는 prompt_cache_breakpoint, Anthropic은 cache_control이다. 당근은 사내 LLM 플랫폼이 템플릿의 첫 변수 앞에 자동으로 구분점을 찍도록 고쳤다. 사람에게는 "바뀌는 부분은 템플릿 끝에 둔다" 하나만 지키게 했다. 이게 게이트웨이 팀이 가져갈 핵심 교훈이다.

5. 사내 게이트웨이·가드레일 점검표

게이트웨이는 요청을 중간에서 고치는 계층이다. 그래서 캐시를 깨는 1순위 용의자이기도 하다. 아래 항목에 하나라도 걸리면 히트율을 실측해 봐야 한다.

게이트웨이가 하는 일캐시가 깨지는 경우안전한 방식
가드레일 정책문을 system 앞에 삽입정책문에 사용자 ID·시각·요청 ID·부서명이 들어감정책문은 전사 고정 문구로. 가변 정보는 맨 뒤에 붙인다
PII 마스킹 (입력 다시 쓰기)턴마다 마스킹 결과가 달라짐 (예: [EMAIL_1] 번호가 매번 다시 매겨짐). 이전 대화까지 다시 마스킹결정적 마스킹 (같은 값 → 같은 토큰). 이미 처리한 이전 턴은 건드리지 않는다
요청 JSON 파싱 후 재직렬화키 순서·공백·유니코드 이스케이프가 바뀜. 특히 도구 스키마원본 바이트를 그대로 넘기거나, 정렬을 고정한 직렬화
권한별로 도구 목록 필터링사용자마다 도구 집합·순서가 달라짐도구 정의는 고정. 막을 때는 tool_choice 같은 방식으로 실행 단계에서 차단
스키마 검증·필드 화이트리스트cache_control·prompt_cache_breakpoint·prompt_cache_options를 모르는 필드로 떨굼캐시 필드는 그대로 통과. 당근도 중간 계층이 일부 요청에서 이걸 빠뜨렸다
폴백·라우팅으로 모델 전환모델이 바뀌면 캐시는 처음부터 다시 쌓인다. 제공사가 바뀌면 규칙도 다르다세션 중 모델을 고정한다 (sticky). 전환 전후 히트율을 비교한다
입력 가드레일 분류 호출 (별도 LLM 호출)정책 프롬프트 + 검사할 입력을 메시지 하나로 보냄 → 당근과 같은 함정분류 호출 자체도 "고정 정책 → 구분점 → 가변 입력" 구조로

잘 적용됐는지 확인하는 법

  1. 두 요청 테스트: 앞부분은 같고 끝만 다른 요청 두 개를 게이트웨이를 거쳐 연달아 보낸다. 두 번째 응답의 캐시 읽기 토큰이 0보다 커야 한다. 똑같은 요청을 두 번 보내면 구분점이 잘못돼도 히트처럼 보이니 주의한다.
  2. 응답 필드 수집: OpenAI는 usage.input_tokens_details.cached_tokens와 cache_write_tokens를 본다. Anthropic은 cache_read_input_tokens와 cache_creation_input_tokens를 본다. Anthropic은 input_tokens에 이 둘이 빠져 있어서 셋을 더해야 전체 입력이다.
  3. 토큰 기준 히트율 대시보드: 캐시 읽기 토큰을 전체 입력 토큰으로 나눈 값을 서비스·모델·일자별로 본다. 요청 기준(한 토큰이라도 읽었으면 히트)은 후하게 나온다.
  4. 쓰기 대비 읽기 비율: 쓰기만 많고 읽기가 적으면 할증만 내고 있다는 신호다.
  5. 제공사 진단 기능: OpenAI의 Prompt Cache Diagnostics와 Anthropic의 cache diagnostics를 쓰면 미스 사유(도구 변경 등)를 알려 준다.

6. 코덱스·클로드코드는 개인이 쓰는데, 크로스히트가 되나

사람 사이 공유는 기대하면 안 된다. 맞다. 그런데 그게 손해의 핵심도 아니다.

  • 캐시 공유 범위: OpenAI는 조직(org)과 처리 리전 단위로 공유하고, 조직끼리는 절대 공유하지 않는다. Anthropic은 Claude API에서 워크스페이스 단위로 격리한다. Bedrock은 조직 단위다. 개인 구독으로 로그인한 코덱스·클로드코드는 각자 계정이라 사용자끼리 캐시를 나눌 일이 없다.
  • 에이전트 코딩 툴의 이득은 세션 안에서 나온다: 에이전트는 매 턴마다 지금까지의 대화 전체를 다시 보낸다. 이전 턴까지가 그대로 앞부분이 되니, 긴 세션일수록 입력의 대부분을 캐시에서 읽는다. 다른 사람과 공유하지 않아도 히트율이 높게 나오는 구조다.
  • 회사 키로 게이트웨이를 거치면 얘기가 달라진다: 같은 조직 키를 쓰면 공통 시스템 프롬프트와 도구 정의는 사용자 사이에서도 히트할 수 있다. 다만 OpenAI는 캐시가 개별 머신에 있다. 같은 앞부분이 분당 15건을 넘으면 다른 머신으로 넘쳐서 못 읽을 수 있다. GPT-5.6 이전 모델은 prompt_cache_key로 관련 요청을 묶어 줘야 잘 맞는다. 사용자별 프로젝트 설명(CLAUDE.md 등)이나 레포 내용이 앞쪽에 섞이면 공통 부분은 짧아진다.
  • 보안 관점: 같은 조직 안에서 캐시가 공유되는 것 자체가 걱정이면 Anthropic은 워크스페이스를 나누면 된다. OpenAI는 prompt_cache_key로 그룹별 회계를 분리할 수 있다.

7. 에이전트가 늘어날 때 사내 가이드로 줄 7가지

  1. 고정부(지시문·규칙·예시·도구)는 앞에, 가변부(입력·시각·ID)는 뒤에 둔다.
  2. 고정부 끝에 명시 구분점을 찍는다. 템플릿 플랫폼이나 게이트웨이가 자동으로 찍게 하는 게 가장 좋다.
  3. 고정부가 모델별 최소 길이를 넘는지 확인한다. GPT-5.6 이후는 1,024토큰이다. 짧으면 에러 없이 캐시가 안 된다.
  4. 같은 앞부분이 유지 시간 안에 다시 오는지 본다. OpenAI 5.6 이후는 기본 30분, Anthropic은 기본 5분이다. 드물게 오는 작업은 할증만 낸다.
  5. 도구 목록과 JSON 직렬화를 고정한다. 도구는 빼지 말고 실행 단계에서 막는다.
  6. 모델 교체는 코드 한 줄이 아니라 운영 변경으로 다룬다. 전후 요청당 비용·히트율·지연을 운영 트래픽으로 하루 이상 비교한다.
  7. 히트율·쓰기/읽기 비율을 게이트웨이 표준 대시보드에 넣는다. 캐시가 깨져도 에러는 안 나고 비용만 오르기 때문이다.

8. cocy 판단

"앞단에 캐시를 둔다"가 아니라 "게이트웨이가 앞부분을 흔들지 않는다"가 정확한 그림이다. 효과는 크다. 같은 요청이 캐시 상태에 따라 8배 넘게 차이 난다. 그리고 게이트웨이 가드레일은 구조상 앞부분을 건드리는 위치에 있다. 지금 가드레일이 잘 적용됐는지는 문구를 봐서는 알 수 없고, 두 요청 테스트와 토큰 기준 히트율로만 판단할 수 있다. 개인 구독 코딩 에이전트는 크로스히트가 안 되지만 세션 내 히트로 이미 대부분 이득을 본다. 사내 API 에이전트가 늘어날 때 게이트웨이 팀이 줄 수 있는 가장 값싼 절감은 구분점 자동 삽입 + 히트율 대시보드 두 가지다.
