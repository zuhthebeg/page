사내 LLM 게이트웨이
프롬프트 캐시 점검표

회사에서 항목별로 적용됨 / 적용 필요 / 해당 없음을 눌러 체크한다. 체크 상태와 메모는 이 브라우저에만 저장된다. 배경 설명은 공개 페이지 프롬프트 캐시와 게이트웨이 점검표에 있다.

0. 먼저 알아둘 것 (3줄)

캐시는 우리 쪽에 없다. KV캐시는 제공사 GPU에 있다. 게이트웨이의 역할은 앞부분을 매번 똑같이 보내고, 어디까지 저장할지 표시해 주는 것이다.

구분점 = 요청 JSON의 표시용 필드. 마침표 같은 글자가 아니고 프롬프트 내용도 안 바뀐다. "처음부터 여기까지 한 덩어리로 저장해"라는 꼬리표다.

깨져도 에러가 안 난다. 비용만 오른다. 그래서 체크는 설정이나 문구가 아니라 응답의 캐시 필드 숫자로 해야 한다.

// Anthropic
"system": [{ "type":"text", "text":"(고정 지시문)",
             "cache_control": {"type":"ephemeral"} }],   ← 구분점
"messages": [{ "role":"user", "content":"(가변 입력)" }]

// OpenAI (GPT-5.6+, Responses API)
"prompt_cache_options": {"mode":"explicit"},
"input": [{ "role":"developer", "content":[{ "type":"input_text",
            "text":"(고정 지시문)",
            "prompt_cache_breakpoint": {"mode":"explicit"} }]},   ← 구분점
          { "role":"user", "content":"(가변 입력)" }]

1. 어디가 위험한가 (우선순위)

P1사내 서비스가 API로 분류·요약·추출을 대량으로 돌리는 경우. "고정 지시문 + 매번 다른 입력" 구조다. 당근이 당한 게 이 경우다. GPT-5.6부터 자동 구분점이 마지막 메시지 끝에 찍혀서, 지시문과 입력을 메시지 하나로 보내면 매번 저장(1.25배)만 하고 못 읽는다.

P2사내 챗봇·에이전트. 대화가 뒤에 계속 붙는 구조라 자동 구분점으로도 대체로 읽힌다. 다만 게이트웨이가 앞부분을 건드리면 깨진다.

P3개인이 쓰는 코덱스·클로드코드. 구분점은 도구 회사가 찍는다. 사용자 간 공유는 안 되지만 세션 안에서 대부분 히트한다. 회사 키로 게이트웨이를 태울 때만 점검 대상이다.
