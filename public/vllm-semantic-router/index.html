Infra Deep-Dive · Semantic Routing

vLLM Semantic Router:
요청 신호로 모델을 고르는 컨트롤 플레인

모델명을 하드코딩하는 대신, 요청의 의도·위험·난이도를 읽어 라우팅한다. 사내 도입 관점에서 이 라우터가 무엇이고, 무엇을 실제로 돌려야 하며, 어디까지 믿을 수 있는지 정리한다.

대상 vllm-project/semantic-router · v0.3 Themis 일자 2026-07-23 관점 사내 도입 검토

애플리케이션이 "이 요청은 gpt로, 저건 claude로"를 코드에 박는 순간, 라우팅은 흩어진 if-else가 된다. vLLM Semantic Router(이하 vLLM SR)는 그 판단을 애플리케이션 밖 컨트롤 플레인으로 끄집어낸다. 클라이언트와 모델 백엔드 사이에 Envoy External Processor(ext_proc)로 앉아, 요청에서 신호를 뽑고, 정책으로 결정하고, 그 결정을 관측·감사·통제 가능하게 만든다. 앱은 단일 엔드포인트 MoM(Mixture-of-Models) 하나만 호출한다.

사내 도입 한 줄 판단

"단일 게이트웨이 뒤에서 비용·안전·품질을 정책으로 통제"가 필요하면 진지한 후보다. 라우터 본체가 GPU 없이 CPU로 도는 점, 요청 경로 안에 PII·탈옥·환각 통제가 붙는 점, K8s 오퍼레이터가 있는 점이 사내 적합성을 높인다. 다만 아직 v0.3(0.x)이고 Envoy 운영·설정 학습곡선이 있어, 표준 채택이 아니라 통제된 PoC로 시작하는 게 맞다.

01무엇인가 — Mixture-of-Models 컨트롤 플레인

vLLM SR의 전제는 "하나의 만능 모델"이 아니라 Mixture-of-Models — 모델마다 잘하는 일이 다르고, 컴퓨트(GPU·엣지·클라우드)와 데이터 위치도 제각각이라는 것. 그 이질성을 앱이 떠안지 말고, 라우터가 요청별 실행 경로로 바꿔준다. vLLM 프로젝트 공식 서브프로젝트이며 AMD가 라우터 모델 학습용 GPU를 후원한다.

  • 하드코딩 대신 정책 — 라우팅 로직을 신호·결정·설정으로 분리해 코드 밖에서 관리.
  • 역량 기반 선택 — 모든 요청을 한 모델로 보내지 않고, 작업 성격·위험·품질 요구에 맞춰 배분.
  • 요청 경로 내 거버넌스 — 라우팅을 결정하는 바로 그 계층에서 PII·탈옥·환각을 통제.
  • 감사 가능한 결정 — 왜 이 모델로 갔는지 로그로 남아, 추측이 아니라 데이터로 튜닝.

02어떻게 도는가 — 신호 → 투영 → 결정 → 플러그인

핵심 파이프라인은 4단이다. 요청이 들어오면 신호를 뽑고(Signals), 경합하는 근거를 조율하고(Projections), 정책 규칙으로 경로를 정하고(Decisions), 플러그인 체인을 태워 모델로 보낸다.

Signals
요청·안전·후속·선호 사실 추출 (16 신호군)
→
Projections
경합 매칭 조율 → 명명된 라우팅 밴드
→
Decisions
신호에 대한 AND/OR 정책 규칙 → 경로·후보모델
→
Plugins
캐시·안전·주입 체인 → 모델 디스패치

16개 신호군 (CPU BERT 분류기로 추출)

붉은 칩(authz·pii·jailbreak·fact-check)이 안전·컴플라이언스 신호다. "난이도(complexity)" 신호가 비용 절감의 핵심 — 쉬운 요청은 싼 모델로 내린다.

플러그인 체인 (요청/응답 가로채기)

플러그인역할사내 가치
semantic-cache의미 유사도 기반 캐싱유사 질의 비용·지연 절감
pii개인식별정보 탐지컴플라이언스 민감정보 보호
jailbreak적대적 프롬프트 탐지보안 프롬프트 인젝션 차단
hallucination토큰 단위 환각 탐지(생성 중)실시간 사실 검증
system_prompt경로별 동적 시스템 프롬프트 주입라우트별 맥락 지시
header_mutationHTTP 헤더 조작백엔드 라우팅 제어

이게 vLLM SR의 차별점이다 — 라우팅을 결정하는 계층에서 안전·거버넌스를 함께 처리한다. 별도 보안 프록시를 두지 않아 서빙 스택이 쪼개지지 않는다.

03실제로 뭘 돌려야 하나 — 배포·요구사항

사내 도입에서 가장 중요한 현실. 라우터 본체는 GPU가 필요 없다 — 신호 추출을 최적화된 BERT 모델로 CPU에서 돌린다. 판단 계층이 싸다는 뜻이라 도입 문턱이 낮다.

항목내용
실행 하드웨어CPU 전용 (라우터). 백엔드 LLM은 vLLM·Ollama·외부 API 무엇이든
요구사항Python 3.10+ · Docker · Linux/macOS/WSL2
모델 다운로드분류기 ML 모델 ~1.5GB 최초 1회 (HuggingFace, 미러 hf-mirror.com 지원)
배포 형태로컬 vllm-sr serve(Docker) · 또는 Kubernetes/OpenShift 오퍼레이터
인터페이스OpenAI 호환 /v1/chat/completions, 모델명 MoM
포트대시보드 8700 · Envoy 8888 · 시뮬 8810 · 메트릭 9190(Prometheus)
설정YAML-first config.yaml (version/listeners/providers/routing/global) · vllm-sr validate

기본 스모크 테스트는 이 한 방이다 — 앱 입장에서는 그냥 OpenAI API다:

curl http://localhost:8888/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"MoM","messages":[{"role":"user","content":"Hello!"}]}'

v0.3에서 vllm-sr init은 제거됐고, canonical 레이아웃으로 config.yaml을 직접 쓰거나 config migrate로 이관한다. GPU 없이 로컬 LLM만으로 감을 보려면 Ollama 연동 경로가 있다.

04왜 사내에 맞나 — 엔터프라이즈 적합성

거버넌스 · 컴플라이언스

  • PII·탈옥·환각 통제가 요청 경로 안에 — 별도 보안 프록시 불필요
  • 권한(authz) 신호로 사용자·워크로드별 접근 제어

비용 거버넌스

  • 난이도 신호로 쉬운 요청은 싼 모델 → 프리미엄 모델·긴 컨텍스트·툴콜은 필요한 요청에만
  • 시맨틱 캐싱으로 유사 질의 재사용

데이터 경계

  • 엣지·프라이빗·클라우드 백엔드로 요청을 경계 안에 가두는 라우팅 설계(데이터 residency)

관측성 · 운영

  • 라우팅·정책 결과가 감사 가능 — "왜 이 모델로 갔나" 복기
  • Prometheus 메트릭(9190) 기본 노출 → 기존 모니터링에 편입

05냉정한 리스크 — 도입 전 알아야 할 것

Risks

  • 성숙도 0.x — v0.1(1월)·v0.2(3월)·v0.3(6월)로 빠르지만, 설정 계약(config contract)이 버전 간 바뀐다(예: v0.3에서 init 제거). 업스트림 급변 대비해 버전 고정·어댑터 격리 필요.
  • Envoy 운영 부담 — ext_proc 사이드카 구조라 Envoy·Docker/K8s 운영 역량이 전제. 서버리스 팀엔 학습곡선.
  • 신호 분류 정확도 — 라우팅 품질은 BERT 분류기 정확도에 달렸다. 도메인·난이도 오분류 시 엉뚱한 모델로 감 → 사내 트래픽으로 튜닝·평가 필수.
  • HF 의존 — 분류 모델 ~1.5GB를 HuggingFace에서 받는다. 폐쇄망이면 미러·사전 캐시(HF_HOME) 전략 필요.
  • 지원 체계 — 커뮤니티(vLLM Slack #semantic-router, 월 2회 미팅) 기반. 엔터프라이즈 SLA·유상 지원은 없다.

06사내 PoC 플랜 — 어떻게 시작하나

  1. 무설치 감 잡기 — 온라인 플레이그라운드(app.vllm-sr.ai/playground)로 라우팅 동작 체험.
  2. 로컬 CPU 기동 — 격리 VM/WSL2에 vllm-sr serve, 대시보드(8700)에서 우리 모델 2~3개(외부 API + 로컬 Ollama) 연결.
  3. 정책 구성 — 난이도 라우팅(쉬움→싼 모델) + semantic-cache + pii 플러그인 활성, config.yaml로 버전관리.
  4. 실측 — 대표 트래픽 샘플로 4지표 측정: ①비용 절감% ②라우팅 정확도(오분류율) ③지연 오버헤드 p50/p95 ④PII·탈옥 차단율.
  5. 스테이징 승격 — 결과 양호 시 K8s 오퍼레이터로 스테이징 배포, Prometheus(9190) 대시보드·감사 로그 검증.
  6. 거버넌스 관문 — 키 격리, 아웃바운드 화이트리스트, 폐쇄망 HF 캐시, 버전 고정. 하나라도 막히면 실험으로 격하.
측정 없는 도입 금지

"싸졌다"만으론 부족하다. 비용 절감이 품질 저하로 상쇄되지 않는지(오분류로 약한 모델에 간 요청 비율)를 반드시 같이 측정한다. 이 4지표가 채택/보류를 가른다.

07결론

Bottom line

vLLM SR은 "단일 엔드포인트 뒤의 정책 컨트롤 플레인"을 진지하게 구현한, 사내 도입을 검토할 가치가 충분한 후보다. CPU로 도는 가벼운 판단 계층 + 요청 경로 내 안전·거버넌스 + K8s 배포 + 관측성이 엔터프라이즈 요건을 정면으로 겨눈다. 리스크는 성숙도(0.x)와 Envoy 운영·분류 정확도 — 그래서 PoC로 4지표를 실측한 뒤 표준화 여부를 판단한다. 지금 단계의 정답은 "채택"이 아니라 "측정된 PoC"다.
