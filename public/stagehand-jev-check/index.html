Model check · Follow-up to jev-check

Stagehand v4, Jev 탑재로
정말 출시됐나

"오픈소스 Stagehand v4가 나와서 Playwright 유저들이 대거 갈아탄다. 요즘 화제인 Jev를 탑재해서 LLM 호출을 97% 줄이고 속도를 11배 올렸다"는 바이럴 트윗을 봤다. 반복 실행 비용이 "0원"으로 수렴한다는 표현까지 붙었다. 숫자만 보면 인상적인데, 실제로 뭐가 릴리즈됐고 뭐가 아직 아닌지 GitHub PR과 npm 배포 기록을 직접 대조했다.

6/10판정: 숫자는 진짜 PR 데이터에서 나왔다, 근데 그 PR 10개가 전부 merge 안 됐다
✓ Stagehand는 실재하는 유명 오픈소스(★25,009, MIT, Browserbase) ✓ Jev 연동 작업도 실재 — GitHub에 PR 10개, 9/17~9/21 사이 커밋 △ 인용된 숫자(4.3배·11.1배·97%)는 실제 PR 결과 표에서 나온 값, 다만 각기 다른 PR의 최고치를 하나로 합침 ✗ npm 최신 안정판 v4.1.0(9/9)엔 Jev 코드 자체가 없음 — "v4 출시"와 시점이 안 맞음 ✗ PR 10개 전부 merge 안 됨. merge돼도 `experimentalJevAct` 플래그 opt-in이라 기본은 꺼짐

1. 진짜인 부분 — Stagehand와 Jev 연동 작업 자체

Stagehand는 진짜다. Browserbase가 만든 오픈소스 브라우저 자동화 SDK로, Playwright 위에서 자연어로 act()(클릭·입력 등 액션), observe()(페이지 요소 파악), extract()(데이터 추출)를 시키는 라이브러리다. 2024년부터 개발돼 ★25,009, MIT 라이선스, 지금도 활발히 커밋되는 프로젝트다.

Jev 연동도 실재한다. GitHub에 PR 10개짜리 스택(#2951~#2998, 9/17~9/21 사이)이 있다. 지금까지 매 act() 호출마다 a11y 트리 전체를 LLM 한 번에 넘기던 구조를, "클릭 X" "Y에 텍스트 입력" 같은 뻔한 액션은 먼저 Jev(닫힌 선택지 분류 문제)에게 맡기고 애매할 때만 LLM으로 폴백하는 구조로 바꾸는 작업이다. 전에 정리한 Jev 유즈케이스 리뷰에서 "④ Browser Use"로 꼽았던 바로 그 자리다.

2. 숫자 검증 — PR 데이터 원본 대조

PR 설명에 실제 측정 표가 있다. 트윗의 "97%·11배" 숫자는 실제로 이 표들에서 나왔다:

지표출처측정값
act() 지연시간PR #2953P50 1.97s → 0.46s = 4.3배
observe() 지연시간PR #2954P50 1.99s → 0.18s = 11.1배
LLM 호출 불필요 비율PR #2953 (act 스위트)147개 중 143개(4개만 LLM 필요) = 97.3%

즉 트윗의 "11배"는 observe() 숫자, "97%"는 act() 스위트의 LLM-불필요 비율이다. 둘 다 진짜 값이지만 서로 다른 PR, 서로 다른 함수의 최고치를 하나로 묶어 "Stagehand 전체가 이렇게 좋아졌다"는 식으로 포장한 것 — laya-mlx의 "50배" 사건과 같은 패턴이다. PR 저자 본인도 "in-sample로 threshold를 튜닝했다"고 caveat을 달아뒀다.

3. "v4 출시로 탑재됐다"는 왜 틀렸나

타임라인이 안 맞는다.
- npm @browserbasehq/stagehand 최신 안정판은 v4.1.0, 9월 9일 배포. 이 시점엔 Jev 관련 코드가 저장소에 전혀 없었다(PR들은 9/17부터 시작).
- Jev 연동 PR 10개 전부 아직 merge 안 됨(#2998은 merge 없이 close됨). 지금 npm install로 받는 Stagehand엔 Jev 코드가 안 들어 있다.
- PR 설명에 명시: "Experimental and off by default. Nothing changes unless experimentalJevAct is present in the init params." — 나중에 merge돼도 기본은 꺼진 상태로 배포될 설계다.

"반복 실행 비용이 0원으로 수렴한다"는 표현도 방향은 맞지만 과장이다. Jev가 LLM 폴백 없이 액션을 끝내면 그 호출의 LLM 토큰 비용은 실제로 0이 맞다(PR 테스트 로그에 "0 LLM tokens"로 명시). 다만 Jev 자체 API 호출 비용은 별도로 존재하고, 97.3%는 특정 튜닝된 테스트 스위트에서 측정한 비율이라 모든 워크로드에 그대로 적용되진 않는다.

4. 그래서 지금 쓸 수 있나

✗ 지금 당장npm install stagehand로는 Jev 기능이 안 들어온다. 쓰려면 PR 브랜치를 직접 체크아웃해야 함
△ merge된 이후플래그 opt-in이라 명시적으로 experimentalJevAct를 켜야 동작. 프로덕션 기본값은 여전히 LLM 전체 경로
✓ 아이디어 자체a11y 트리 전체를 매번 LLM에 넘기는 대신, 닫힌 선택지 판단만 빠른 분류 모델에 맡기는 설계는 타당 — Jev 게이트웨이 리뷰에서 이미 "지금 당장 넣을 만한 것"으로 꼽은 유즈케이스와 정확히 일치

결론

Stagehand도 진짜, Jev 연동 작업도 진짜, 인용된 숫자도 실제 PR 측정치에서 나온 진짜 값이다. 다만 "v4 릴리즈로 탑재돼 Playwright 유저들이 갈아타는 중"이라는 프레이밍은 사실이 아니다 — 10개 PR 전부 merge 전 단계고, merge돼도 기본 꺼짐 상태로 나올 설계다. 실제로 쓰려면 지금은 PR 브랜치를 직접 받아 실험하는 수밖에 없고, 프로덕션에 넣을 물건은 아직 아니다.
