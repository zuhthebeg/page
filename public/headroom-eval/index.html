01 개요

Headroom은 에이전트가 읽는 툴 출력·로그·RAG 청크·파일을 LLM에 도달하기 전에 압축하는 레이어다. 로컬에서 동작해 데이터가 외부로 나가지 않고, 원본을 보존했다가 필요 시 모델이 다시 꺼내는 가역(CCR) 구조다. 라이브러리·프록시·MCP·플러그인 4가지 모드를 제공하며 OpenClaw 전용 플러그인도 1급으로 지원한다.

게이트웨이 담당자 관점에서 매력 포인트는 프록시를 게이트웨이 앞단에 두면 사용자 코드 변경 없이 중앙에서 토큰을 절감할 수 있다는 점이다.

02 실측 결과

격리 환경에서 실제 워크로드 데이터(JSON 덤프·검색 결과·소스 파일)로 측정했다. 헤드라인 "60–95%"는 최상 케이스(거대·반복 구조 데이터)에서만 재현됐다.

사용자 워크로드실효 절감판정
반복 JSON · 검색결과 · 로그 · RAG 대량40–90%강력 ✓
중첩·산문형 JSON~10%미미 △
코드·HTML·산문 파일 (코딩 에이전트)~0%효과 없음 ✗
기본 안전모드 (디폴트)~0%설계상 보호

기본값은 "툴 출력 전부 보호"로 설정돼 코딩 에이전트를 깨지 않게 보수적이다. 큰 절감은 압축을 적극 활성화해야 나오며, 산문 압축에는 별도 ML 모델(Kompress-base ≈ 604MB, CPU 구동 가능)이 필요하다.

요지: 효과는 전적으로 "누가 쓰느냐"에 달렸다. 데이터·로그·검색 헤비 사용자에겐 실익이 크고, 코딩 에이전트 사용자에겐 거의 없다.

03 게이트웨이 리스크

  • 블라스트 반경 = 전 사용자. 중앙 압축이 오작동하면 모든 사용자의 맥락이 조용히 열화될 수 있다.
  • 프롬프트 캐시 적중 저하 가능. 압축 개입이 KV 캐시를 깨면 절감이 상쇄되거나 역효과 — 사전 측정 필수.
  • 단일 프록시 = 장애점. SLA 있는 공용 게이트웨이엔 가용성 부담.
  • 코드 정밀 편집 위험. 압축이 verbatim 편집에 필요한 바이트를 떨구면 편집 실패 가능.
  • 완화 요인. 로컬 실행(데이터 안전) · 가역(CCR 원본 보존) · 보수적 기본값 · Apache-2.0. 롤백은 설정 한 줄.

04 권장안

  1. 전사 기본 적용 금지. 게이트웨이 강제 레이어로 넣지 않는다.
  2. 옵트인 카탈로그 등재. "툴출력·로그·RAG 헤비" 사용자에게 권장(프록시 또는 플러그인).
  3. 코딩 에이전트 사용자엔 비권장 또는 안전모드 고정.
  4. 파일럿 먼저. 자원자 소수에 2–4주 적용 후 ① 실절감률 ② 정확도 회귀 ③ 캐시 적중 변화를 측정해 확대 판단.
  5. 산문 압축이 필요하면 Kompress-base(≈604MB, CPU 가능)를 추가한다.

05 결론

도구 자체는 견고하고, 로컬·가역이라 데이터 안전성이 높다. 다만 이득이 워크로드에 강하게 의존하므로 "모두에게 켜는" 인프라 기능으로는 적합하지 않다. 적합한 사용자에겐 적극 권장하되, 코딩 헤비 워크로드엔 보류하는 선택적 도입이 정답이다.
