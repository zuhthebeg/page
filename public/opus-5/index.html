Claude Opus 5

Claude Opus 5(claude-opus-5)는 Opus 4.8의 후속으로, 가격이 같다($5/$25). 4.8에서 올라올 때 깨지는 변경은 딱 두 개인데 둘 다 thinking 관련이라 놓치기 쉽다. 실무에서 더 중요한 건 조용히 바뀐 것 — 캐시 최소 길이가 512토큰으로 절반이 됐다.

02 4.8에서 깨지는 것 — 두 개

① thinking이 기본 ON이 됐다. 4.8에서는 thinking 필드를 생략하면 사고 없이 실행됐다. Opus 5는 같은 요청이 adaptive thinking으로 돈다. max_tokens는 사고 + 응답 텍스트 합계의 하드 리밋이므로, 4.8에서 사고 없이 빠듯한 max_tokens로 돌던 워크로드는 응답이 잘린다. 이전 동작을 유지하려면 명시적으로 꺼야 한다.

② thinking:disabled는 effort high 이하에서만 허용된다. {"type":"disabled"}와 effort xhigh/max를 함께 보내면 400이다. 게다가 요청마다 독립적으로 검증돼서, 대화 중간에 effort만 올려도 그 요청이 거부된다.

거부되는 조합
{ model: "claude-opus-5", thinking: { type: "disabled" }, output_config: { effort: "xhigh" } } ← 400
해결 A — 사고를 다시 켠다
{ model: "claude-opus-5", output_config: { effort: "xhigh" } } // thinking 생략 = ON
해결 B — effort를 낮춘다
{ model: "claude-opus-5", thinking: { type: "disabled" }, output_config: { effort: "high" } }

문서 권고: 사고를 끄면 툴 호출이 평문으로 새거나 내부 XML 태그가 응답에 섞이는 경우가 있다. 가능하면 사고를 켠 채 effort를 낮추는 쪽을 택하라고 안내한다.

03 4.7 이전에서 올라온다면

위 두 개에 더해, Opus 4.7 세대에서 이미 적용된 변경들이 함께 걸린다. 구버전 코드를 그대로 올리면 여기서 먼저 터진다.

  • 샘플링 파라미터 제거 — temperature·top_p·top_k를 보내면 400. 결정성이 목적이었다면 effort:"low" + 더 조인 프롬프트로, 변주가 목적이었다면 프롬프트 지시로 옮긴다
  • 수동 확장사고 제거 — thinking:{type:"enabled", budget_tokens:N}은 400. adaptive + effort로 대체하며, 토큰 예산과 1:1 대응은 없다
  • assistant 프리필 제거 — 마지막 assistant 턴 선입력은 400. JSON 강제는 output_config.format, 서두 제거는 시스템 프롬프트 지시로
  • 토크나이저 변경(4.7부터) — 같은 텍스트가 더 많은 토큰이 된다. 옛 모델에서 잰 토큰 수·컨텍스트 예산·max_tokens를 재사용하지 말고 count_tokens로 다시 잰다

04 캐싱 — 이번 세대의 실질 이득

Opus 5에서 조용히 바뀐 것 중 비용에 가장 직접 닿는 건 최소 캐시 길이가 1,024 → 512 토큰으로 내려간 것이다. 4.8에서 짧아서 캐싱이 안 걸리던 프롬프트가 코드 변경 없이 캐싱 대상이 된다.

주의할 건 미달 시 에러가 없다는 점이다. cache_control을 붙여도 조용히 캐싱되지 않고, 응답의 cache_creation_input_tokens와 cache_read_input_tokens가 둘 다 0인 것으로만 확인할 수 있다.

무효화 계층 — 전부 날아가는 게 아니라 단계가 있다. 게이트웨이 설계에서 이 표가 핵심이다.

바뀐 것tools 캐시system 캐시messages 캐시
툴 정의 추가·삭제·순서 변경무효무효무효
모델 변경무효무효무효

즉 모델 라우팅을 대화 중간에 바꾸면 캐시가 통째로 날아간다. 툴 목록도 요청마다 동적으로 만들면 안 되고, 이름순 정렬 같은 결정적 직렬화가 필요하다. 렌더 순서가 tools → system → messages라, 앞쪽일수록 파괴력이 크다.

05 Bedrock · Foundry 가용성

AWS Bedrock — 모델 ID는 anthropic.claude-opus-5. Claude in Amazon Bedrock(Messages 엔드포인트 bedrock-mantle.{region}.api.aws/anthropic/v1/messages) 경유이며, 구 InvokeModel/Converse 통합과는 별개 경로다. 글로벌 엔드포인트 지원(할증 없음), 리전 엔드포인트는 +10%.

  • 지원 — Messages API, 프롬프트 캐싱, thinking, 툴 사용(bash·computer use·memory·text editor), citations, 구조화 출력
  • 미지원 — Files API·URL 소스, 서버사이드 툴(코드실행·웹검색·웹페치), Agent Skills·MCP 커넥터·programmatic tool calling, Batches·Models·Admin API, Managed Agents, 서버사이드 폴백
  • 접근 권한 확인 필요 — 문서상 "모든 Bedrock 고객에게 열려 있는" 목록은 Fable 5 / Opus 4.8 / Sonnet 5 / Opus 4.7 / Haiku 4.5다. Opus 5는 그 목록에 없다 — 콘솔의 model access에서 조건을 확인해야 한다

Microsoft Foundry — model 파라미터에 모델 ID가 아니라 배포(deployment) 이름을 넣는다. 호스팅 옵션이 둘이고 기능 차이가 크다.

호스팅배포 타입제약
Anthropic 호스팅Global Standard기능 제약 적음
Azure 호스팅Global Standard / US Data Zone구조화 출력·서버사이드 툴·MCP·Agent Skills·PTC·Files API가 400

전 배포 공통으로 Admin·Compliance·Models·Batches API, Advisor 툴, Managed Agents, 서버사이드 폴백이 미지원이다. 데이터가 Azure 안에 머무는 대신 기능을 잃는 구조이므로, 규제 요건과 기능 요건을 같은 표에 놓고 결정해야 한다. US Data Zone은 단가에 ×1.1.

게이트웨이 시사점 — Bedrock·Foundry 둘 다 서버사이드 폴백을 지원하지 않는다. 모델 거부 시 다른 모델로 재시도하는 로직은 벤더에 맡길 수 없고 게이트웨이 레이어에서 직접 구현해야 한다.

06 그 밖에

  • effort 기본값은 high (Claude API·Claude Code 기준). low/medium/high/xhigh/max 전 레벨 지원
  • xhigh·max로 돌릴 땐 max_tokens를 크게 — 문서 권고 시작값 64k
  • web fetch 툴 미지원, Priority Tier 미지원
  • 툴 사용 시 고정 오버헤드 — auto/none 286토큰, any/tool 406토큰. 시스템 프롬프트 사용 시 325토큰
