01 워크플로 vs 에이전트 — 핵심 구분

Anthropic은 둘 다 "에이전트형 시스템(agentic systems)"으로 묶되, 아키텍처상 결정적 차이를 둔다:

구분정의성격
워크플로 (Workflow)LLM과 도구가 미리 정해진 코드 경로로 오케스트레이션됨예측 가능·일관성 — 잘 정의된 작업에 적합
에이전트 (Agent)LLM이 스스로 프로세스·도구 사용을 동적으로 지휘, 작업 수행 방식의 통제권을 가짐유연성·모델 주도 판단 — 규모 있는 개방형 문제에 적합

즉 "경로를 사람이 코드로 박았나(워크플로) vs 모델이 런타임에 정하나(에이전트)"가 갈림길.

02 언제 (안) 쓰나 + 프레임워크 경고

  • 가장 단순한 해법부터. 에이전트형 시스템은 지연·비용을 더 나은 성능과 맞바꾼다. 그 트레이드오프가 말이 될 때만 복잡도를 올려라. 많은 경우 단일 LLM 호출 + 검색 + in-context 예시면 충분하다.
  • 워크플로 vs 에이전트 선택. 잘 정의된 작업엔 워크플로(예측 가능), 규모 있는 유연성이 필요하면 에이전트.
  • 프레임워크는 양날의 검. Claude Agent SDK·Strands(AWS)·Rivet·Vellum 등은 시작을 쉽게 하지만, 추상화 레이어가 실제 프롬프트·응답을 가려 디버깅을 어렵게 하고 불필요한 복잡도를 부추긴다. LLM API를 직접 쓰며 시작하고, 프레임워크를 쓰더라도 내부 코드를 이해하라. "내부가 이럴 것"이라는 잘못된 가정이 흔한 에러 원인.

03 빌딩블록 — 증강된 LLM

모든 에이전트형 시스템의 기본 단위는 검색(retrieval)·도구(tools)·메모리(memory)로 증강된 LLM이다. 현 모델은 스스로 검색 쿼리를 만들고, 적절한 도구를 고르고, 무엇을 기억할지 판단한다.

구현에서 중요한 두 가지: ① 능력을 네 유스케이스에 맞게 재단하고, ② LLM에게 쉽고 잘 문서화된 인터페이스를 줄 것. (MCP가 서드파티 도구 생태계 연결의 한 방법.)

04 워크플로 5패턴

단순한 조합부터 점점 복잡해지는 순서. 각 패턴엔 "언제 쓰나"가 명확하다.

패턴구조언제 / 예시
1. 프롬프트 체이닝
Prompt chaining		작업을 순차 단계로 분해, 각 LLM 호출이 앞 출력을 처리. 중간에 게이트(프로그램적 검사) 삽입 가능깔끔히 고정 하위작업으로 쪼개질 때. 지연↔정확도 맞교환. 예: 카피 생성→번역, 개요 작성→검증→본문
2. 라우팅
Routing		입력을 분류해 전문화된 후속 작업으로 보냄(관심사 분리)구분되는 카테고리를 따로 다루는 게 나을 때. 예: 고객문의 유형별 분기, 쉬운 질문→Haiku / 어려운 질문→Sonnet으로 비용·성능 최적화
3. 병렬화
Parallelization		섹셔닝(독립 하위작업 동시 실행) + 투표(같은 작업 여러 번 → 다양한 출력)속도 또는 다관점 신뢰도가 필요할 때. 예: 본응답/유해성 검사 분리, 코드 취약점 여러 프롬프트로 교차 점검, 평가 자동화
4. 오케스트레이터-워커
Orchestrator-workers		중앙 LLM이 동적으로 작업을 쪼개 워커 LLM에 위임하고 결과를 종합하위작업을 미리 예측 못 할 때(병렬화와 달리 사전 정의 아님). 예: 여러 파일 고치는 코딩, 다중 소스 검색
5. 평가자-최적화기
Evaluator-optimizer		한 LLM이 생성, 다른 LLM이 평가·피드백을 루프로 제공명확한 평가기준 + 반복 개선이 가치 있을 때. 예: 문학 번역, 여러 라운드 검색(평가자가 추가검색 여부 결정)

05 에이전트 — 자율 루프

에이전트는 사람의 명령/대화로 시작 → 작업이 명확해지면 독립적으로 계획·실행한다. 핵심은 매 스텝마다 환경에서 "그라운드 트루스(ground truth)"를 얻는 것 — 도구 호출 결과·코드 실행 결과로 진척을 평가하고, 체크포인트나 막힐 때 사람에게 돌아온다.

  • 구현은 의외로 단순. "환경 피드백에 기반해 도구를 루프로 쓰는 LLM"일 뿐. 그래서 도구셋과 그 문서 설계가 결정적이다.
  • 언제 쓰나. 스텝 수를 예측·고정할 수 없는 개방형 문제, 모델 판단을 어느 정도 신뢰할 수 있는 환경. 자율성 = 신뢰된 환경에서 작업을 스케일하는 데 이상적.
  • 대가. 비용↑ + 오류 누적(compounding errors) 위험. → 샌드박스에서 광범위 테스트 + 가드레일 + 정지조건(예: 최대 반복 횟수) 필수.

자사 사례: SWE-bench 코딩 에이전트(PR 설명만으로 실제 GitHub 이슈 해결), computer use 레퍼런스 구현.

06 3대 원칙 + ACI

  1. 단순성(Simplicity). 에이전트 설계를 단순하게 유지.
  2. 투명성(Transparency). 에이전트의 계획 단계를 명시적으로 드러내라.
  3. 잘 만든 ACI(Agent-Computer Interface). 철저한 도구 문서화와 테스트로 에이전트-컴퓨터 인터페이스를 정성껏 설계.
ACI = 모델을 위한 UX. 사람용 인터페이스(HCI)에 쏟는 노력만큼 도구 정의에 투자하라. "주니어 개발자에게 주는 좋은 docstring"처럼 — 예시·엣지케이스·입력형식·도구 간 경계를 명시. 포맷은 모델이 인터넷에서 자연스럽게 본 형태에 가깝게(diff보다 전체 재작성이 쉬울 때가 있음, JSON 안 코드보다 마크다운). 실수 못 하게 인자를 바꾸는 포카요케(poka-yoke). SWE-bench 때 전체 프롬프트보다 도구 최적화에 더 많은 시간을 썼고, 상대경로→절대경로 강제만으로 실수가 사라졌다.

07 우리(OpenClaw/cocy) 스택 매핑

이 글이 특히 유용한 건, 우리가 이미 이 패턴들을 굴리고 있기 때문이다. 용어만 맞추면 우리 도구가 바로 보인다.

원문 패턴우리 스택의 대응
프롬프트 체이닝Workflow 툴의 pipeline() — 단계별 통과, 게이트 검사
병렬화(섹셔닝/투표)parallel() 팬아웃, 그리고 우리가 쓰는 다수결 검증(여러 검토자)
오케스트레이터-워커sessions_spawn/subagents, Workflow의 agent() 동적 위임·종합
평가자-최적화기워크플로의 adversarial verify 단계(생성→독립 검증 루프)
라우팅llm.cocy.io 모델 라우팅 + agents.defaults 폴백(쉬운 건 저비용 모델, 어려운 건 상위 모델)
  • "단순부터, 복잡도는 증명될 때만" = 우리 위임 원칙 그대로. 스펙 명확한 단순 작업은 단일 호출/위임, 3파일 이상 복잡 작업만 harness로 끌어올린다.
  • ACI = 우리 TOOLS.md·스킬 SKILL.md·MCP 스키마. "도구 문서를 주니어용 docstring처럼"은 우리 스킬 작성 규칙과 정확히 같은 말. 우리도 절대경로 강제 같은 포카요케를 이미 쓴다.
  • 투명성 = 우리 위임 계약(Target State / Scope / Done When / Stop Conditions). 계획을 드러내라는 원칙의 운영판.
  • 프레임워크 추상화 경고 = 우리가 무거운 에이전트 프레임워크 대신 CLI·LLM API를 직접 쓰는 이유의 근거.

08 메모

  • 이 글은 Anthropic의 의견 있는 가이드다. "에이전트 = 도구를 루프로 쓰는 LLM일 뿐"이라는 의도적으로 거품을 뺀 framing이 핵심 — 마케팅보다 엔지니어링 관점.
  • 패턴은 처방(prescription)이 아니라 조합용 블록. 성능 측정 → 반복이 유일한 정답이라고 못박는다.
