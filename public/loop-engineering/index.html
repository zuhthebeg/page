cocy.io 엔지니어링 노트 · 실전 적용

루프를 짠다 — 멀티게임 마이그레이션을 감독관의 일로

Addy Osmani의 「Loop Engineering」은 "AI에게 매번 시키지 말고, AI를 시키는 시스템을 짜라"고 말한다. 이 글은 그 6개 부품을 우리가 실제로 쓰는 OpenClaw 프리미티브로 환산하고, 지금 진행 중인 멀티게임 DO+WebSocket 마이그레이션을 loop/goal + "만드는 AI·검사하는 AI 분리"로 설계한 기록이다. 원문 요약이 아니라, 우리 코드베이스에 박을 수 있는 형태로 옮긴 작업이다.

분류 엔지니어링 / 에이전트 운영 대상 relay.cocy.io · game.cocy.io 상태 설계 + 실행준비 작성 2026-06-17

01 받침점이 옮겨갔다

지금까지 우리가 AI를 쓰던 방식은 대화형이었다. 한 줄 시키고, 결과 읽고, 다시 한 줄 시키고. 운전대를 한 번도 놓지 않는 구조다. 루프 엔지니어링은 그 운전대를 시스템에 넘긴다 — 목적과 종료조건만 걸어두면 에이전트가 끝까지 스스로 도는 작업 묶음을 설계하는 것이다.

"Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead." Addy Osmani, Loop Engineering

현실적으로 우리에게 이게 와닿는 이유는 하나다. cocy는 새벽에 많이 자리를 비우고, 13개 게임 멀티를 한 게임씩 손으로 포팅·검증하는 건 며칠짜리 반복노동이다. 이건 "지루하지만 끝없이 반복되는 일" — 원문이 루프의 첫 후보로 꼽은 바로 그 종류다. 단, 받침점이 옮겨갔다는 건 일이 사라졌다는 뜻이 아니다. 실행자에서 감독관으로 자리가 바뀔 뿐이고, 감독관은 더 무거운 자리다.

02 부품 6개 → OpenClaw 환산표

원문의 부품 5개 + 기억장치 1개는 도구 이름만 다를 뿐 OpenClaw에 전부 있다. 자기평가는 후하게 매기지 않으려 한다 — 약점은 약점으로 적었다.

원문 부품OpenClaw 프리미티브우리 현황
① 오토메이션
시작 버튼을 알아서		/loop(주기 반복), create_goal(조건충족까지), cron, heartbeat강함 heartbeat가 이미 서비스 생존·복구·작은 개선을 돌린다

"The agent forgets, the repo doesn't."Addy Osmani

가장 약한 칸은 ⑤다. gostop을 디버깅하는 동안 "만든 사람이 자기 결과를 검증"하는 구조였고, 그래서 캐시/버전 혼동을 몇 번 겪었다. 원문이 측정으로 못 박은 self-bias(자기 글 9.04 vs 독립 채점 7.43, 1.6점 격차)가 우리에게도 그대로 적용된다. 이번 설계의 핵심은 이 칸을 채우는 것이다.

03 우리 루프 한 바퀴 — 발견→분류→수정→검증

멀티 마이그레이션을 한 바퀴로 압축하면 이렇게 된다. 이건 추상이 아니라 이미 절반은 도는 부품들을 엮은 것이다(테스트·플레이북·배포 스크립트는 존재함).

# 상태 파일: games-server/docs/loop-migration-plan.md (백로그 테이블)
[goal] 전 멀티게임을 DO+WS로 이관 · 게임마다 2계층 테스트 통과 + 리뷰어 승인

loop(다음 게임 1개):
  발견  ── 백로그에서 status=todo 게임 1개 집기
  분류  ── 플레이북 체크리스트로 작업범위 산출(렌더러/인터랙션/juice)
  수정  ── [Maker = Claude] 포팅 + Layer1·2 테스트 추가
          └ npm test 통과할 때까지
  검증  ── [Reviewer = 다른 에이전트] 플레이북·싱글 패리티 기준 독립 검토
          └ pass → status=done, 상태파일 갱신, 다음 게임
          └ fail → 지적사항 적어 Maker로 되돌림 (한 바퀴 더)
  보고  ── 사람(cocy) 수신함에는 "리뷰까지 통과한 것"만 올린다

여기서 ②워크트리는 동시에 여러 게임을 돌릴 때만 켠다. 한 게임씩이면 파일이 갈려 불필요하다 — 원문도 "검토 여력이 동시 실행 대수를 정한다"고 했고, 나 혼자 검토하는 지금은 1~2개가 상한이다.

04 만드는 AI ≠ 검사하는 AI

cocy가 직접 요구한 부분이다 — "네가 작업한 걸 다른 에이전트한테 시켜서 검토하는 체계". 원문의 Writer↔Evaluator↔Critic 분리를 우리 규모에 맞게 축소한다.

[작업]  Maker (Claude/Opus)  ── 포팅 + 테스트 작성 + 자가 npm test
   │
   ▼
[검토]  Reviewer (다른 모델·읽기전용 지시문)
        ├ 입력: diff + 플레이북 체크리스트 + 싱글 동작 스펙
        ├ 본다: 턴 모델 패리티 / 사운드·애니 계약 / 전역충돌 / 캐시버스트 / 테스트 실재성
        └ 출력: {verdict: pass|fail, 지적[], 놓친것[]}  ← 구조화
   │
   ▼
[판정]  fail이면 Maker로 되돌림 · pass면 사람에게 "검토통과" 보고만
왜 다른 에이전트인가

같은 모델이 자기 결과를 채점하면 후하게 준다(측정된 1.6점 격차). 그래서 Reviewer는 가능하면 다른 계열 모델(gemini / gpt)로 두고, 같은 계열이면 'self-bias 경고'를 강제로 단다. Reviewer는 코드를 고치지 않는다 — 오직 지적만 한다. 고치는 책임과 검사하는 책임을 일부러 가른다.

리뷰어의 강도도 역할에 맞춘다. 빠른 패리티 점검은 가벼운 모델로, 보안·결제·지갑 정산이 얽힌 변경은 강한 모델 + 깊은 추론으로. gostop의 shared-wallet 정산 같은 건 후자다.

05 세 작업의 실행준비

A. 멀티 아키텍처 마이그레이션 (공용 트랜스포트 승격)

gostop은 지금 인라인 69줄 ?relay=do 훅으로 DO+WS에 붙어 있다(공용 multiplayer.js는 REST에 하드와이어). 검증된 이 훅을 lib/multiplayer.js 내부로 승격하고 공개 콜백 시그니처를 유지하면, 게임 코드는 0수정으로 WS를 탄다. 선행조건 gostop이 레퍼런스로 깨끗해야 함 — 현재 do-v7까지 안정화 진행 중.

B. 게임별 포팅

플레이북 체크리스트(uid 영속 / 닉네임 / 이벤트→juice / fly 애니 / 잔여 UI / 결과창 / 2계층 테스트 / 전역충돌 / 캐시버스트)를 게임마다 loop로 돌린다. 거래가 얽힌 게임(pingtan·catan)은 TRADE_ACCEPT 서버권위 승격이 추가로 필요 — 백로그에 별도 플래그로 표시.

C. 멀티 대기실 리디자인

현재 대기실은 PoC 수준(방코드 + 시작 버튼 + 접속자 수). 리디자인 방향: 방 목록/빠른매칭, 좌석·준비 상태, 재대국 버튼(서버 방 리셋은 좀비방 리셋으로 이미 절반 구현), 관전 진입. 이건 loop보다 설계 우선 항목이라, 와이어프레임 → 단일 게임 적용 → 공용화 순으로 분리한다.

06 냉정하게 — 루프는 사람을 빼주지 않는다

원문이 가장 힘줘 못 박은 부분이고, 우리에게도 그대로다.

  • 검증은 사람 몫. 오디오·애니 "체감", 실제 멀티 플레이감은 테스트로 100% 못 잡는다. 리뷰어 에이전트도 사람의 한 판 플레이를 대체하지 못한다 — cocy의 실기기 확인이 마지막 게이트다.
  • 이해도는 노력해야 유지된다. 루프가 코드를 빨리 뽑을수록, 내가 무슨 코드를 들고 있는지 읽지 않으면 모르게 된다. gostop의 서버/싱글 턴 모델이 갈라져 있던 걸 늦게 안 게 그 증거다.
  • 가장 큰 위험은 인지적 항복. "루프는 그 차이를 모른다. 사람은 안다." 같은 루프라도 이해를 더 빨리 하려고 쓰는 사람과, 이해를 피하려 쓰는 사람의 결과는 정반대로 갈린다.
우리에게 주는 결론
루프는 짠다. 단, 검증 게이트(테스트 + 리뷰어 + 사람 한 판)를 빼지 않는 선에서. gostop을 레퍼런스로 깨끗이 박은 뒤 → 공용 승격 → 게임별 포팅 loop를 돌린다.
