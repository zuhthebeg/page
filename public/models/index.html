프론티어 모델 인터페이스 지도

API로 프론티어 모델을 붙이는 사람을 위한 정본. 인터페이스는 파라미터를 평준화하려 하고, 모델은 파라미터를 없애는 방향으로 간다. 그 간극이 게이트웨이를 운영할 때 실제로 발생하는 작업량이다. 여기서는 인터페이스 계열이 어떻게 갈라져 있는지, 파라미터가 어떤 방향으로 바뀌는지, 툴콜링·MCP 스펙이 어디로 가는지, 플랫폼별로 무엇을 잃는지를 정리하고 모델별 상세로 연결한다.

01 인터페이스는 네 갈래다

2026년 현재 프론티어 모델을 호출하는 방식은 크게 네 계열로 갈린다. 같은 모델이라도 어느 계열로 붙느냐에 따라 요청 바디 모양·상태 관리·쓸 수 있는 기능이 전부 달라진다.

Messages

Anthropic 1P · Claude Platform on AWS · Bedrock(Mantle) · Foundry · Vertex
{ model, max_tokens, system, messages[], tools[], thinking:{type:"adaptive"}, output_config:{ effort, format } }

system이 messages 밖에 top-level로 나와 있는 게 특징. 사고량은 thinking과 output_config.effort로 제어하고, 샘플링 파라미터는 최신 모델에서 아예 거부된다.

Chat Completions

OpenAI · 그리고 사실상의 업계 호환 규격(vLLM·Ollama·대부분의 게이트웨이)
{ model, messages[{role,content}], tools[], temperature, top_p, max_tokens }

가장 널리 복제된 형태. system도 messages 배열 안의 한 role이다. 대화 상태는 클라이언트가 전부 다시 보내야 한다. OpenAI 본가에서는 유지는 되지만 신규 프로젝트에는 Responses를 권장한다.

Responses

OpenAI (신규 프로젝트 권장)
{ model, instructions, input, store:true, previous_response_id }

messages 대신 instructions + input으로 쪼갰고, store:true로 서버가 대화 상태를 들고 간다. 후속 요청은 previous_response_id로 이어 붙인다. 출력은 텍스트뿐 아니라 추론(reasoning)·툴 호출이 타입 있는 항목으로 나온다.

Converse / InvokeModel

Amazon Bedrock (벤더 중립 추상화 계층)
{ modelId, messages[], system[], toolConfig, inferenceConfig:{ maxTokens, temperature, topP, stopSequences }, additionalModelRequestFields:{ ... } }

"코드를 한 번 쓰고 여러 모델에 쓴다"가 설계 목표. 그래서 공통 파라미터를 inferenceConfig에 고정 스키마로 박아뒀다. 모델 고유 파라미터는 additionalModelRequestFields라는 탈출구로 넘긴다.

혼동 주의 — "Bedrock에 붙는다"는 말은 이제 두 가지를 뜻한다. ① 기존 InvokeModel/Converse(ARN 버전 모델 ID) ② Claude in Amazon Bedrock의 Messages 엔드포인트 bedrock-mantle.{region}.api.aws/anthropic/v1/messages — 후자는 1P와 요청 바디가 동일하다. SDK 클라이언트도 서로 다르다.

02 파라미터는 사라지는 방향으로 간다

지난 2년간 추가된 파라미터보다 제거된 파라미터가 더 중요하다. 추론(reasoning) 모델이 주류가 되면서, "출력 분포를 직접 흔드는" 손잡이가 "얼마나 생각할지를 지정하는" 손잡이로 대체됐다.

과거현재비고
temperature / top_p / top_kClaude Opus 4.7 이후 전송 시 400프롬프트로 대체. OpenAI 추론 모델도 temperature를 받지 않는 방향
thinking.budget_tokens (사고 토큰 상한)thinking:{type:"adaptive"}모델이 사안별로 사고량을 정한다. 고정 예산 개념 폐기
—output_config.effort
low / medium / high / xhigh / max		사고 깊이 + 전체 토큰 지출을 함께 조절. OpenAI 계열의 reasoning_effort와 같은 계보
assistant 프리필(마지막 턴 선입력)400 — 구조화 출력으로 대체output_config.format의 JSON Schema 사용
클라이언트가 대화 전체 재전송서버 상태 보존OpenAI store/previous_response_id, Anthropic 서버측 compaction

방향성은 명확하다. "모델이 무엇을 출력할지"를 숫자로 조종하던 시대에서, "얼마나 노력할지"를 지정하고 나머지는 모델에 맡기는 시대로 넘어가고 있다. 창의성 편차가 필요해서 temperature를 쓰던 용례는 이제 프롬프트로 옮겨야 한다.

03 여기서 실무 사고가 난다

공통 인터페이스는 파라미터를 평준화하려 하고, 프론티어 모델은 파라미터를 제거하려 한다. 이 둘이 정면으로 부딪히는 지점이 있다.

  • Converse의 inferenceConfig에는 temperature와 topP가 여전히 1급 필드다. 스키마상 넣을 수 있게 생겼다. 그런데 최신 Claude 모델에 그대로 흘리면 거부된다. 추상화 계층의 스키마가 모델의 파라미터 축소를 아직 따라오지 못한 상태다.
  • 새 기능은 공통 스키마에 자리가 없다. thinking, effort 같은 최신 제어는 Converse의 고정 필드에 없어서 additionalModelRequestFields로 우회해야 한다. 즉 "한 번 쓰고 여러 모델에" 라는 약속이 최신 모델에서 가장 먼저 깨진다.
  • 게이트웨이가 기본값을 채워 넣으면 그게 폭탄이 된다. 프론트에서 안 보냈어도 게이트웨이가 temperature: 0.7을 관례적으로 주입하면, 구모델에선 잘 돌던 요청이 신모델로 라우팅되는 순간 400이 된다. 파라미터 주입 로직부터 감사할 것.
  • 모델 교체가 캐시를 파괴한다. 프롬프트 캐시는 모델 단위로 분리된다. 게이트웨이가 요청마다 모델을 갈아끼우거나 툴 목록을 동적으로 만들면 캐시 적중률이 0에 수렴한다. 라우팅 안정성이 곧 비용이다.

04 툴콜링 — 개념은 하나, 표기는 넷

어느 인터페이스든 툴콜링 루프는 같다. 모델이 호출 의사를 밝히고 → 클라이언트가 실행하고 → 결과를 되돌려준다. 다른 것은 표기뿐인데, 게이트웨이에서 사고가 나는 곳이 정확히 이 표기 차이다.

계열툴 정의호출(모델→)결과(→모델)
Messagestools[{name, input_schema}]content 안 tool_use 블록 — 입력이 구조화 객체role:"user" 안 tool_result 블록
Chat Completionstools[{type:"function", function:{parameters}}]tool_calls[] — arguments가 JSON "문자열"role:"tool" 메시지
Responses평탄화된 function 툴 + 호스티드 툴(web_search·mcp 등)function_call 항목function_call_output 항목
ConversetoolConfig.tools[{toolSpec:{inputSchema:{json}}}]toolUse 블록(구조화)toolResult 블록
  • 문자열 vs 객체 — 변환 사고 1순위. Chat Completions만 arguments가 JSON 문자열이고 나머지는 구조화 객체다. 계열 간 변환하는 게이트웨이에서 이중 직렬화("{\"q\":...}"를 또 감싸기)나 파싱 누락이 가장 흔한 버그다.
  • tool_choice 어휘가 계열마다 다르다. Messages는 auto/any/tool, OpenAI 계열은 auto/required/함수 지정, Converse는 toolChoice. "아무 툴이나 반드시 호출"을 옮길 때 any↔required 매핑을 빼먹기 쉽다.
  • 병렬 호출이 기본이다. 최신 모델은 한 턴에 툴을 여러 개 호출한다. 결과는 호출 id별로 전부 돌려줘야 다음 턴이 진행된다 — 하나만 돌려주고 멈추는 구현이 의외로 많다.
  • 툴 정의는 프롬프트 맨 앞에 렌더된다. 즉 툴 목록이 요청마다 흔들리면 아래 캐싱 섹션의 규칙대로 캐시 전체가 무효가 된다. 툴 스키마는 정적으로 고정할 것.

04b MCP — 스펙이 통째로 바뀌었다 (2026-07-28)

툴콜링이 "모델↔클라이언트" 계약이라면, MCP는 그 바깥쪽 "클라이언트(호스트)↔툴 서버" 계약이다. 2026-07-28 개정판은 메인테이너 스스로 "출시 이후 최대 개정"이라 부르는 판갈이다.

영역변경의미
상태(state)initialize 핸드셰이크·Mcp-Session-Id 폐지. 요청마다 _meta에 버전·클라이언트 정보를 자기 기술. 사전 조회는 선택적 server/discoverMCP 서버가 일반 HTTP 워크로드가 된다 — 라운드로빈 LB·수평 확장에 sticky session 불필요
라우팅Mcp-Method·Mcp-Name HTTP 헤더 필수게이트웨이·WAF가 바디 파싱 없이 헤더로 라우팅·인가·과금
서버발 요청elicitation·sampling의 역방향 스트림 대신 MRTR: 서버가 resultType:"input_required"로 질문을 돌려주고, 클라이언트가 답을 붙여 재시도상시 열린 양방향 연결 없이 "실행 중 사용자 확인" 구현 가능

확장확장 프레임워크 공식화 — Tasks(장기 작업)·MCP Apps·EMA(엔터프라이즈 인가, stable)코어는 가볍게, 부가 기능은 확장으로 분리

폐기Roots·Sampling·Logging, 구 HTTP+SSE 전송 — 최소 12개월 유예신규 구현에서 쓰지 말 것. 공식 폐기 정책도 이번에 도입
  • 세션에 숨겨두던 상태는 툴이 명시적 핸들로. 스펙 권고: 상태가 필요하면 툴이 핸들을 발급하고 모델이 인자로 되넘기게 하라. 모델이 상태를 "볼 수 있어야" 툴 간에 이어 쓸 수 있다.
  • API 쪽 연결 통로는 이미 있다. Anthropic Messages API는 MCP 커넥터(beta 헤더 mcp-client-2025-11-20, mcp_servers + mcp_toolset)로 원격 MCP 서버를 클라이언트 구현 없이 붙인다 — 단 툴 호출만 지원, HTTP 노출 서버만, Bedrock·Vertex에서는 미지원. OpenAI는 Responses의 호스티드 mcp 툴이 같은 역할.
  • 서버 구현자라면 마이그레이션 계획을 세울 시점. 구 전송·세션 의존 코드는 12개월 유예 안에 정리해야 한다. TS·Python·Go·C# 공식 SDK는 신 스펙을 당일 지원, Rust는 베타.

06 비용을 줄이는 곳은 캐싱 하나다

모델 단가는 협상 대상이 아니지만 캐시 적중률은 설계 대상이다. 프롬프트 캐싱은 접두사(prefix) 일치로 동작한다 — 앞쪽이 1바이트만 달라도 뒤가 전부 무효다.

동작기본 입력 대비손익분기
캐시 읽기 (히트)0.1×—
5분 캐시 쓰기1.25×요청 2회면 이득
1시간 캐시 쓰기2×요청 3회면 이득

조용히 캐시를 깨는 것들 — 코드 리뷰에서 이것만 봐도 대부분 잡힌다.

  • 시스템 프롬프트 안의 datetime.now()·UUID·요청 ID — 매 요청 접두사가 달라진다
  • JSON 직렬화 시 키 정렬 누락. Go·Swift는 맵 키 순서가 무작위라 툴 정의 캐시가 깨진다
  • 유저·세션 ID를 시스템 프롬프트에 보간 — 유저 수만큼 캐시가 쪼개진다
  • 요청마다 툴 목록을 동적 생성 — 툴은 렌더 순서상 맨 앞이라 전체가 무효
  • 동시 요청 팬아웃 — 캐시는 첫 응답이 스트리밍되기 시작해야 읽힌다. 병렬로 N개 쏘면 전부 미스

캐시 최소 길이 미달이면 에러 없이 조용히 캐싱되지 않는다. 응답의 cache_creation_input_tokens와 cache_read_input_tokens가 둘 다 0인지로만 확인할 수 있다.
