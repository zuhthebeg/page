01 핵심 아이디어

검색 에이전트는 보통 점점 길어지는 대화 기록(transcript) 전체를 정책(모델)이 들고 다닌다. 무엇을 검색할지뿐 아니라 — 뭘 봤는지, 어떤 근거가 쓸모 있는지, 어떤 조건이 아직 안 풀렸는지, 어떤 주장을 실제로 검증했는지까지 — 전부 모델 머릿속에서 관리한다.

저자들의 주장: 이건 강화학습(RL)에 과부하다. RL이 "의미 있는 검색 결정"과 "환경이 더 안정적으로 관리할 수 있는 단순 기록(bookkeeping)"을 동시에 최적화하도록 강요받는다. 보상도 흐려진다 — 최종 결과가 비거나 틀리면, 그게 검색 실패인지·증거를 잊은 건지·검증을 안 한 건지 구분이 안 된다.

해법: 회수 가능한 상태(state)는 환경 쪽 하니스가 관리하고, 정책은 의미 판단만 남긴다 — 무엇을 검색·보존·폐기·검증할지, 그리고 언제 멈출지.

02 하니스가 관리하는 것 (환경 측 작업기억)

구성요소역할
후보 풀 (candidate pool)검색으로 만난 문서 적재. 검색 관측은 압축·중복제거 후 정책에 도달(청크ID + 내용 지문)
큐레이션 셋 (curated set)중요도 태그 부착, 상한 30개·중요도 기반 퇴출. 정책이 add/remove/promote/demote
증거 링크 (evidence graph)문서 간 교차 연결을 요약 — 전체 기록 재독 없이 근거 다리 파악
검증 기록 (verification)정책이 쓴 주장을 저장 문서 텍스트에 대조해 yes/no 기계적 지지 검사
예산 인지 렌더링컨텍스트 예산에 맞춰 작업기억을 요약 렌더 — 같은 렌더러를 교사데이터·SFT·RL·평가에 공통 사용

정책 행동은 search / curate(add·remove·중요도태그) / verify / review-docs(저장 문서 재열람) 로 좁혀진다. 나머지는 환경이 처리.

03 학습 레시피

  • 베이스 모델 — gpt-oss-20b (오픈 20B).
  • 파이프라인 — 교사 롤아웃 → SFT 재생(필터 후 899 궤적) → CISPO RL. RL은 SEC(금융) 데이터에서만 최적화(128 배치 × 8 롤아웃, 온도 1.0, 40턴 상한).
  • 보상 설계 — Fβ(β=2, recall 가중) 기반: 궤적 recall + 큐레이션 최종답 recall + 궤적 답 recall + 도구 다양성 + 답 발견 보너스 − 턴 패널티 − "찾고도 안 올린" 답-누락 패널티. 발견(어디서든 찾음)과 선택(최종 셋에 올림)을 분리해 보상.
  • 일반화 설계 — SFT는 4개 계열(BC+·Web·Patents·SEC), RL은 SEC만. 나머지 4개(LongSeal·Seal0·FRAMES·HotpotQA)는 학습에 안 쓴 held-out 전이 벤치.

06 우리에게 주는 시사점

이 논문의 메시지는 에이전트를 직접 굴리는 입장(예: 우리 openclaw 스택)에 바로 꽂힌다.

  • "컨텍스트를 압축"하기 전에 "상태를 빼내라". 앞서 우리가 평가한 Headroom(토큰 압축)은 길어진 기록을 줄이는 접근이었다. Harness-1은 한 발 더 가서, 애초에 모델이 기록을 들지 않도록 상태를 환경에 둔다 — 압축의 상위호환 설계.
  • 작은 모델 + 좋은 하니스 ≈ 프런티어. 20B가 GPT-5.4를 검색 recall에서 앞선 건, 능력의 상당 부분이 모델이 아니라 하니스/스캐폴딩에 있다는 실증. 비용·한국어 토큰 페널티까지 고려하면(관련 보고서) 자체 하니스 투자의 ROI가 크다.
  • 검증을 환경이 강제. "정책이 쓴 주장 → 저장 문서에 기계적 대조(yes/no)"는 에이전트 환각 억제에 그대로 차용 가능한 패턴.

07 유의점

  • RL 최적화는 SEC(금융) 단일 도메인에서만 — 전이 성능이 강하긴 하나, 도메인 편향 가능성은 남는다.
  • 지표가 recall 중심(정밀도/F1은 보조). 검색 에이전트 특성상 합리적이나, 큐레이션 셋 크기가 인터페이스의 일부라는 점은 감안.
  • 이건 검색(retrieval) 서브에이전트 평가 — 최종 답변 생성 품질은 별도(큐레이션 셋을 frozen 생성기에 넘겨 측정).
