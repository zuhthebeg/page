하나의 프롬프트, 여러 개의 뇌:
멀티모델 라우팅을 어떻게 지휘할 것인가

"제일 좋은 모델 하나만 쓰면 되지"는 데모의 사고방식이다. 프로덕션에서 라우팅은 비용·품질·역량·가용성·데이터 경계를 매 요청마다 협상하는 컨트롤 플레인의 핵심 결정이다. 전략을 분류하고, 각 전략이 무엇을 사고 무엇을 파는지, 그리고 우리 게이트웨이를 어디로 끌어올릴지 정리한다.

작성 cocy — LLM Gateway / Platform 일자 2026-08-29 범위 라우팅 설계 원리 + 우리 스택 적용

오늘 우리 파이프라인에서 fable 경로가 조용히 죽었다. 코드는 그대로였다. Anthropic이 Fable 5를 구독 포함에서 별도 usage-credit 유료 모델로 바꾼 것뿐이다. 모델 하나에 특정 잡을 못박아 두면, 벤더 정책 한 줄이 바뀔 때 그 잡이 통째로 멈춘다. 이게 정확히 라우팅 문제다. 라우팅은 "어느 모델이 제일 똑똑하냐"를 고르는 일이 아니라, 어느 요청을 어느 뇌로 흘려보내고, 그 뇌가 사라졌을 때 어디로 우회할지를 설계하는 일이다.

이 글은 제품 비교가 아니다(그건 별도 검토에서 했다). 여기서는 라우팅이라는 결정 자체를 해부한다 — 무엇을 위해 라우팅하는가, 어떤 전략들이 있고 각각 무엇을 트레이드오프하는가, 라우터를 세우는 비용은 얼마인가, 그리고 우리는 지금 어디에 서 있는가.

01라우팅이 실제로 푸는 문제 — 다섯 개의 축

단일 최강 모델이 답이 아닌 이유는, 요청마다 우선순위가 다르기 때문이다. 라우팅은 아래 다섯 축을 매 요청 단위로 협상한다. 대부분의 잘못된 라우팅은 이 중 하나만 최적화하고 나머지를 잊어서 생긴다.

  1. 비용 — 쉬운 요청에 프론티어 모델을 태우는 건 낭비다. "요약해줘"에 opus를 부르면 haiku 대비 수십 배를 태운다. 라우팅의 가장 흔한 동기.
  2. 품질·역량 — 반대로 어려운 추론·긴 컨텍스트·정밀 코딩은 싼 모델이 못 한다. 라우팅은 필요한 만큼만 센 모델을 쓰는 다이얼이다.
  3. 가용성 — 쿼터 소진, 리전 차단, 벤더 장애, 그리고 오늘처럼 과금정책 변경. 폴백 경로가 없으면 파이프라인이 벤더 상태에 인질로 잡힌다.
  4. 지연·처리량 — 대화형 UI는 첫 토큰 지연이 생명이고, 배치 잡은 총 처리량이 생명이다. 같은 잡도 맥락에 따라 다른 모델이 맞다.
  5. 데이터 경계 — 민감한 요청은 외부 프로바이더로 나가면 안 된다. 로컬/온디바이스로 가두는 것도 라우팅 결정이다.
Frame

라우팅은 "최고의 모델 찾기"가 아니라 "이 요청에 충분한 가장 값싼·가장 안전한 경로 찾기"다. 북극성은 품질이 아니라 품질 제약을 만족하는 최소 비용이다.

02라우팅 전략 분류 — 일곱 가지 패턴

업계에서 실제로 쓰이는 라우팅은 아래 일곱으로 정리된다. 위에서 아래로 갈수록 똑똑해지지만 라우터 자체가 비싸고 불투명해진다. 핵심 축은 두 개다 — 누가 결정하나(사람/규칙/모델), 언제 결정하나(요청 전/생성 중/생성 후).

전략결정 주체·시점강점대가우리 적용
① 명시
manual / model-name		 사람이 요청 전 모델 지정 ● 완전한 예측성·제로 오버헤드 ● 적응 없음, 벤더 변화에 취약 현행 llm.cocy.io alias
② 휴리스틱
rule / heuristic		 규칙이 요청 전(길이·키워드·언어) ● 싸고 투명·디버깅 쉬움 ● 규칙이 현실을 못 따라감 부분 heartbeat=haiku
③ 시맨틱
embedding router		 임베딩이 요청 전 의도 분류 ● LLM 호출 없이 빠른 의도 판정 ● 클러스터 정의·드리프트 관리 없음 vLLM SR 계열
④ 학습 분류기
RouteLLM		 학습된 라우터가 요청 전 난이도 예측 ● 선호데이터 기반 정밀 하향 ● 학습·평가·유지 파이프 필요 없음
⑤ 캐스케이드
model cascade		 싼 모델 먼저 → 생성 후 신뢰도로 승격 ● 평균비용 최저, 품질은 상단 보장 ● 승격 시 지연·중복비용, 신뢰도 판정 난제 유사 Claude→GPT 폴백
⑥ 쿼터 폴백
quota-aware		 가용성이 요청 중 다음 경로로 ● 무중단, 무료티어 스태킹 ● 품질 무관 전환 = 조용한 열화 1단 폴백만 있음
⑦ 믹스처
MoM / MoA		 여러 모델 동시 호출 후 종합 ● 단일 모델 상한 돌파 ● N배 비용·지연, 종합기 품질에 종속 없음 oh-my-hermes 계열

읽는 법: ①~④는 요청 전에 한 번 정하는 "정적" 라우팅, ⑤~⑦은 생성 과정에서 판단하는 "동적" 라우팅이다. 정적은 싸고 예측 가능하지만 요청의 실제 난이도를 모른 채 도박한다. 동적은 실제 결과를 보고 정하지만 그 정보를 사는 데 지연·중복비용을 낸다. 대부분의 성숙한 게이트웨이는 하이브리드다 — 값싼 규칙(②)으로 대다수를 거르고, 애매한 것만 시맨틱(③)이나 캐스케이드(⑤)로 넘긴다.

03결정의 역설 — 라우터도 공짜가 아니다

라우팅 논의가 빠지는 함정: 모델 비용만 계산하고 라우터 비용은 잊는다. 똑똑한 라우터는 세 가지를 청구한다.

  • 결정 비용 — 요청마다 임베딩을 뜨거나(③) 분류기를 돌리거나(④) LLM으로 판단하면, 그 자체가 지연·요금이다. 라우터가 절약한 것보다 더 태우면 순손실이다. 특히 "라우팅을 LLM에게 시키는" 설계는 값싼 요청에 숨은 세금을 붙인다.
  • 오라우팅 비용 — 캐스케이드(⑤)에서 싼 모델이 실패해 승격되면, 우리는 두 번 냈다. 승격률이 높으면 캐스케이드가 오히려 비싸진다. 신뢰도 판정이 틀리면 "싸게 됐지만 답이 틀린" 최악을 산다.
  • 관측 비용 — 동적 라우팅은 "왜 이 요청이 이 모델로 갔나"를 로그로 남기지 않으면 디버깅 불가능하다. 사고 복기가 안 되는 라우터는 프로덕션에 못 올린다. 관측성은 옵션이 아니라 라우팅의 일부다.

그래서 전략 선택의 진짜 질문은 "가장 똑똑한 라우터"가 아니라 "이 트래픽 분포에서, 라우터 비용을 빼고도 남는 순이득이 있는 가장 단순한 라우터"다. 트래픽이 균질하면 명시(①)가 최선이다. 난이도가 크게 갈리고 볼륨이 크면 그제서야 ③~⑤가 본전을 뽑는다.

04레퍼런스 세 개 — 각 전략의 실체

RouteLLM 학습 분류기 ④ lm-sys

방식 선호데이터 학습 라우터목표 강↔약 2모델 분기

인간 선호 데이터로 "이 요청이 강한 모델을 정말 필요로 하는가"를 예측하는 경량 분류기를 학습한다. 벤더 주장: MT-Bench에서 GPT-4 품질의 95%를 유지하며 비용 최대 85%↓. 강점은 정밀한 하향 판정, 대가는 라우터를 학습·평가·재학습하는 ML 파이프라인 자체다. 우리처럼 트래픽이 작고 다양하면 학습 데이터가 안 모여 ROI가 안 난다.

OmniRoute 계열 쿼터 폴백 ⑥ gateway

방식 가용성 기반 자동 폴백초점 무료티어 스태킹

"어느 모델이 맞나"가 아니라 "어느 경로가 지금 열려 있나"를 푸는 계열. 쿼터 소진 시 재로그인 없이 다음 프로바이더로 넘긴다. 개발 생산성·비용엔 강하지만, 품질을 무시한 전환은 조용한 열화를 만든다 — 폴백된 모델이 더 나쁜 답을 줘도 파이프라인은 성공으로 기록한다. 폴백엔 반드시 품질 SLO가 따라와야 한다.

oh-my-hermes 믹스처 ⑦ rlaope · OSS

방식 Mixture-of-Models 라우팅층위 Hermes Agent 하네스

Nous의 Hermes Agent 위에 얹는 오픈소스 하네스. 잡을 모델 카테고리로 분배하고 dispatch별 reasoning effort를 조절하는 MoM 라우팅이 핵심. 아이디어(작업별 모델·추론량 최적화)는 정확히 우리가 손으로 하는 것과 같다. 단, 저자도 결국 "클로드 실행시켜 병합"이라고 프론티어를 다시 부른다 — 믹스처는 상한을 올리지만 값싸지 않다. 하네스 패턴은 훔칠 가치가 있고, 구독을 갈아탈 이유는 없다.

05우리는 지금 어디에 있나 — llm.cocy.io의 정직한 좌표

우리 게이트웨이(Cloudflare Worker + AI Gateway)는 전략 표에서 ①명시 라우팅 + ⑥폴백 1단에 서 있다. 모델 alias로 경로를 나누고(OpenAI 직접 / 구독 CLI / Claude CLI), 실패하면 상위로 한 번 폴백한다. 이건 나쁜 위치가 아니다 — 트래픽이 작고 잡마다 우리가 이미 최적 모델을 알고 있을 때, 명시 라우팅은 가장 싸고 예측 가능한 선택이다.

문제는 오늘 드러났다. 우리 폴백은 "장애"에는 반응하지만 "정책 변경"에는 반응 못 한다. fable은 죽지 않았다 — 크레딧을 요구하며 거절했을 뿐이다. 명시 라우팅에 fable을 박아둔 잡들은 에러도 폴백도 아닌, 조용한 실패로 빠졌다. 이게 ①의 구조적 약점이다: 벤더가 규칙을 바꾸면 명시 라우팅은 그 변화를 알 방법이 없다.

오늘의 교훈

단일 모델에 잡을 못박는 건 암묵적 벤더 결합이다. 최소한의 방어는 "모델"이 아니라 "역할"로 라우팅하는 것 — fable이 아니라 fast-cheap-writer를 지정하고, 그 역할 뒤에 fable→sonnet5→haiku 순서를 두면, 벤더 한 곳이 정책을 바꿔도 역할은 살아남는다.

06우리가 할 것 — 라우팅 성숙도 로드맵

OmniRoute를 통째로 표준화할 이유도, RouteLLM을 학습시킬 트래픽도 우리에겐 없다. 현실적 레버는 명시 라우팅 위에 얇은 정책 층을 얹는 것이다. 우선순위 순서:

지금 역할 기반 alias로 전환. 모델명 직접 지정을 writer / coder / judge / cheap 같은 역할 alias로 감싸고, 각 역할에 우선순위 리스트(primary→fallback)를 매핑한다. 오늘 같은 정책 변경이 역할 하나를 못 죽이게.
지금 폴백을 "거절"까지 확장. 현재 폴백은 5xx·타임아웃만 잡는다. credit-required·rate-limit·리전차단 같은 정상 응답 형태의 거절도 폴백 트리거에 넣는다.
다음 결정 로깅. 요청→선택 역할→실제 모델→폴백 여부를 한 줄 로그로. 관측 없는 라우팅은 못 믿는다. 이게 있어야 다음 단계 판단이 데이터로 선다.
다음 휴리스틱 한 겹(②). 입력 길이·언어·잡 종류로 명백히 싼 요청을 값싼 모델로 자동 하향. 규칙은 10줄이면 되고, 로그가 어디서 돈이 새는지 이미 알려줄 것이다.
나중 캐스케이드(⑤)는 볼륨이 정당화할 때만. 특정 잡의 볼륨이 크고 난이도가 갈릴 때, 그 잡에 한해 싼-모델-먼저 + 신뢰도 승격을 넣는다. 전면 도입이 아니라 국소 적용.

순서가 핵심이다. 똑똑한 라우터부터 짓는 건 거꾸로다 — 역할 추상화와 로깅이 먼저다. 그게 있어야 어디에 지능을 넣을지가 추측이 아니라 측정으로 정해진다.

07결론

Bottom line

라우팅은 "가장 똑똑한 모델 고르기"가 아니라 "역할을 정의하고, 그 뒤에 우회로를 까는" 일이다. 오늘 fable이 우리에게 청구서를 보낸 건, 우리가 모델에 결합돼 있었지 역할에 결합돼 있지 않았다는 증거다. 값비싼 학습 라우터도, 남의 게이트웨이 구독도 우리 답이 아니다. 답은 우리 llm.cocy.io를 모델명을 부르는 얇은 프록시에서, 역할을 부르고 정책으로 우회하는 컨트롤 플레인으로 한 단계 올리는 것 — 그것도 지능이 아니라 추상화와 로깅부터.

단일 최강 모델은 존재하지 않는다. 존재하는 건 이 요청에 충분한 가장 값싸고 안전한 경로와, 그 경로가 사라졌을 때의 다음 경로다. 라우팅을 소유한다는 건 그 지도를 소유한다는 뜻이다.
