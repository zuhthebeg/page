**90일 후 선택:** 검증된 업무만 확대 / 통제를 보완해 재실험 / 기존 자동화로 전환 / 중단. 플랫폼 대규모 선투자나 고객 금융거래 자율 실행을 이번 제안의 출발점으로 삼지 않는다.

## 02. 시대 대응 — 실험을 운영 가능한 능력으로

### 개인의 숙련과 회사의 실행 통제를 분리한다

**[사용자 견해]** 임직원이 Codex·Claude Code 등으로 에이전트에 익숙해지고, 토큰뿐 아니라 로컬 에이전트·로컬 모델·음성 인터페이스도 실험할 필요가 있다. 이는 필요성에 대한 견해이며, 현재 회사의 사용·보급 현황을 확인한 서술이 아니다.

**[제안]** 교육은 “얼마나 사용했는가”가 아니라 “제한된 권한으로 과제를 맡기고 오류를 찾아냈는가”로 평가한다. 공개·합성 데이터로 코드 검토, 문서 근거 확인, 음성 요청의 의도 재확인 등을 실습한다. 음성은 입력 편의 수단이지 인증·승인 대체 수단이 아니다. 원음 보관·전사 오류·주변인 음성 수집도 검토한다. 개인 실험에서 고객정보나 기밀을 외부 서비스에 입력하도록 유도하지 않는다.

### 배치 위치보다 운영 책임을 비교한다

| 선택지 | 적합한 업무 | 반드시 확인할 비용·제약 |
| --- | --- | --- |
| 로컬 에이전트 | 개인 탐색, 개발 초안, 제한된 자료 검토 | 단말 보호, 절전·중단, 권한 회수, 로컬 파일·로그 노출, 모델 품질 |
| 기존 결정적 자동화 | 규칙·입출력이 명확한 계산, 정기 집계, 반복 처리 | 변경 비용, 예외 처리, 기존 스케줄러·승인·감사 기능 재사용 |
| 공용 서버 에이전트 | 여러 사용자가 공유하고 운영자가 지속 실행·복구를 책임지는 업무 | 위임 신원, 격리, 상태·재시도, 중복 실행 방지, 당직·장애·감사 비용 |

**[제안]** 장기·예약·반복이라는 이유만으로 서버를 선택하지 않는다. 동일한 업무의 품질·총비용·운영 가능성을 세 선택지로 비교한다. 모델 API 게이트웨이는 호출·모델·비용을 관리하는 계층이고, 에이전트 플랫폼은 작업 상태·권한·도구 실행·승인·복구까지 관리하는 계층이다. 둘을 같은 제품으로 간주하지 말고 기존 IAM·로그·워크플로·보안 통제를 먼저 재사용한다.

### 최소 공통 통제: 대규모 플랫폼 이전에 갖출 것

**[제안]** 업무 오너가 위험과 완료를 책임지고, 플랫폼 엔지니어링 역할이 실행 환경을 운영한다. 보안·준법·데이터 역할은 독립적으로 허용 범위를 검토한다. 전담 역할·운영 책임은 필요하지만, 팀 규모나 신설 조직을 지금 확정할 근거는 없다.

## 03. 생존 — 신뢰를 고객의 완료 경험으로 전환한다

**[제안]** 카카오뱅크의 차별화 후보는 “대화가 가능한 앱”이 아니라, 고객이 금융 목적을 달성할 때 드는 시간·불확실성·오류를 줄이는 경험이다. 이것이 이미 회사의 강점이거나 전략이라는 주장은 아니다. 검증할 전략적 선택지다.

### 구체적 고객 시나리오

| 고객 의도 | 에이전트가 보조할 범위 | 사람·기존 금융 절차의 경계 | 고객 가치 지표 |
| --- | --- | --- | --- |
| 대출 준비를 빠뜨리지 않고 하고 싶다 | 공개 상품 설명과 제출 항목 안내, 합성 서류의 누락 점검, 진행 단계 설명 | 실제 고객자료 처리·개인화 추천·심사·약정은 별도 검토. 자동 승인·적합성 판단을 전제하지 않는다. | 준비 완료율, 누락 재제출률, 설명 이해도 |
| 이번 달 자금 계획을 이해하고 싶다 | 허용된 범위의 조회·분류와 예상 현금흐름 설명, 조건·가정 표시 | 송금·자동이체 변경·상품 가입은 기존 인증과 명시적 확인. “수익 보장” 금지 | 계획 이해도, 상담 재접촉, 오류 정정률 |
| 의심스러운 연락에 어떻게 대응할지 알고 싶다 | 민감정보 입력을 요구하지 않는 사기 징후 안내, 공식 신고·상담 경로 연결 | 실제 지급정지·신고 처리는 검증된 절차와 담당자에게 인계 | 공식 채널 연결 성공률, 오안내율, 인계 시간 |

**[제안]** 첫 90일의 고객 실험은 공개·합성 데이터로 대출 준비 안내를 검증한다. 실거래, 실제 고객 데이터 연결, 개인화 금융 조언은 다음 단계의 별도 승인 대상이다. 비용 절감을 고객의 대기·재작업 감소로 연결하지 못하면 서비스 확대를 정당화하기 어렵다.

### 앱 밖으로 고객 접점이 이동할 수 있다

**[가설]** 고객이 범용 에이전트에게 금융 목적을 말하고 여러 금융사의 기능을 조합하면, 은행 앱이 모든 여정의 첫 화면이 아닐 수 있다. 현재 보편화됐거나 카카오뱅크가 점유율을 잃고 있다는 사실로 쓰지 않는다.

**[제안]** 두 경로를 병행 검토한다. **자체 에이전트**는 은행 안에서 설명·진행·인계를 일관되게 제공한다. **외부 에이전트 연결**은 허가된 금융 기능을 좁은 범위로 노출하되 외부 모델에 거래 권한을 포괄 위임하지 않는다. 최초 후보는 공개 정보·준비 체크리스트다. 인증된 조회는 별도 권한·법규 검토, 송금·약정 등 쓰기는 더 높은 위험 단계다. 범용 에이전트 연결이 기존 인증·소비자보호 의무를 없애지 않는다.

### 고객과 내부 업무에 공통 적용할 권한 사다리

| 단계 | 행위 | 제안 통제 |
| --- | --- | --- |
| 1. 읽고 설명 | 공개자료 요약·근거 제시 | 출처·최신성·정답 검증, 개인정보 반출 금지 |
| 2. 초안 준비 | 문서·코드·신청 내용 초안 | 제한된 작업 공간, 검토자 지정, 실제 변경 없음 |
| 3. 승인 후 변경 | 제한된 내부 시스템 변경 | 변경 전후 차이, 영향 대상, 정책 검증, 별도 승인, 복구 계획 |
| 4. 고위험 금융 실행 | 송금·약정·심사 등 고객에게 중대한 결과 | 첫 실험 제외. 행위별 법규·인증·책임·보상 검토와 별도 의사결정 |

**[제안]** 의미 있는 승인은 버튼 하나가 아니다. 승인자는 수취인·금액·대상 자료·변경 전후·근거·예외를 확인해야 한다. 실행 직전 승인 대상과 실제 인자가 같은지 검증하고 승인 유효기간을 제한한다. 되돌릴 수 없는 거래는 “롤백 가능”으로 설명하지 말고 취소 가능 구간, 보상 처리, 수동 대응을 구분한다.

## 04. 일하는 방식 — 사용자가 아니라 위임 설계자로

**[제안]** 업무의 단위를 프롬프트에서 **검증 가능한 위임 계약**으로 바꾼다. 목표 / 허용 데이터 / 허용 도구 / 금지 행위 / 시간·비용 상한 / 완료 기준 / 승인자 / 중단·인계 조건을 먼저 정한다.

| 사람의 역할 | 에이전트의 역할 | 완료 증거 |
| --- | --- | --- |
| 오너: 목표·위험·기준 설정 | 계획과 불확실성 제시 | 승인된 과제 범위와 검증 기준 |
| 담당자: 제한된 실행 위임 | 검색·분석·초안·테스트 | 근거 원문, 결과물, 테스트 기록 |
| 검토자: 독립 검증 | 오류 수정, 한계 설명 | 검토 결과와 미해결 이슈 |
| 승인자: 결과·영향 확인 | 승인된 범위만 실행 | 승인 내용과 실제 변경 일치 |
| 운영자: 장애·중단·인계 | 상태 보고와 안전 정지 | 복구 기록과 최종 책임자의 수용 |

**[사실]** 금융위원회 2026-06-18 발표는 06-22 시행 예정 가이드라인의 보조수단성 원칙에서 최종 의사결정과 책임을 임직원이 수행하도록 제시한다.[1] **[제안]** AI를 썼다는 이유로 책임을 에이전트·모델 제공자에게 넘기지 않는다. 자동 평가와 독립적인 사람 검토를 조합하고, 검토자가 결과를 이해할 시간·권한을 확보한다.

### 첫 실험의 내부 업무 두 가지

- **공개 규정 변경 브리핑:** 원문 수집→변경점 초안→출처 대조→담당자 수용. “확인할 수 없음”을 허용하고 법률 판단을 대신하지 않는다. 기존 알림·스크립트와 동일 문서 묶음으로 비교한다.
- **합성 사례 기반 상담 초안:** 가상 고객 질의→허용 답변과 근거→상담 검토자의 수정. 실제 발송 권한 없이 오안내·누락·재작업 시간을 측정한다. 실제 상담기록 연결은 별도 데이터 검토 대상이다.

**[제안]** 교육은 도구 노출만 넓히지 말고 과제별 정답·실패 사례·검토 루브릭을 제공한다. 부서별 챔피언은 실제 위임·검증 사례를 공유한다. 오류를 보고한 직원을 불리하게 평가하면 실패 은폐와 무검토 승인이 늘어날 수 있으므로, 안전한 중단과 오류 발견을 학습 성과로 인정한다.

## 07. 위험·변경 거버넌스 — 속도와 보수성을 함께 설계한다

**[제안]** 인터넷은행은 디지털 채널의 고객 경험과 장애·사고 대응이 밀접하므로, 고위험 행동에는 보수적 경계를 적용하되 읽기·초안 업무까지 일괄 금지하는 방식은 피한다. 손실을 제한할 수 있는 작은 실험을 빠르게 반복한다.

- **정보 유출·권한 오용:** 업무별 격리, 명시적 반출 정책, 위임 신원, 최소 도구·조회 범위. 로컬 실행도 같은 원칙 적용.
- **그럴듯한 오류·부적절한 추천:** 원문 근거, 정확성·소비자보호 평가, 불확실성 표시와 담당자 인계. 자동 심사·개인화 추천은 별도 검토.
- **승인 피로·고무도장 승인:** 위험별 승인 차등화, 실제 변경 요약, 검토 시간·책임 확보, 승인 대상과 실행 대상의 결합.
- **모델·도구·정책 변경:** 버전 고정, 회귀평가, 제한 배포, 재승인 조건, 이전 버전 복귀·수동 처리 경로. 도구 권한 확대는 단순 모델 교체보다 별도 검토.
- **벤더 종속·비용 폭증:** 모델 교체 시험, 예산 상한, 공급자 장애 시 안전 정지. 공통 인터페이스를 유지하되 대체 모델의 동등 품질을 가정하지 않음.
- **중단 조건:** 데이터 반출 의심, 승인 없는 쓰기, 권한 경계 실패, 중대 오안내, 감사 누락 발견 시 즉시 정지·보전·조사·담당 조직 인계. 신고·고객 통지 의무는 해당 규정과 사고 유형에 따라 별도 판단.

**[사실]** NIST AI RMF는 자발적 위험관리 프레임워크이고, 공식 페이지는 생성형 AI Profile의 2024-07-26 공개도 안내한다.[4] **[제안]** 과제마다 위험 오너·평가·감시·중단의 기록을 유지한다. 해외 프레임워크를 국내 준법 판단의 대체물로 쓰지 않는다.

### 규제는 “AI 허용” 한 문장으로 정리되지 않는다

**[사실]** 금융위원회 2026-06-18 발표는 06-22 시행 가이드라인의 7대 원칙(거버넌스·합법성·보조수단성·신뢰성·금융안정성·신의성실·보안성)을 제시하고 자율규제로 설명한다. 고영향 AI 등 별도 법률 해당 시 법적 의무 확인이 필요하다고 명시한다.[1] 2024-08-13 망분리 개선 로드맵은 보안 조건을 수반한 단계적 특례와 제도 개선 계획이다.[2] 이를 2026년 현재 모든 연결·데이터 처리가 일괄 허용됐다는 근거로 사용하지 않는다. 2025-12 발표의 개정안·시행 계획은 현재 가이드라인 대신 적용하지 않는다.[3]

**[제안·확인 항목]** 실행 전 준법·보안·개인정보 담당이 최신 법령·감독규정, 해당 업무의 특례·지정 조건을 확인한다. 특히 개인정보·개인신용정보의 목적·동의·처리 위탁·국외 이전, 망분리·외부 통신, 클라우드·제3자 위탁, 접근매체·전자금융거래 인증, 금융소비자보호, 기록 보존·통지, 고영향 AI 해당 여부를 검토한다. 본 보고서는 개별 업무의 허용 여부를 판단하는 법률 검토를 대체하지 않는다.

## 08. 결론 — 플랫폼이 아니라 검증된 업무로 시작한다

**[제안]** 원문의 문제의식은 타당하다. 다만 “회사 서버 에이전트가 필요하다”를 최종 결론으로 삼지 않는다. **고객의 의도를 더 잘 완결하고, 사람이 더 정확하게 위임·검증하며, 회사가 권한과 사고 책임을 통제할 수 있는가**가 결론의 기준이다.

임원 미팅에서는 세 가지를 논의할 수 있다. **①** 실데이터·실거래 없이 시작할 90일 과제와 오너, **②** 품질·안전·총비용 기준 및 중단 권한, **③** 검증 후에만 운영 범위와 플랫폼 투자를 늘리는 단계별 의사결정. 이 순서라면 보안은 혁신의 반대가 아니라 반복 가능한 혁신의 기반이 된다.
