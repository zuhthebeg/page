01 / 2,300개는 모델만의 숫자가 아니다

Elliot Padfield의 2026-10-15 X 글(09:59 KST)은 “모델·재질·조명 환경 2,300개 이상, $0, API 키 불필요, 상업 이용 가능”이라고 소개했다. 읽기 전용 미러로도 본문과 게시 시각을 확인했다. 원문의 어색하게 붙은 외부 주소 대신 공식 Poly Haven과 공식 API를 기준으로 검증했다.

20:22 KST의 GET /assets 응답은 총 2,387개였다. 반환된 고유 ID를 세었고, 집계 시각보다 미래의 date_published 항목은 없었다. 개별 다운로드 파일 수가 아니라 에셋 항목 수다.

따라서 게시물의 “2,300+”는 확인 시점 기준 맞지만 3D 모델 2,300개라는 해석은 틀리다. 한 항목의 1K·2K·8K 파일과 PNG·JPG·EXR 변형을 별도 에셋으로 더하지 않았다. 숫자는 추가 공개에 따라 달라진다.

API는 목록과 다운로드 URL을 제공하는 데이터 통로다. AI가 Blender 장면을 수정하려면 별도로 Blender 실행 환경과 연결 도구·파일 권한이 필요하다. API 주소 하나가 그 연결을 설치해 주지는 않는다. 원문의 예시인 소프트박스 스튜디오 조명은 아래 Studio Small 09에서 실제로 찾았다.

02 / “무료”를 세 겹으로 나눠 읽기

에셋 자체: CC0

공식 라이선스는 HDRI·텍스처·3D 모델 전체를 CC0로 명시한다. 상업 이용, 수정, 재배포와 판매 제품 포함이 가능하고 저작자 표시도 의무가 아니다.

다운로드해 게임에 포함하거나 자체 호스팅한 에셋에 API의 출처표시 의무가 새로 붙는 것은 아니다.

라이브 API: 별도 서비스 약관

현행 API 약관 2.1–2.3은 개인·기업 모두 상업 목적까지 무료, 기본 접근의 유료 라이선스·키 요구 없음을 명시한다. 상업 서비스라는 이유만으로 유료 티어가 필요한 구조가 아니다.

대신 앱을 식별할 User-Agent 또는 Referer가 필요하다(2.4). 라이브 API로 콘텐츠를 사용자에게 보여 주는 제품은 Poly Haven 출처를 분명히 밝혀야 한다(2.5). 공식 제휴·보증처럼 보이면 안 된다.

  • 사이트 HTML 수집과 API를 혼동하지 말 것. 웹사이트 약관은 허가 없는 웹 스크래핑·데이터 마이닝을 금지한다. 공식 llms.txt도 목록·메타데이터·파일 URL은 API를 쓰도록 안내한다.
  • 정해진 무제한 처리량은 확인되지 않았다. 확인한 API 약관·문서에는 숫자로 된 고정 rate limit이 없지만, 서비스 성능을 저하시키는 사용은 금지되고 SLA도 없다. 캐시·필요한 항목만 요청·429 발생 시 Retry-After 존중과 백오프를 운영 방침으로 권한다. 이는 공개된 “분당 N회 보장”이 아니다.
  • 벌크는 무조건 금지가 아니다. 공식 API 소개는 연구용 벌크 다운로드도 활용 예로 든다. 그렇다고 무제한 병렬 요청 허가나 가용성 보장은 아니다. 이번에는 파일 목록만 확인했고 본체 다운로드는 하지 않았다. 기업용 Bulk Snapshot·직접 후원은 선택 사항이다.
  • CC0가 사이트의 모든 것을 뜻하지 않는다. 로고, 사용자 아바타, 예시 렌더, 사용자 렌더와 글은 별도 보호 대상이다. 이 글도 사이트 썸네일을 CC0 에셋인 것처럼 복제하지 않았다.
  • 개인정보와 권리의 경계. 개인정보 방침은 쿠키 동의 후 UUID·다운로드 설정 기록 등을 설명한다. 계정 가입은 이번 API 조회에 필요하지 않았다. CC0는 상표·인물 초상 등 모든 제3자 권리를 보증하는 문서가 아니므로 실제 출시물의 맥락은 별도 검토한다(CC0 설명).

파일 목록을 읽을 때 놓치기 쉬운 것

/assets에서 ID와 종류를 고른 뒤 필요한 5개의 /files/{id}만 확인했다. 각 항목에는 URL·바이트 크기·MD5가 있고, 모델·재질 파일에는 include 의존 목록이 있다. glTF를 GLB 단일파일이라고 단정하지 말고, 상대 경로 구조와 BIN·텍스처를 함께 관리해야 한다.

목록의 정상 응답은 실제 파일 다운로드·임포트 성공 증명이 아니다. Blender 버전, 색공간, 노멀 방향, 재질 연결과 축척·원점은 실제 소규모 파일럿에서 확인해야 한다. 이번 조사에서는 바이너리 파일을 내려받지 않았다.

04 / 우리 게임에서는 “직접 투입”보다 “재료화”

현재 전제는 KayKit 저폴리 원본 → 베이크 스프라이트 → Standard Ink 스타일, 약 40도 카메라다. Poly Haven의 강점은 실사 스캔·재질·환경 조명이다. 저작권 문제는 작아도 서로 다른 소스의 그림체가 자동으로 통일되지는 않는다.

필요한 후보 1–2개만 선택 → 격리 장면 → 기존 카메라·광원 유지 → 형태·색 단순화 → 스프라이트/타일 베이크 → 실제 화면 비교
  1. 먼저 환경 소품. Rock 07과 포장길 텍스처부터 작은 샘플로 보는 것이 낫다. 플레이어·몬스터·무기 애니메이션을 이 라이브러리로 교체하는 작업은 아니다.
  2. 그림체가 우선. 실사 노멀·거칠기·색 얼룩을 덜어 내고 기존 외곽선·팔레트·광원 방향·픽셀 밀도와 맞춘다. 같은 카메라 각도만으로는 충분하지 않다.
  3. 모바일에는 최종 산출물을 예산화. 스프라이트 베이크 방식이면 원본 모델 폴리곤은 주로 오프라인 제작 비용이다. 게임 성능은 최종 아틀라스 크기·장수·드로콜·알파 오버드로·메모리로 다시 측정해야 한다. 3D 직접 렌더라면 LOD·메시·재질 수를 별도 최적화한다.
  4. 압축 파일 크기와 메모리는 다르다. 일반적인 RGBA8 1024×1024 텍스처 한 장은 압축 없이 기본 레벨만 4 MiB, 전체 밉 포함 약 5.33 MiB다. 세 장이면 약 16 MiB다. 이는 산술 예시이며 실제 포맷·압축·엔진 측정값이 아니다. 1K부터 검토하고 8K·16K를 무작정 싣지 않는다.
  5. 운영 의존은 최소화. 게임 실행 때 매번 외부 API를 호출하기보다, 선정·제작 단계에서 필요한 자원만 확보하고 CC0 출처·ID·조회일·파일 해시를 작업 기록에 남긴다. 라이브 API를 노출하는 자산 브라우저를 만들 때만 식별 헤더·Poly Haven 출처표시를 구현한다.

최종 결론: “써도 되나?”에는 된다. “지금 우리 ARPG에 전부 넣나?”에는 아니다. 라이선스가 아니라 스타일 정합성과 제작 비용이 핵심 제약이다. 이번에는 후보 선정까지만 했으며 게임 코드·아트·기존 조명은 변경하지 않았다.
