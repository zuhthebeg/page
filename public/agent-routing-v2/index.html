Agent-Aware Smart Routing
Design v2

반복되는 비개발 업무(Jira 티켓 발급, 위키 분석 같은)를 에이전트로 처리하는 플랫폼에서, 요청의 요구사항을 한 번 확정하고 그에 맞는 실행 방식과 모델·추론 레벨을 고르며 결과로 정책을 개선하는 설계다. 1차 초안을 별도 검토 보고서와 교차 비교한 뒤 다시 썼다. 이 문서는 설계안이다. 구현도 실측도 아직 없고, 숫자 기준은 전부 사전에 정한 통과 조건(제안)이지 성능 주장이 아니다.

설계 문서v2스마트 라우팅레시피승인·커밋 원장오픈소스 후보

한 줄 요약: "라우터"가 아니라 "검증 가능한 업무 레시피 + 모델·추론 arm 선택 + 승인 원장"으로 책임을 쪼갠다.
✓ 유지: 요구사항 확정 → 실행 방식 결정 → 결과 기록 → 정책 제안의 큰 흐름 ✓ 유지: 자기 개선은 추천까지만, 적용은 관리자 승인 △ 변경: 캐시하는 것은 "완성된 요구사항"이 아니라 "승인된 레시피 + 최신 전제조건" △ 추가: 쓰기 작업은 승인 바인딩·커밋 원장·사후 확인을 통과해야만 실행 ✗ 제거: LLM이 내는 점수(복잡도·위험도·확신도)를 정책 입력으로 쓰는 것 ✗ 제거: MVP의 온라인 학습(bandit), 스킬 자동 생성, 턴 단위 모델 전환

1. 이 문서가 다루는 것과 1차 초안에서 바뀐 것

1차 초안의 철학은 유지한다: 한 번 성공한 업무 실행 패턴을 조직의 실행 정책으로 쌓아, 시간이 지날수록 불필요한 추론과 고비용 모델 사용을 줄인다. 다만 이 문장은 "성공"의 정의, "재사용"의 안전 조건, "정책"의 변경 권한이 비어 있으면 위험한 약속이 된다. v2는 그 세 가지를 채우는 쪽으로 고쳤다.

영역1차 초안v2
캐시 대상요구사항이 확정된 실행 정책(cache key로 조회)사람이 검토한 레시피(동결된 상태 기계)를 재사용하고, 슬롯 값·권한·자료 revision은 매번 새로 바인딩
분류Resolver 한 단계가 intent·슬롯·복잡도·위험도를 산출2단계: 결정 모델은 "승인된 레시피 중 하나 / none / unknown" 선택만, 슬롯 추출·질문 생성은 생성 모델
복잡도·위험도모델이 판단한 점수 계열복잡도는 결정론적 feature bucket, 위험도는 레시피의 operation과 도구 권한에서 코드로 도출
쓰기 작업실행 후 성공/실패 기록승인이 payload·revision에 묶이고, 커밋 원장·멱등성·unknown_commit 재조정·read-back 확인
상태need_more_info / ready 정도awaiting_confirmation, unknown_commit, cancelled 추가
학습성공 로그로 정책 추천paired holdout 평가, 선택 확률(propensity) 로깅, 성공 3분해, 실패 원인 귀속, shadow → canary → 승격
가상 모델agent-smart 등 한 가지 의미모드 A(자체 하니스)와 모드 B(투명 게이트웨이)를 분리하고, B는 세션 고정 라우팅
저장소Postgres + Redis 전제내구 DB가 정본(SQLite 기본, Postgres 선택), Redis는 선택 가속층
검증MVP 시나리오 중심실험 5개와 통과 조건, 중단 기준을 문서에 고정. 기준은 결과를 보고 바꾸지 않는다

2. 설계 원칙

  • 책임을 분리한다. 의미 판정, 업무 절차, 권한·승인, 모델 선택, 학습 제어는 서로 다른 컴포넌트다. 한 곳에 겹치면 실패 원인을 귀속할 수 없다.
  • 확정된 계약 없이 쓰기 없음. 읽기 전용 탐색(검색, dry-run 준비)은 계약 전에도 허용하되, 쓰기는 승인된 계약과 레시피 없이는 금지한다.
  • 점수가 아니라 분류와 코드. LLM에게 "복잡도 0~1"을 물으면 같은 입력에서도 값이 출렁인다(우리 쪽 관측). 모델은 닫힌 선택지에서 고르게만 하고, 수치는 결정론적 규칙으로 계산한다.
  • 승인된 것만 재사용. 한 번 성공했다고 레시피가 되지 않는다. 사람이 검토·동결한 것만 재사용 대상이다.
  • 정책 변경은 제안과 승인. 시스템은 후보를 만들고 오프라인으로 평가해 보고하며, 범위를 넓히는 변경은 사람이 승인한다.
  • 자료는 데이터지 지시가 아니다. 위키·티켓 본문을 학습 입력이나 제어 입력으로 쓰지 않는다(프롬프트 인젝션 방어).
  • 모르면 묻거나 멈춘다. unknown과 none은 정상 출력이며, 이때의 기본 동작은 사람에게 질문 또는 사람이 고르는 워크플로우다.

3. 두 가지 제품 모드

1차 초안은 "임의 모델명을 지정하면 Codex나 Claude Code에서도 동작"을 하나의 기능처럼 다뤘다. 실제로는 만들 수 있는 것이 두 가지로 갈린다.

모드 A — 자체 하니스 (이 설계의 본체)

  • 플랫폼이 대화 입구부터 실행까지 쥔다. 업무(job) 단위로 라우팅하고, 레시피·승인·원장·결과 학습이 전부 가능하다.
  • 비개발 대상 반복 업무는 여기서 다룬다.

모드 B — 투명 게이트웨이 (호환용)

  • Codex·Claude Code 같은 외부 클라이언트가 agent-smart 같은 모델명으로 호출하면 게이트웨이가 실제 모델을 고르는 방식.
  • 세션(또는 업무) 단위로 라우트를 고정한다. 턴마다 모델을 바꾸지 않는다. 이유: thinking 서명은 모델·계정·방향에 묶이고, 모델을 바꾸면 프롬프트 캐시가 새로 시작해 비용이 오른다(공식 문서 기준, 우리가 재현하지는 않음).
  • 게이트웨이가 아는 것은 사용량·지연·캐시뿐이다. 업무 성공 여부는 모른다. 학습은 클라이언트와 명시적으로 연동했을 때만 가능하다.
  • 호환 조건은 문서로 확인된 범위로 한정한다: Codex는 wire_api="responses" 계열 프로토콜이 필요하고, Claude Code에 비-Claude 업스트림을 붙이는 구성은 Anthropic이 지원하지 않는다고 적고 있다. 실패하면 지원 범위를 줄이고, 지원 밖 기능을 조용히 버려서 "통과"로 만들지 않는다.

4. 아키텍처

사용자 대화
  └─ Conversation API
       └─ [1단] Contract Resolver (결정 모델: 레시피 선택 / none / unknown)
            └─ [2단] Slot Extractor (생성 모델: 슬롯 추출, 부족하면 질문 생성)
                 └─ Task State (episode 단위, 후속 발화·정정·취소 연결)
                      └─ Contract 확정 + (쓰기면) 사용자 승인 ── 승인은 payload·revision에 바인딩
                           └─ Policy Router (레시피 호환 arm 중 선택, 결정론적 feature 사용)
                                └─ Executor (레시피 상태 기계 실행, 도구 allowlist, 검증기)
                                     ├─ Commit Ledger (멱등 키, 외부 쓰기 기록, unknown_commit 재조정)
                                     └─ Outcome Log (성공 3분해, 실패 귀속, 선택 확률)
                                          └─ Policy Analyzer (오프라인, 추천만) → shadow → canary → 관리자 승인

v1의 Execution Profile(모델 + 추론 + 스킬 + 도구)은 v2에서 레시피(절차·도구·검증)와 arm(모델·추론·프로토콜·한도)으로 분리했다. 스킬과 arm이 한 묶음이면 모델을 바꿀 때 절차 검증이 같이 무효화된다.

5. 계약 단계: 2단 resolver와 닫힌 선택

5.1 task_type은 열린 분류가 아니라 닫힌 선택

결정 모델(Luna, Jev 계열, Decisions API 같은)은 "승인된 레시피 목록 + none + unknown" 중에서 고르는 판단만 한다. 새 업무 유형을 모델이 만들어내지 않는다. 목록 밖이거나 확신이 낮으면 none/unknown이고, 이때는 사람에게 묻거나 사람이 고르는 워크플로우로 간다. 후보 순서를 바꿔도 같은 답이 나오는지(순서 편향)는 실험 E1에 넣는다.

5.2 슬롯 추출과 질문 생성은 별도 단계

결정 모델은 선택·점수·예/아니오 확률을 내는 쪽이라 "빠진 슬롯이 무엇이고 어떻게 물을지"를 쓰지 못한다. 그래서 2단계로 나눈다. 슬롯 추출기는 레시피의 슬롯 스키마에 맞춰 값을 뽑고, 필수 슬롯이 비면 질문을 만든다. 추출 결과는 스키마·권한 검사를 통과해야 계약 후보가 된다.

5.3 Task State와 상태 값

상태의미
collecting레시피 후보 또는 필수 슬롯이 아직 부족해 질문 중
awaiting_confirmation계약이 만들어졌고 사용자 승인 대기. 승인은 이 시점의 payload와 revision에 묶임
ready승인(또는 읽기 전용이라 불필요) 완료, 실행 가능
running / done / failed실행 중 / 검증 통과 / 실패(원인 귀속 포함)
unknown_commit쓰기 응답이 불명확해 실제로 반영됐는지 모름. 재시도 전에 재조정(조회)부터
cancelled승인 후 취소 포함. 취소는 원장에 남긴다

승인 후 사용자가 내용을 정정하면 승인은 무효이고 awaiting_confirmation으로 돌아간다. 후속 발화가 기존 episode의 연속인지 새 업무인지는 E1에서 따로 잰다.

6. 레시피와 arm

6.1 정의

  • 레시피 = 사람이 검토해 동결한 제한된 상태 기계. 슬롯 스키마, 사전·사후 조건, 단계, 도구 allowlist, 검증기, 승인 바인딩, 재시도 정책, 의존성 해시(스키마·위키 revision 등), 호환 arm 목록, 무효화 조건을 가진다.
  • arm = 고정된 모델 스냅샷 × 추론 effort × 프로토콜 × 토큰·시간 한도 × 폴백. 모델 별칭이 아니라 스냅샷을 고정해야 정책 비교가 재현된다.
  • job = 한 episode에서 레시피 하나를 특정 슬롯 값·권한·자료 revision으로 실행한 인스턴스.

6.2 스키마 예시 (설계 수준의 예시이며 실제 필드명은 구현 시 확정)

recipe: jira.create_issue
version: 1
operation: create            # 위험도는 여기서 도출 (create/update/delete/bulk, read)
slots:
  project:  {type: enum, source: user_acl_projects, required: true}
  summary:  {type: string, max: 200, required: true}
  type:     {type: enum, values: [Bug, Task], required: true}
  details:  {type: string, required: false}
preconditions:  [user_can_create_in(project), project_schema_hash == pinned]
steps:
  - dry_run_payload        # 읽기 전용: 최종 payload 조립
  - request_approval       # payload 해시에 바인딩
  - commit_with_idempotency_key
  - read_back_and_verify   # 생성된 이슈를 다시 읽어 슬롯과 대조
tools_allow: [jira.read, jira.create]
validators: [schema_valid, read_back_matches_slots]
compatible_arms: [arm.small.low, arm.mid.medium]   # E2에서 통과한 것만
invalidate_on: [project_schema_changed, tool_permission_changed, model_snapshot_retired]

6.3 위험도와 복잡도는 코드로

  • 위험도는 레시피 operation(create·update·delete·bulk·read)과 도구 권한에서 도출한다. 추론이 많이 필요한지와는 직교한다: 쉬운 삭제도 위험하고, 어려운 분석도 읽기 전용이면 낮은 위험이다.
  • 복잡도는 입력 길이, 문서 수, 슬롯 수, 도구 호출 단계 수, 이전 재시도 횟수 같은 결정론적 feature를 구간(bucket)으로 나눈 값을 쓴다.
  • 모델 확신도는 "물어볼지 말지"의 참고 신호일 뿐 정책 키가 아니다. 보정(calibration)은 E1에서 측정한다.

7. 승인·커밋 레이어

1차 초안에는 이 층이 거의 없었고, 교차 검토에서 가장 큰 구멍으로 지적됐다. 쓰기 업무에서 라우팅 이득보다 중복 생성·잘못된 대상 쓰기 한 건이 훨씬 비싸다.

  • 승인 바인딩. 사용자 승인은 "이 payload, 이 레시피 버전, 이 자료 revision"에 묶인다. 하나라도 바뀌면 재승인.
  • 커밋 원장(ledger). 쓰기 의도, 멱등 키, 외부 시스템 응답, 결과를 append-only로 기록한다. 같은 멱등 키의 재시도는 중복 생성을 만들지 않는다.
  • unknown_commit. 타임아웃·연결 끊김처럼 반영 여부를 모를 때는 재시도 대신 조회로 재조정한 뒤 판단한다.
  • read-back 검증. 쓴 결과를 다시 읽어 슬롯과 대조한다. 모델의 "완료했습니다"는 성공 신호가 아니다.
  • 권한. 호출 사용자 기준 ACL을 도구 계층에서 강제한다. 모델이 고른 대상이라도 권한 밖이면 실행되지 않는다.
  • 데이터 분류와 provider allowlist. 자료의 분류 등급에 따라 보낼 수 있는 모델·provider를 제한한다. 라우팅 입력에 포함한다.

8. 재사용(캐시)과 저장소

  • 템플릿 선택과 인스턴스 바인딩을 분리. 재사용되는 것은 레시피(템플릿)다. 슬롯 값, 사용자 권한, 위키 revision은 실행마다 새로 묶는다. 비슷한 요청이라고 이전 결과를 그대로 내놓지 않는다.
  • 캐시 키에는 tenant, 정책 버전, 레시피 버전, operation, 복잡도 bucket, 도구·모델 capability manifest 버전이 들어간다. 이 중 하나가 바뀌면 자동 무효화.
  • 저장소. 정본은 내구 DB(기본 SQLite, 필요 시 Postgres). Redis는 있어도 되는 가속층이다. 없어도 동작해야 하고, 캐시 이득이 E3에서 안 나오면 MVP에서 뺀다. 공급자의 프롬프트 캐시와 Redis 캐시는 서로 다른 것으로 따로 계산한다.
  • 의미 유사도 기반 응답 캐시는 쓰지 않는다. "비슷하면 같은 답"이 아니라 "비슷하면 같은 절차를 새 입력으로 실행"이다. 위험한 근접 사례(다른 operation, 다른 프로젝트 권한)는 재사용 불가가 기본이다.

9. 결과 기록과 학습 루프

9.1 무엇을 기록하나

  • episode·job·레시피 버전·arm·선택 시점의 후보 목록과 선택 확률(propensity). 나중에 다른 정책을 오프라인 평가하려면 필요하다.
  • 성공을 하나로 뭉치지 않고 셋으로 나눈다: 도구 호출 성공 / 사후조건 충족(read-back 일치) / 사람의 사후 수정 없음.
  • 무응답은 라벨이 아니다. "사용자가 아무 말 안 함 = 성공"으로 세지 않는다. 지연 피드백(며칠 뒤 수정)을 받을 자리를 둔다.
  • 실패 귀속: resolver / 레시피 / 모델 / 검색 / 도구 / 정책 / 인프라 중 어디서 났는지. 귀속 없이는 "모델을 올릴지 레시피를 고칠지"를 정할 수 없다.
  • 저비용 arm이 실패하고 상위 arm으로 승격해 성공한 경우, 그 성공을 저비용 arm의 성공으로 세지 않는다.

9.2 개선은 어떻게 적용되나

  • 분석기는 오프라인에서 후보(예: 레시피 X의 기본 arm을 한 단계 낮춤)를 만들고, 시간 분할 holdout과 paired 비교로 평가한다.
  • 통과한 후보는 shadow(실행은 기존 정책, 새 정책은 기록만) → canary(소수 트래픽) → 승격 순서로 간다. 범위를 넓히는 변경(새 도구 권한, 쓰기 범위, 더 싼 arm을 쓰기 레시피에 적용)은 사람 승인이 필요하다.
  • MVP에서는 bandit·온라인 변이·스킬 자동 승격을 하지 않는다. 성공 한 건으로 새 레시피를 만들지 않는다. 데이터가 부족하면 "학습 중"이라 쓰지 않고 후보 보고서만 남긴다.
  • 위키·티켓 본문이 정책, 도구, 승인 규칙을 바꾸는 입력이 되지 않도록 격리한다.

10. 검증 실험 5개 (통과 조건은 사전 제안)

아래 수치는 성능 주장이 아니다. 데이터를 보기 전에 정해 두는 gate이며, 결과를 보고 바꿔 통과시키지 않는다. 표본이 모자라면 통과가 아니라 inconclusive다. 같은 job의 paraphrase를 독립 표본으로 부풀리지 않는다.

실험질문제안 통과 조건
E1 계약·후속 발화·경계 안전결정 모델이 레시피 선택과 연속 발화 연결을 안전하게 하는가 (결정론/sticky 기준, 생성형 resolver와 비교). 실제 episode 200개 이상 + 별도 적대 시나리오 400개위험 operation·대상 혼동이 승인 gate를 통과한 사례 0 / 자동 선택 구간 계약 정밀도 ≥99%, 자동 처리 coverage ≥60% / 후속 발화 연결 ≥98% / 불필요 질문 ≤10% / 앞단 p95 추가 지연 ≤1초
E2 model×effort 라우팅가장 좋은 고정 정책보다 이득인가. 비교군: 강한 고정 모델, 폼 + 결정론적 검증 + 직접 API, 레시피별 최저가 통과 arm, cheap+검증 cascade. 300 paired job 이상강한 고정 모델 대비 성공률 차이 95% CI 하한 ≥ −3%p, 심각한 안전 퇴행 0, 총비용 ≥30% 절감. 라우터 고유 가치는 레시피별 최선 고정 정책 대비 추가 ≥15% 절감 또는 ≥3%p 품질 개선
E3 레시피 재사용재사용이 안전하고 계획 비용을 실제로 줄이는가. 근접 위험 사례·무효화 장애 포함 200건 이상잘못된 operation·권한·버전의 근접 사례 실행 허용 0, 무효화 장애 차단 100% / 재사용 적합 판정 정밀도 ≥99% / 계획 비용 ≥25%, 전체 비용 ≥10% 절감. 미달이면 plan cache 제외
E4 두 CLI 호환(모드 B)auto 모델명이 스트림·도구 호출·thinking·캐시를 보존하는가. 클라이언트당 100 trace 이상지원 표기한 정상 경로 trace 100% 완결, 도구 ID 손실·중복 커밋 0, sticky 경로에서 thinking 손실 0, 캐시 read 비율 직접 호출 대비 악화 ≤5%p, 순수 중계 p95 추가 ≤200ms
E5 자기 개선제안 정책이 동결 정책을 holdout에서 이기고 오염을 막는가. outcome 라벨된 episode 200개 이상holdout 총비용 ≥10% 개선(E2 품질·안전 gate 충족) / escalation 회복 성공을 저비용 arm 독립 성공으로 센 사례 0 / 신뢰할 수 없는 문서·미인증 피드백이 권한·도구·승인 규칙 변경으로 승격된 사례 0 / 롤백 ≤5분
통계 주의. "0/1000 사고"도 표본이 독립이라고 가정할 때 오류율 95% 상한이 대략 0.3%다(rule of three). 0.1% 미만을 주장하려면 독립 표본이 약 3000개 필요하다. 합성 공격 표본은 실제 트래픽의 무작위 표본이 아니다. 그래서 쓰기에는 통계 gate와 별개로 스키마·ACL·승인 gate가 항상 남는다.

11. 중단 기준 (kill criteria)

  • 승인 없는 쓰기, ACL 누출, 잘못된 operation 커밋, 중복 생성이 한 번이라도 나오면 자동 실행을 즉시 멈추고 dry-run으로 전환한다. 라우팅 지표가 아니라 제품 안전 gate다.
  • E1의 정밀도와 coverage를 함께 못 맞추거나 질문 UX가 나빠지면: 의미 resolver를 운영 경로에서 빼고 좁은 결정론 선택기나 사람이 고르는 워크플로우로 전환.
  • E2에서 레시피별 고정 정책 대비 추가 이득 <15%이거나 강한 모델 대비 절감 <30%이거나 품질 CI를 못 넘으면: 범용 학습 라우터 개발 중단. 고정 arm과 레시피 자동화는 유지.
  • 대상 업무의 계획·추론 비용 비중이 작거나 반복 workload가 부족하면: plan cache 제외. (계획 비중이 10%면 완벽히 없애도 그 이상은 못 줄인다.)
  • 검증기 자체의 false accept가 안전 gate를 못 지키거나 성공 라벨을 못 믿으면: "스스로 개선" 약속 중단. 사람 검수에 투자.
  • E4를 못 넘기거나 모델 전환의 cold-cache 비용이 절감을 삼키면: 엔드포인트 단위 자동 전환 중단, 세션 고정 게이트웨이와 명시적 workflow로 제한.
  • E5가 재현되지 않으면: 온라인 학습·자동 승격 금지, 오프라인 추천 전용 유지.

가장 현실적인 반증 시나리오는 이것이다: Jira 이슈 생성은 에이전트가 필요 없을 수 있다. 폼 + 결정론적 검증 + 직접 API가 비용·안정성에서 이미 충분하면 라우터는 과잉 설계다. 그래서 E2 baseline에 이 비교군을 일부러 넣었다.

12. MVP 범위와 14일 일정

범위

  • 한 업무로 시작: 단일 Jira 이슈 생성(샌드박스 프로젝트). 읽기 전용 위키 분석 1~2개. 레시피 4~6개.
  • Incident → Jira 데모는 그대로 못 한다. 이슈가 여러 개 나오는 작업이라 하위 job으로 쪼개 job마다 승인을 받거나, 후속 단계로 미룬다.
  • 가장 먼저 만들 것: Jira dry-run 계약·승인·커밋 원장, 위키 근거 검증기, 레시피별 model×effort 결과 매트릭스, eval/ 픽스처. 가장 늦게 만들 것: 범용 intent 분류 체계, 자유로운 세션 중 provider 전환, 온라인 스킬 변이, bandit.

14일 (제안)

일작업
1–2실제 episode 100–200개 표본 확보·라벨링(수집 가능성은 미확인), E1~E5 픽스처 골격
3–4Task State 상태 기계, 레시피 4~6개 작성
5–6검증기, 커밋 원장, 샌드박스 Jira 연동
7–8alias 게이트웨이와 두 CLI 호환 spike(E4 예비)
9–10shadow 비교(기존 방식 vs 라우팅 후보)
11–12holdout 평가, 장애 주입(타임아웃·중복·권한 철회)
13–14감독 하 파일럿, 오프라인 후보 보고서. 통과 못한 실험은 통과라고 쓰지 않는다

13. 레포 구조와 스택 제안

agent-router/
  recipes/          # 버전 관리되는 YAML 레시피 + 스키마
  approval/         # 승인 바인딩, payload 해시
  ledger/           # 커밋 원장, 멱등 키, 재조정
  resolver/         # 1단 결정 선택, 2단 슬롯 추출
  policy/           # arm 정의, 라우터, 오프라인 분석기
  harness/          # 모드 A: 실행기·검증기
  gateway/          # 모드 B 어댑터 (Responses, Messages) — 하니스와 분리
  eval/             # E1–E5 픽스처와 러너 (먼저 만든다)
  docs/
  • 1차 초안의 Python 스택(FastAPI·Pydantic·SQLAlchemy·HTTPX)은 그대로 쓸 수 있다. 저장소만 SQLite 기본·Postgres 선택·Redis 선택으로 바꾼다.
  • eval/을 첫 커밋에 둔다. 통과 조건을 코드 옆에 박아 두면 결과를 보고 기준을 옮기기 어렵다.

14. 오픈소스로 만든다면 차별점

RouteLLM, Agentic Plan Caching, vLLM Semantic Router 같은 선행 작업과 "라우팅" 자체로는 새롭지 않다. 겹치지 않는 부분은 아래라고 본다(평가).

  • 레시피 스키마: 사람이 검토·동결하는 업무 절차 표준 형식과 무효화 규칙.
  • 커밋 원장과 승인 바인딩: 쓰기 업무의 안전 계층을 라우팅과 한 세트로 제공.
  • 실패 원인 귀속: resolver·레시피·모델·도구 중 어디가 문제인지 분리하는 로깅.
  • CLI 호환 적합성 스위트(conformance): 스트림, 도구 ID, thinking 보존, 캐시 비율을 클라이언트·버전별로 검사하는 테스트.

15. 우리 구조에서 먼저 써볼 후보

실제 업무 데이터 전에 개인 환경의 반복 작업으로 레시피 모양을 시험해 볼 수 있다. 아래는 후보이며 실제로 레시피화해 본 것은 아직 없다.

  • "조공" 파이프라인: 검증 → 페이지 게시 → 공유 → 보고. 쓰기(게시·포스팅)가 있어 승인 바인딩과 원장 시험에 적합.
  • page 승인 대기 점검: 읽기 전용 점검 후 보고. 낮은 위험 레시피의 기준선.
  • log 소모품 재고 등록: 사진 → 비전 추출 → 등록. 슬롯 추출 + 사용자 확인 + 쓰기의 작은 예.
주의. 회사에서 나온 아이디어나 데이터를 개인 레포에 옮기기 전에는 사내 정책과 IP 조항을 먼저 확인해야 한다. 개인 환경의 대화·작업 기록은 기업 배포용 데이터가 아니다. 이 문서는 회사 자료를 포함하지 않는다.

16. 아직 확인하지 않은 것

  • 실제 API 호출, CLI 설정 변경, Jira 생성, 게이트웨이 배포는 하지 않았다. 이 문서의 어떤 수치도 실측이 아니다.
  • 통과 조건(≥99%, −3%p, ≥30% 등)은 사전에 정한 제안이다. 표본 크기와 신뢰구간에 따라 조정이 아니라 inconclusive 판정을 받을 수 있다.
  • 참고한 외부 자료 26건은 검토 보고서 작성자가 본문을 읽은 것이며, 이 문서의 필자가 전부 다시 열어보지는 않았다. 문서에 주장이 있다는 뜻이지 재현했다는 뜻이 아니다.
  • Jev·Laya 등 특정 결정 모델의 한국어 정확도와 슬롯 추출 대체 가능성은 검증되지 않았다. Martian 같은 상용 라우터의 현재 API도 확인하지 못했다.
  • 우리 세션 기록에서 episode 100–200개를 뽑을 수 있는지는 확인하지 않았다.
  • 2주 일정은 실험 설계이며 달성된 사실이 아니다.
