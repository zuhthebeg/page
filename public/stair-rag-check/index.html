Research note · RAG · 2026-10-27

"RAG는 끝났다,
IBM이 환각 65배 줄였다"?

@HowToPrompt__의 게시물(조회 4만)은 IBM이 "파인튜닝된 RAG보다 환각이 65배 적은 검색기"를 만들었고, 생성 전에 검색 결과를 걸러 검증하며, 이제 "환각 0 = 책임 0"이라고 주장한다. 원 논문 STAIR (arXiv 2609.03874)를 열어 보니 65배라는 숫자는 계산이 되지만, 그 "환각"은 우리가 아는 환각이 아니다.

논문 원문 대조65배 역산우리 RAG 적용 판단

3/10판정: 논문은 진짜, 아이디어도 쓸 만하다. 게시물의 해석은 대부분 과장 또는 오독.
✓ IBM 저자들의 STAIR 논문·벤치마크 실재✓ 0.05% vs 3.25% → 65배는 산수상 맞음✗ "환각" = 답변 환각이 아니라 존재하지 않는 목차 항목을 고른 비율✗ 오답률은 여전히 18.67% — "환각 0"과 거리가 멂✗ "생성 전 필터·검증" 구조 아님, RAG 대체 아님

1. 논문이 실제로 한 것

보통 RAG는 문서를 일정 길이로 잘라(청크) 벡터 유사도로 찾는다. 그러면 책의 장·절 같은 구조가 사라진다. STAIR는 사람이 책에서 답을 찾을 때처럼 목차(ToC)를 보고 어느 절에 답이 있을지 고르게 한다.

  • Mistral-7B를 LoRA로 파인튜닝한다. 입력은 "질문 + 그 책의 목차 전체"(최대 14k 토큰), 출력은 정답 절 제목이다.
  • 답할 때 목차에 실제로 있는 맨 아래 항목만 출력할 수 있게 막는다(제약 디코딩).
  • 18권(6개 분야)으로 만든 새 벤치마크 SearchTome에서 평가한다. 책마다 따로 학습한다(최대 200 에폭).
검색기Recall@1
Mistral 그대로13.8%
BM25 (키워드)59.5%
DPR (NV-Embed-v2 벡터)68.7%
DSI (책 내용을 모델에 학습시킨 생성형 검색)76.9%
STAIR (DSI + 목차)82.6%

출처: 논문 초록·표. Recall@1 = 첫 번째로 고른 절이 정답일 확률.

2. "65배"는 어디서 나왔나

논문 오류 분석에 이 문장이 있다. DSI는 예측의 3.25%가 "맨 아래 항목이 아닌 것"(존재하지 않거나 중간 단계 목차)이었고, STAIR는 0.05%였다. 3.25 ÷ 0.05 = 65. 게시물의 65배는 이 비율이다.

즉 여기서 "환각"은 "목록에 없는 문서 ID를 지어낸 비율"이다. 그리고 STAIR가 그걸 거의 0으로 만든 주된 이유는 출력을 실제 목차 항목으로만 제한했기 때문이다. 모델이 똑똑해져서가 아니라, 없는 걸 말할 수 없게 막은 것이다.

같은 분석에서 STAIR의 전체 오답률은 18.67%다. 다섯 번에 한 번 꼴로 엉뚱한(하지만 실제로 존재하는) 절을 가져온다는 뜻이다. 엉뚱한 절을 받은 LLM이 그걸로 답을 지어내는 문제, 즉 게시물이 말한 "인용 달린 환각"은 그대로 남는다.

4. 한계 — 저자들이 직접 쓴 것

  • 목차가 있는 문서에만 통한다고 논문 한계 절에 명시했다. 교과서·매뉴얼·약관은 되지만, 메일·채팅·로그 더미는 해당 없다.
  • 책마다 파인튜닝한다. 문서가 바뀔 때마다 다시 학습해야 한다. 기업 문서가 매일 바뀌는 환경에는 비용이 크다.
  • 평가가 18권, 장/절 단위 위치 찾기에 한정된다. 실제 질의응답 정확도는 재지 않았다.

5. 우리한테 쓸 만한 것

파인튜닝까지 할 필요는 없다. 가져올 건 두 가지다. ① 목차 기반 검색: 약관·매뉴얼처럼 구조가 있는 문서는 청크 벡터 검색 대신 "목차를 보여주고 절을 고르게" 하는 방식이 잘 맞는다. 우리가 앞서 본 PageIndex가 같은 계열이고, 방카 AI 비서의 약관 조항 인용에 바로 적용할 수 있다. ② 출력 ID 제한: 검색 단계에서 모델이 고른 문서·조항 ID를 실제 목록과 대조해 없는 건 버린다. 구조화 출력(enum) 한 줄로 STAIR가 0.05%를 만든 핵심을 그대로 얻는다. "RAG가 끝났다"가 아니라 "RAG의 검색을 문서 구조에 맞춰라"가 이 논문의 실제 메시지다.
