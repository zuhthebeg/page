Personal Agent Protocol,
스펙이 공개됐다

2026-10-06 Sierra가 발표한 Personal Agent Protocol(별칭 Poppy)의 스펙이 공개돼 있다. 10월 7일에는 "블로그 이상의 정보가 없다"는 분석이었지만, 이번에는 draft 0.3 원문을 직접 읽고 당시 만든 확인 질문 8개에 하나씩 답했다. 사내 에이전트 플랫폼을 제공하게 될 수도 있는 입장에서 본 정리다.

프로토콜 분석Sierra · MetaOAuth · DPoPMCP · OpenAPI에이전트 플랫폼

8/10판정: 구현 설계가 가능한 수준의 스펙이 공개됐다. 다만 1.0 이전 draft이고 공식성 확인이 일부 남았다.
✓ 스펙 원문 공개 — draft 0.3, Apache 2.0, 저장소와 문서 사이트 존재 ✓ 발견·에이전트 신원·세션·스코프·회사 에이전트·오류·철회 모두 필드 수준으로 정의 ✓ 기반은 OAuth 계열 표준(RFC 8414·7523·9449 DPoP·7009·8628)과 MCP·OpenAPI. 별도 서명 체계를 새로 만들지 않았다 △ 1.0 이전이라 호환성 깨지는 변경을 허용한다. 결제·푸시 알림·버전·첨부·자체 호스팅 개인 에이전트는 미정 △ 감사 로그 형식과 정식 표준화 기구는 없다. 가시성은 "회사가 요청마다 에이전트·client_id·사용자를 안다"는 수준 △ 이 사이트·저장소의 운영 주체가 Sierra·Meta인지는 확인하지 못했다

점수는 "지금 공개된 정보만으로 구현 설계를 얼마나 할 수 있나"를 뜻한다. 10월 7일의 3/10에서 올렸다. 8에서 멈춘 이유는 draft라는 점, 공식 주체 확인 불가, 결제 등 핵심 확장이 비어 있다는 점이다(평가).

1. 무엇이 공개됐나

항목확인한 내용
공개 위치문서 사이트 personalagentprotocol.org, GitHub 저장소 personal-agent-protocol/personal-agent-protocol. 저장소를 내려받아 스펙 원문(spec.md), introduction, path-to-1을 읽었다
버전저장소 versions.json 기준 v0.1은 2026-10-09 공개(동결), v0.2는 10-24, 현재는 draft 0.3(변경 이력상 10-25 "Review draft 0.3"). 블로그가 "이달 말까지 v0.1"이라 했는데 실제 기록은 더 빠르다. 이 차이의 이유는 확인하지 못했다
라이선스Apache 2.0. 1.0 이전이라 breaking change 허용을 문서가 명시한다
구현 도구회사용 구현 키트, 검증기(validator), JSON Schema, 구현 가이드, 서드파티 구현 여러 개(typo3-poppy, poppyseed 등)와 독립 트래커가 이미 있다
접근 불가pap.sierra.ai는 로그인 페이지로 리다이렉트돼 접근 불가로만 기록하고 우회하지 않았다. Sierra 블로그 본문은 이번에도 스펙 주소를 링크하지 않는다

설계 파트너 목록에는 개인 에이전트 쪽 Instinct·Meta·OpenAI, 회사 쪽 Bank of America·PayPal/Venmo·Target·Walmart·United Airlines 등, 기술 제공자 쪽 Okta·Stripe·Shopify·Cloudflare·Visa·Mastercard·Sierra 등이 올라 있다. 이전 글의 "OpenAI 불참(2차 보도)"는 틀린 정보였다. Anthropic과 Amazon은 목록에 없다. 이 목록은 문서 자체의 서술이며 각 사의 확인을 받은 것은 아니다.

2. 구조 한눈에

회사는 /.well-known/poppy.json을 둔다. 개인 에이전트는 이 문서로 회사의 OAuth 발급자, 스코프, API, 회사 에이전트, 웹 세션 진입점을 알아낸다.

{"protocol_version":"0.3",
 "organization":{"name":"Example Company","domain":"example.com"},
 "auth":{"issuer":"https://auth.example.com","mediated":{...},"scopes":{...},
         "scope_hints":{"orders:write":{"changes":"irreversible","personal_data":true}}},
 "agent":{"protocols":[{"type":"poppy","endpoint":"https://api.example.com/poppy/conversations"}]},
 "web":{"browser_session_endpoint":"..."},
 "feedback":{"endpoint":"..."},"excluded_tasks":{"url":"..."},
 "apis":[{"type":"openapi","url":"..."},{"type":"mcp","url":"..."}]}

위 예시는 스펙 3장의 예를 줄인 것이다. 세션은 DPoP에 묶인 짧은 Session Token과 갱신용 Account Token으로 이뤄지고, 경로는 웹(브라우저 세션 합류), API(OpenAPI·MCP), 회사 에이전트와의 대화(7장) 세 가지다.

3. 인접 표준과 실제 관계

10월 7일에는 Visa TAP·Web Bot Auth를 신원 증명 후보로 놓고 비교했다. 스펙 원문, introduction, path-to-1, 가이드, 확장 문서에서 이 둘의 언급을 찾지 못했다(키워드 검색 기준). PAP는 요청 서명 체계를 따로 쓰지 않고 OAuth 계열로 풀었다.

표준스펙에서의 쓰임
RFC 8414 · 9728발급자 메타데이터와 보호 리소스 메타데이터. 회사 도메인과 발급자가 양방향으로 서로를 가리켜야 한다
RFC 7523 · 9449 (DPoP)에이전트가 자체 발급한 assertion으로 세션을 시작하고, 토큰은 DPoP 키에 바인딩된다
RFC 7009 · 8628 · 7636 · 9700토큰 폐기, 기기 코드 로그인, PKCE, 보안 모범 사례
MCP · OpenAPIAPI 경로. MCP는 Streamable HTTP(2025-06-18 이상), OpenAPI는 3.0·3.1. MCP 서버는 Session Token을 받고 보호 리소스 메타데이터에 발급자를 적어야 한다
Visa TAP · Web Bot Auth채택 근거 없음. 결제는 오히려 "기존 결제 프로토콜과 어떻게 맞출지" 미정 과제로 남아 있다

4. 사내 에이전트 플랫폼 대비 권고 (갱신)

아래는 스펙을 읽고 내린 내 판단이다. 스펙의 요구사항이 아니다.

  • OAuth 인가 서버에 DPoP를 먼저 얹는다. 이전 권고(OAuth 2.1 + MCP)는 유지하되 한 단계 구체화됐다. Poppy 세션은 DPoP 바인딩 토큰이 전제이고 JWT-bearer(RFC 7523) grant를 기존 인가 서버에 맞춤 구현해야 한다. 이 부분이 가장 큰 개발량이다.
  • 에이전트는 client_id(HTTPS URL)로 식별한다. Client ID Metadata Document와 private_key_jwt 방식이다. 사내 플랫폼이 에이전트를 발급하는 쪽이라면 이 문서 호스팅과 키 관리가, 받는 쪽이라면 client_id별 허용·차단·레이트 리밋이 필요하다.
  • 사용자와 에이전트를 분리해 기록. 이전 권고 그대로다. 스펙이 감사 로그 형식은 정하지 않으므로 사용자(pairwise ID), 에이전트(client_id), 세션을 기록하는 로그 스키마는 우리가 정해야 한다.
  • 스코프에 변경성·개인정보 힌트를 붙인다. scope_hints가 changes(none·reversible·irreversible)와 personal_data를 정의하므로 처음부터 이 두 축으로 스코프를 설계한다.
  • 코어 도구 레지스트리와 프로토콜 어댑터 분리. 유지. 이제는 어댑터 후보가 구체적이다: MCP, OpenAPI, Poppy 대화 엔드포인트, 브라우저 세션 진입점.
  • "회사 에이전트" 경로는 결정을 미룰 필요가 없어졌다. 대화 규격(메시지 작성자 구분, 스트리밍 이벤트, 사람에게 핸드오프, 종료)이 정의돼 있다. 다만 1.0 전이므로 지금은 어댑터를 얇게 두는 쪽이 안전하다.
  • 초기 도입은 검증기와 구현 키트로 먼저 돌려 본다. 스펙 변경이 잦다(10-09의 v0.1에서 10-25 무렵 draft 0.3까지 보름 남짓에 버전이 두 번 올랐다). 전용 구현을 대규모로 짜기보다 검증기를 통과하는 최소 구현으로 감을 잡는 편이 낫다.

한 가지 구분: PAP는 소비자의 개인 에이전트와 기업의 접점을 다룬다. 직원용 사내 에이전트가 사내 시스템에 접근하는 문제와는 방향이 다르지만, "사용자 위임 + 에이전트 신원 + 범위 제한 + 폐기"라는 구조는 같다(평가).

5. 체크리스트 8개에 대한 답

항목답 (스펙 draft 0.3 기준)
발견https://{도메인}/.well-known/poppy.json. 모든 URL은 HTTPS. organization.domain이 제공 호스트와 같아야 하고, 발급자의 RFC 8414 메타데이터 protected_resources에 해당 도메인이 있어야 한다(양방향 검증). 리다이렉트의 최종 경로도 well-known 경로와 같아야 한다
에이전트 신원client_id가 HTTPS URL이고 그 문서에 jwks_uri·redirect_uris가 있다. private_key_jwt로 인증한다. 회사는 사전 등록을 요구할 수 있고(invalid_client 401), client_id별 허용·차단·레이트 리밋을 둘 수 있다. 요청 단위 서명이 아니라 토큰 바인딩 방식
세션Session Token(DPoP 바인딩 접근 토큰, 수 시간, 불투명)과 Account Token(갱신 토큰). 세션 시작은 RFC 7523 JWT-bearer grant로, 자체 발급 assertion(iss=client_id, sub=pairwise 사용자 ID, aud=발급자, 만료 5분 이내, jti 128비트 이상)과 DPoP proof를 보낸다. 새 DPoP 키가 새 세션이다. 세션 하나에는 계정 하나(account_mismatch). 로그인 방식은 Direct(인가 코드+PKCE), Device(RFC 8628), Mediated(과도기용, 에이전트가 사용자 자격증명을 전달) 세 가지다
스코프회사가 정의하고 poppy: 접두사만 예약된다. OpenAPI 또는 auth.scopes에 설명한다. scope_hints로 changes(none·reversible·irreversible)와 personal_data를 알리며 MCP의 readOnlyHint류 주석을 본뜬 구조다. 읽기/쓰기 이상의 액션 단위 제한이 첫 버전부터 들어 있다. 게스트(로그인 전) 세션도 지원한다
회사 에이전트poppy 프로토콜(HTTPS JSON). POST 엔드포인트로 대화를 만들고 /{id}/messages, /{id}/events(스트리밍), /{id}/handoff(사람 연결, HTTP 202), /{id}/close를 쓴다. 메시지마다 작성자가 사람인지 AI인지 구분한다. 규격은 새로 정의했고 기존 에이전트 간 프로토콜을 재사용하지 않았다(찾은 범위 기준). 회사가 못 하는 일은 excluded_tasks와 대안, feedback 엔드포인트로 알린다
가시성·오류오류 코드가 정의돼 있다: invalid_client 401, invalid_grant 400, account_mismatch 400, invalid_target 400, invalid_dpop_proof, use_dpop_nonce, extension_required 403, rate_limited 429, invalid_token 401, insufficient_scope 403. 가시성은 별도 기능이 아니라 모든 요청에서 회사가 에이전트·client_id·사용자를 안다는 구조에서 나온다. 보안 고려사항(9장)은 프롬프트 인젝션, 비밀값을 모델 컨텍스트에 두지 않기, 웹 세션 합류 CSRF 등을 다룬다
철회·감사철회는 RFC 7009로 Account Token을 폐기하고, 사용자는 회사 계정 설정에서 연결을 끊을 수 있으며, 회사는 client_id를 차단할 수 있다. 감사 로그의 표준 형식은 없다. 폐기 후 세션이 로그아웃 상태로 이어지는 세부 동작은 요약 수준으로만 읽었다
거버넌스Apache 2.0, 피드백은 GitHub 이슈와 사이트의 인라인 코멘트. 정식 표준화 기구(IETF 등)는 찾지 못했다. 저작권자와 사이트·조직의 운영 주체는 확인하지 못했다. Sierra는 설계 파트너 목록에 이름이 있을 뿐 저장소가 Sierra 소유라는 근거는 아직 없다

확인하지 못한 것: 스펙 4.3(DPoP·Token Exchange)·4.6·4.7·7.4~7.13의 세부 동작 전체를 줄 단위로 검증하지는 않았다. 위 답은 개요 수준이며 구현 전에 원문 해당 장을 다시 읽어야 한다. operations 확장과 가이드 문서는 읽지 않았다.

결론

PAP는 이제 발표문이 아니라 읽을 수 있는 스펙이다. 기반이 OAuth·DPoP·MCP·OpenAPI라서 사내 에이전트 플랫폼이 이미 갖췄거나 곧 갖출 요소와 많이 겹친다. 반대로 JWT-bearer grant, client_id 메타데이터 문서, DPoP 바인딩은 새로 해야 한다. 아직 draft이고 결제·알림이 비어 있으며 운영 주체가 불분명하므로 전용 대규모 구현은 이르다. 검증기로 최소 구현을 돌려 보고, 어댑터를 얇게 유지한 채 버전 변화를 따라가는 것이 합리적이다.
