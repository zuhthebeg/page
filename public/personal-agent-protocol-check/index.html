Personal Agent Protocol,
스펙이 나오기 전에 알 수 있는 것

2026-10-06, Sierra가 Meta 등과 함께 개인 에이전트가 기업과 상호작용하는 개방형 표준 "Personal Agent Protocol(PAP)"을 발표했다. 사내에 에이전트 플랫폼을 제공하게 될 수도 있는 입장에서, 실제 인터페이스가 얼마나 구체적으로 확인되는지부터 따져봤다.

프로토콜 분석Sierra · MetaOAuthMCP에이전트 플랫폼

3/10판정: 발표는 사실이다. 그러나 구현할 수 있는 인터페이스 정보는 아직 거의 없다.
✓ 공식 발표 실존 — Sierra 블로그(Bret Taylor, Clay Bavor), 파트너 7곳 명시 ✓ 확정된 기술 요소 3가지 — OAuth 기반 세션, 게스트→로그인(읽기 전용/쓰기 선택), 회사가 고르는 세 경로(웹·API·회사 에이전트) ✗ v0.1 스펙·레퍼런스 구현·저장소는 아직 공개되지 않았다. "이달 중 공개 예정"이 전부다 △ 발견 방식, 에이전트 신원 증명, 세션 객체, 스코프 어휘, 오류 모델은 전부 비어 있다 △ "누구나 구현 가능"은 스펙이 나와야 확인할 수 있다. 거버넌스와 라이선스도 미공개

점수는 "지금 이 정보만으로 구현 설계를 얼마나 할 수 있나"를 뜻한다. 방향은 분명하지만 바이트 단위 규격은 없다. 이 상태에서 PAP 전용으로 만들기보다, 겹칠 가능성이 높은 OAuth·MCP 층부터 맞춰 두는 편이 안전하다는 것이 이 글의 결론이다(평가).

1. 블로그가 실제로 말한 것

공식 블로그 본문을 직접 읽고 정리했다. 기술적으로 읽을 수 있는 문장은 많지 않다.

요소블로그의 서술비어 있는 것
발견웹사이트에서 에이전트가 회사가 제공하는 것과 접속 방법을 알아낸다어떤 URL·문서·형식인지
세션 시작에이전트가 사용자를 대신해 세션을 시작한다. 게스트로 시작할 수 있다세션 객체의 형식과 수명
로그인회사 페이지에서 로그인하거나, 에이전트에 이미 설정된 자격증명을 쓴다. 읽기 전용/쓰기는 고객이 정한다자격증명의 종류, 에이전트가 누구인지 증명하는 방법
기반세션은 OAuth 위에 만들어지고, 채널을 넘어 이어진다OAuth 프로파일(어떤 grant, 토큰 형식, 스코프)
경로웹사이트 탐색 / API(MCP, OpenAPI 등 표준) / 회사 에이전트. 무엇을 열지는 회사가 결정회사 에이전트 호출 규격(에이전트 간 프로토콜)
후속 확장세부 권한, 푸시 알림, 결제 확장을 "could"로 언급모두 미정. 결제는 첫 스펙에 포함되지 않는다고 보도됨

파트너 인용문은 Genesys, Rocket, Shopify, Stripe 네 곳만 실려 있다. Walmart는 파트너 목록에 이름만 있고 Instinct는 "참여 예정"으로 적혀 있다. Meta 자체의 별도 발표문도 찾지 못했다. 그래서 "누가 얼마나 깊게 참여하는지"는 확인되지 않는다.

2. 스펙은 있나

확인한 곳결과
Sierra 블로그"v0.1 스펙을 이달 말까지 공개하고, 설계 워크숍을 열고, 레퍼런스 구현을 공개할 계획"
GitHub 저장소 검색PAP 관련 저장소를 찾지 못했다
추정한 스펙 주소 몇 곳404이거나 로그인·인증 뒤에 있어 공개 문서로 확인하지 못했다. 접근 제한을 우회해서 열어보지는 않았다
독립 보도(TNW, FourWeekMBA, explainx 등)모두 블로그 내용을 재서술한다. "스펙은 읽지 못했다"고 명시한 곳도 있다

즉 블로그 이상의 기술 정보는 현재 공개 경로에서 확인되지 않는다. 구체적인 필드와 엔드포인트를 말하는 글이 있다면 스펙이 아니라 추측일 가능성이 높다.

3. 비교용 인접 표준 — PAP가 쓴다는 근거는 없다

블로그가 확정한 표준 이름은 OAuth, MCP, OpenAPI뿐이다. 아래는 같은 문제를 이미 푼 표준들로, 스펙이 나왔을 때 비교 기준으로 쓰기 위해 원문에서 확인한 내용이다.

표준원문에서 확인한 핵심PAP와의 관계
MCP 인증(2026-07-28판)OAuth 2.1 기반. 서버는 RFC 9728 보호 리소스 메타데이터 구현이 MUST. 클라이언트는 RFC 8707 리소스 지시자 사용이 MUST. Client ID Metadata Documents는 SHOULD. 401에 WWW-Authenticate로 resource_metadata와 scope를 알리고, 권한 부족은 403 insufficient_scope. 토큰의 audience 검증 MUST블로그가 MCP를 경로로 언급. 인증 프로파일을 공유하는지는 미공개
Visa Trusted Agent Protocol요청마다 서명하며 타임스탬프, 세션 ID, 키 ID, 알고리즘 ID를 포함. 가맹점 도메인과 작업에 바인딩되어 재사용 방지. 동의된 식별자를 쿼리 파라미터로 전달경쟁 또는 보완. 보도에 따르면 Stripe·Shopify는 양쪽에 모두 참여
Web Bot Auth(IETF 초안)HTTP Message Signatures로 자동화 클라이언트의 요청을 서명해 서버가 신원을 검증에이전트 신원 증명 후보지만 PAP 채택 여부는 미공개

눈여겨볼 차이: MCP 인증은 "토큰으로 접근 권한을 위임"하는 층이고, TAP·Web Bot Auth는 "요청 자체를 서명해 에이전트가 누구인지 증명"하는 층이다. PAP가 말하는 "기업이 에이전트가 누구를 대리하는지 안다"는 목표(Stripe 인용문의 "recognize their customers' agents")는 두 층을 모두 요구한다. 블로그는 OAuth만 확정했으므로 신원 증명 층이 무엇이 될지가 v0.1의 핵심 변수다(평가).

4. 사내 에이전트 플랫폼을 만들 입장에서 미리 할 일

아래는 공개 정보에서 추론한 내 판단이다. PAP 스펙에서 나온 요구사항이 아니다.

  • 도구 노출은 MCP 서버 + OAuth 2.1 + 보호 리소스 메타데이터로. 블로그가 OAuth와 MCP/OpenAPI를 명시했으므로 어떤 최종 스펙과도 겹칠 가능성이 가장 높은 조합이다.
  • 사용자와 에이전트를 분리해 기록. 토큰과 감사 로그에 "어떤 사용자의 위임으로 어떤 에이전트(client_id)가 호출했는지"를 둘 다 남긴다. 블로그가 기업의 가시성을 핵심 목표로 적었다.
  • 스코프는 읽기/쓰기부터 최소 분리하고 액션 단위로 확장 가능하게. 블로그가 세부 권한을 후속 확장으로 예고했다.
  • 게스트→로그인을 하나의 세션 ID로 묶는 세션 모델을 게이트웨이에 둔다. "로그인 전 질문과 로그인 후 주문 변경이 같은 방문"이라는 서술을 구현하려면 필요하다.
  • 코어 도구 레지스트리와 프로토콜 어댑터를 분리. 내부는 자체 레지스트리, 외부 노출은 MCP·OpenAPI 어댑터로 두고 PAP는 스펙이 나온 뒤 어댑터로 추가한다. 지금 PAP 전용으로 짜면 스펙 변경 때 되돌려야 한다.
  • "회사 에이전트" 경로를 따로 설계 대상으로 표시. 외부 에이전트가 사내 에이전트를 호출하는 규격은 블로그에 없다. 이 부분은 스펙을 보기 전까지 결정을 미룬다.

한 가지 구분: PAP는 소비자의 개인 에이전트와 기업의 접점을 다룬다. 직원용 사내 에이전트가 사내 시스템에 접근하는 문제와 방향은 다르지만, "사용자 위임 + 에이전트 신원 + 범위 제한 + 감사"라는 구조는 같다. 사내 플랫폼을 나중에 외부 에이전트에게도 열 가능성이 있다면 이 구조를 처음부터 맞춰 두는 쪽이 이득이다(평가).

5. v0.1이 공개되면 확인할 것

항목확인 질문
발견지원 기능을 알리는 문서의 위치와 형식은 무엇인가(.well-known 같은 규약이 있는가)
에이전트 신원누구를 대리하는지 어떻게 증명하는가(서명, 증명서, 사전 등록)
세션세션 객체의 형식과 수명, 채널 간 이어짐은 어떻게 구현되는가
스코프읽기/쓰기 이상의 어휘가 있는가, 액션 단위 제한이 첫 버전에 들어가는가
회사 에이전트에이전트 간 호출 규격이 정의되는가, 기존 규격을 재사용하는가
가시성·오류기업이 에이전트 활동을 어떻게 보는가, 거부·재시도 오류 모델은 무엇인가
철회·감사사용자와 기업 양쪽에서 위임을 어떻게 철회하고 추적하는가
거버넌스라이선스, 소유 주체, 다른 회사의 참여 방식. Amazon·OpenAI·Anthropic 참여 여부(Forkast 보도로는 현재 불참)

결론

PAP는 방향이 구체적이다. OAuth 세션, 읽기 전용/쓰기 선택, 웹·API·회사 에이전트라는 세 경로, 파트너 7곳이다. 그러나 인터페이스는 아직 문서가 아니라 발표문이다. 스펙이 공개되기 전에 필드 수준의 구현을 결정하면 위험하고, OAuth·MCP·감사 로그·세션 모델처럼 어떤 결론이 나와도 쓰일 층을 먼저 맞춰 두는 것이 합리적이다. v0.1이 나오면 위 5번 항목으로 다시 점수를 매길 수 있다.
