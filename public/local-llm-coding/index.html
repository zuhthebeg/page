01 배경 — 왜 지금 로컬인가

저자의 출발점은 비용이다. GitHub Copilot이 크레딧/무료 모델 체계에서 사용량 기반 과금으로 전환했고(Copilot은 토큰 재판매상이라 인상폭이 더 노골적), 플래그십 모델은 출시 때마다 가격이 크게 뛰는데 성능은 같은 속도로 오르지 않는다는 지적이다.

예시로 든 게 Flash 3.5가 2.5 대비 +3×, GPT 5.5가 5 대비 +3× 가격이라는 것. 핵심 주장: 최신·최고 모델의 가격은 성능 개선 대비 기하급수적으로 비싸다. 그래서 "로컬이 SOTA를 못 따라간다"는 건 맞지만, 그게 곧 "로컬을 쓸 이유가 없다"는 뜻은 아니라는 것.

02 로컬을 쓸 이유 — 저자의 다섯 논점

  • 가격/성능 비율. 클라우드 SOTA는 성능 1을 더 얻는 데 비용이 지수적으로 든다.
  • 결정론적 하니스로 보완. 도구·지시·스캐폴딩을 잘 짜면 약한 모델의 품질을 최대 6배까지 끌어올릴 수 있다는 주장. (수치 출처는 본인 경험 — 벤치마크가 아님은 분명히 해둔다.) 같은 결의 실증으로는 우리가 이미 정리한 Harness-1이 있다.
  • 벤치마크 함정. 모델을 스칼라 하나로 줄이는 건 위험하고, 각 랩은 자기에게 유리한 벤치만 강조한다. 네 워크로드로 직접 돌려봐야 진짜를 안다.
  • 지정학. 미국 랩이 무료로 푸는 건 최고작이 아니다 — gpt-oss-20b는 낡았고, Anthropic은 오픈웨이트가 없으며, 서구에서 진지한 오픈모델은 사실상 Gemma 4뿐. 반면 중국 랩(Qwen·Kimi·GLM)이 매우 유능한 모델을 푼다.
  • "뇌 위축" 논점. 약한 모델은 사람이 더 개입하게 만들어 오히려 사고력 유지에 낫다 — 자동화에 사고를 전부 넘기는 건 "내 일은 자동화 가능하다"는 자백이라는, 다분히 철학적인 주장. (분석가 주: 동의 여부는 갈릴 영역.)

03 코딩용 모델 선택 — Gemma 4 라인업

저자는 코딩 리더보드 상위가 대체로 중국 모델(Qwen·DeepSeek·Kimi)이라면서도, 본인은 일반 작업(계획·탐색)과 코드 생성의 균형이 좋은 Gemma 4를 추천한다.

버전특징저자 코멘트
E2B (2B, edge)대부분 하드웨어서 구동환각·중도포기 위험 높음
E4B (4B)E2B의 2배 크기다운로드·설정 부담 적어 입문 추천
12B이미지 네이티브 이해(디코더 불필요)프런트엔드·비주얼 코딩에 유리, 오디오도 지원
26B A4B (MoE)26B 중 4B만 활성, 8–12GB VRAM 목표저자 최애 — E4B보다 똑똑
31B (dense)구글 최대 오픈웨이트, 비MoEVRAM 많이 필요 — 본인 AMD APU선 1–2 TPS로 비실용

메모리 절약은 QAT 변형(예: E4B QAT, 품질 유지)으로, 추가 효율은 Unsloth 최적화본으로. 코딩 에이전트엔 Tool Use(필수)·Vision·Reasoning 세 능력이 핵심이라고 못박는다.

04 로컬 실행 스택 — 4개 레이어

저자가 정리한 구성요소. OpenAI 호환 API가 사실상 표준 접점이라는 점이 우리에겐 특히 중요하다.

레이어역할 / 선택지
하니스모델(확률적) 둘레의 결정론적 코드. VS Code Copilot · Copilot CLI · Pi 등
모델가중치 파일. 양자화(Q8/Q4 = 해상도 비유), 포맷(GGUF/MLX)
런타임 (추론엔진)Llama.cpp(가장 대중적, GGUF/MLX) · MLX(Apple) · ONNX(브라우저/모바일, transformers.js) · vLLM(서버)
모델 매니저 (선택)Ollama(OSS, llama.cpp 래퍼) · LM Studio(무료·비OSS, SDK+REST, GUI 풍부) · Jan(무료+OSS). 핵심 = OpenAI 호환 API

하드웨어가 부족하면 OpenRouter의 무료 모델로 우회 가능하다고 언급(클라우드지만 무료).

05 실전 함정 — LM Studio에서 직접 데인 것들

가이드에서 가장 값진 부분. "그냥 켜면 되겠지"가 안 되는 지점들이다.

  • 기본 컨텍스트가 4k다. LM Studio가 모델 로드 시 기본값으로 컨텍스트를 4096까지만 잡는다 — Copilot 클라우드 모델이 보통 200–400k인 걸 생각하면 치명적. 수동으로 키워야 한다. (그리고 설정 저장 안 하면 다음 로드에 기본값으로 되돌아감.)
  • JIT 콜드스타트. 모델은 요청 올 때 lazy-load → 첫 요청에 10–30초 추가(TTFT 악화). 타임아웃 있으면 미리 로드하거나 콜드스타트를 감안해야 함.
  • TTL. 유휴 시 메모리 회수 시점 조절 가능.

핵심 트레이드오프 — Gemma 4 26B를 기준으로 컨텍스트 길이별 VRAM 소요(저자 실측):

4,096 (기본값)
18.16 GB
150,000 (저자 선호)
22.45 GB
262,144 (최대)
25.74 GB

저자 기준 "최소 100k 토큰은 띄울 수 있어야 코딩에 쓸만하다". 즉 26B는 사실상 24GB+급 카드를 요구한다.

06 우리(cocy/openclaw) 스택에 주는 시사점

이 글은 우리가 이미 굴리는 구조와 정확히 맞닿는다 — 하지만 장밋빛으로 받지 말고 우리 하드웨어 현실에 비춰 읽어야 한다.

  • 접점은 이미 있다. llm.cocy.io가 OpenAI 호환 게이트웨이라, Ollama/LM Studio의 OpenAI 호환 API를 그 뒤에 한 모델로 꽂는 건 구조적으로 자연스럽다. 새 인프라가 아니라 라우팅 한 줄 추가 수준.
  • 그런데 12GB가 천장이다. 우리 워크스테이션은 RTX 3080 Ti = 12GB VRAM. 저자가 미는 26B A4B는 4k에서도 18GB+ → 우리 카드엔 안 들어간다. 현실적 상한은 E4B(QAT)나 12B 양자화이고, 역할도 코딩 자율 주행이 아니라 보조(분류·요약·단순 편집)다.
  • 그래서 위임 정책과 맞물린다. 단순·반복·토큰 소모형 작업은 위임한다는 우리 원칙([[feedback_delegation]]) 그대로 — 그 위임처를 부분적으로 로컬 모델로 돌리면 클라우드 토큰을 아낀다. 설계·판단은 여전히 프런티어 모델.
  • "6배"는 우리 워크로드에서 검증된 적 없다. 우리가 Headroom 평가에서 토큰 압축이 "우리 패턴엔 효과 애매"로 결론 냈던 것과 같은 태도가 필요하다 — 저자 주장을 그대로 옮기지 말고, 작은 PoC(한 가지 위임 작업을 로컬 E4B로)로 우리 숫자를 직접 재는 게 다음 수순.
액션 후보: Windows 박스에 LM Studio로 Gemma 4 E4B(QAT) 띄우고 → 컨텍스트 100k 수동 설정 → llm.cocy.io에 local-gemma 모델로 등록 → 위임 가능한 단순 작업 1종을 붙여 클라우드 대비 품질/비용 실측. (실행은 cocy 승인 후.)

07 유의점

  • 이 글은 벤치마크 논문이 아니라 오피니언/실무 가이드다. "6×"는 저자 경험치이고, "뇌 위축" 같은 논점은 견해 영역.
  • 원문 후반(VS Code Copilot/Pi 상세 설정 + 데모 앱 빌드)은 본 분석 범위 밖이라 요약하지 않았다 — 실제 셋업은 원문을 따라가야 한다.
  • 로컬 모델 판은 빠르게 변한다. 모델·런타임 권장은 글 작성 시점 기준이며, 우리도 도입 전 최신 리더보드를 다시 확인해야 한다.

수치·정리·해석은 본 분석이 cocy 앵글로 재구성한 것이며, 원전은 Alex Ewerlöf, "Using local LLMs for agentic coding".
